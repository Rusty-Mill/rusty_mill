## 2026-10-17 - rusty-mcp: first-party OTLP spans (sovereignty item 9, PR 2 of 3)

- **Why:** item 9 replaces the four OpenTelemetry crates with a first-party OTLP exporter (decisions D2 and D3). Metrics went in PR 1; spans are the rest, and with them nothing in `rusty-mcp` uses the SDK any more, so the four crates and their `tonic`/`prost`/`h2` tree leave `rusty-mcp` here rather than in a third PR.
- **Added:**
  - `otel::SpanLayer`, a `tracing_subscriber::Layer`. It follows each span from creation to close and exports it with its name (or `otel.name`), typed fields as attributes, `otel.kind` / `otel.status_code` / `otel.status_message`, and each event inside it as a span event.
  - A span carrying valid `trace_id` and `parent_span_id` fields, as `TraceContext::span` records them, is a child of that remote span: it adopts the trace id, follows the caller's `sampled` flag and passes on `tracestate`. A remote parent wins over a local one. Otherwise a span is a child of its `tracing` parent, otherwise it starts a trace sampled by `sample_ratio`; an unsampled span costs a map entry and nothing else.
  - `otel::set_attribute(&Span, key, value)` and `otel::AttributeValue`, for keys only known after a span is opened (a `tracing` field has to be declared at creation). It reaches the layer through the span's subscriber.
  - `otel::Signal` (`Traces`, `Metrics`).
  - Spans and metrics share one export thread design (`worker`): a bounded queue (4096 spans; more are dropped and counted, never blocking a request), batches of 512 or every 5 s, and the bounded shutdown from PR 1.
  - Limits per span: 128 attributes, 128 events, strings cut at 4096 bytes.
- **Changed (breaking for direct users of `rusty_mcp::otel`):**
  - **Transport:** spans are OTLP/JSON over HTTP, no longer OTLP/gRPC. `OtelConfig::endpoint` is the collector's OTLP/HTTP *base* URL (default `http://localhost:4318`); `/v1/traces` and `/v1/metrics` are added to it. Resolution follows the OpenTelemetry specification: for metrics `metrics_endpoint`, then `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`, then the base; for traces `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, then the base. The base is `endpoint`, then `OTEL_EXPORTER_OTLP_ENDPOINT`. A collector that only takes OTLP/gRPC on 4317 will not receive anything. Metrics now follow `endpoint` too, which closes the gap PR 1 left (metrics and spans on different endpoints and protocols).
  - **`pipeline`** returns `(OtelGuard, SpanLayer)`, not `(OtelGuard, SdkTracer)`: use `.with(layer)` where you used `.with(tracing_opentelemetry::layer().with_tracer(tracer))`.
  - **Removed:** `OtelGuard::provider()`, `TraceContext::attach_parent`, `TraceContext::otel_context`, `OtelError::Exporter`. `TraceContext::span` alone now makes the exported span a child of the caller's (with a `SpanLayer` installed), so `attach_parent` has nothing left to do. `OtelError` is now `Endpoint(Signal)` and `Thread(Signal, io::Error)` (it replaces PR 1's `MetricsEndpoint` / `MetricsThread`); an invalid endpoint is still refused without quoting it.
  - `TraceContext::span` also records `tracestate`.
  - **Resource:** spans carry the same resource as metrics: `OTEL_RESOURCE_ATTRIBUTES` with the config's `service.name` / `service.version` over it. The SDK's `telemetry.sdk.*` attributes are no longer sent.
  - **Span attributes:** the SDK layer's `code.namespace`, `code.filepath`, `code.lineno` and `thread.*` attributes are not sent, and the `trace_id`, `parent_span_id`, `sampled` and `tracestate` fields are now the span's own ids and flags rather than attributes beside it. Span links and `exception` handling are not implemented.
- **Gateway:** `agentgateway-mcp` and `agentgateway` drop their `opentelemetry` and `tracing-opentelemetry` dependencies. `mcpGuardrails.*` annotations go on through `otel::set_attribute`. `tracing.endpoint` is now an OTLP/HTTP base URL (it was the gRPC endpoint). The gateway's own start-up log line, which printed the raw endpoint, is gone: `otel::init` logs the origin only.
- **Not changed:** the metrics instruments, their names, units, buckets, attribute keys and cardinality guard; `McpMetricsLayer`'s API; `TraceContext`'s parsing and injection; the sampling rule (parent-based, ratio for roots).
- **Verified:** unit tests for the layer (typed fields, `otel.*` fields, late `record`, local and remote parents, a remote parent over a local one, unsampled callers and ratios, events, per-span limits, no leaks of closed or unsampled spans, a refusing sink), the span model and its limits, the OTLP/JSON encoding, endpoint resolution and the worker; `otel_export` against a fake HTTP collector (spans on the wire, a joined trace, a tree under the caller's span, an unsampled caller sends nothing, a full batch goes without a flush, `set_attribute` on the wire, an unreachable or refusing collector); `otel_resource` (spans and metrics carry the environment resource); `otel_redaction` (no secret from a span or metrics endpoint in a log line or error); the gateway's `mcp_span_attributes` against the new collector.
- **Known limitations:** a failed batch is dropped, not retried. The layer takes one lock per span event and close, which is fine at MCP request rates but would be the first thing to shard under much heavier span traffic. Spans still open when the process exits are lost. Between this and PR 3 (the `rusty-mcp` version bump, policy and docs) nothing else changes.
