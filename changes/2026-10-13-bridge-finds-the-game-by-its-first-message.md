## 2026-10-13 - rb_rl_bridge: the game is the connection that speaks like it

- **Changed:** `rb_rl_bridge` used the first connection to the game port as the game. A silent or junk connection (a port scanner, a health check, a leftover process) arriving before Rocket League left the real game's dial unaccepted, and the bridge waiting on the wrong socket. It now uses `GameListener::wait_for_game`: a connection is the game once its first message arrives and decodes as one of the game's. A connection that closes, sends something else, or stalls part-way through a message (ten seconds, `STALL_AFTER`: `peek` cannot see a close behind buffered bytes) is dropped and the wait goes on; a silent one waits (the game says nothing until a map loads, so a fixed deadline on speech would reject it); at most `MAX_CANDIDATES` (8) wait at once and a newer arrival drops the oldest, in arrival order, after every waiting connection has been looked at, so a game that has spoken is never the one dropped. At most 8 connections are taken from the backlog per pass, so a stream of arrivals cannot starve those checks or the timeout. The five-minute limit now runs only while nothing is connected. The bridge prints `serving bots on` as soon as the bots' port is taken (not after the game is found), a line when a connection arrives or is dropped, and `the game connected` when the game is found. **The live-test runner (`rl-lib.ps1`) now waits for the dial line (`waiting to speak`) instead of `serving bots on`**, because that line used to mean the game had connected and now means only that the port is bound.
- **Added:** `GameListener::wait_for_game(timeout, note)`, `wait_for_game_stalling` (the stall limit given), `MAX_CANDIDATES` and `STALL_AFTER`. It looks at a connection's first message with `peek`, so nothing is read and the link still gets that message. `wait_for_connection` is unchanged (the probe and tests still use it).
- **Verified:** twelve tests plus one unit test: silent squatter, junk, closed, a message in pieces, a message still arriving, a lone silent connection outliving the timeout, a full house, a game queued first behind silent connections, truncated messages followed by a close (four cut points), rejection followed by overflow (which are dropped, in order), the bridge binary's lines with a silent fake game, and the full-house look-before-drop. Each was checked to fail with its fix removed. Run by hand with the built binary: a silent squatter and then a fake game sending a real first message.
- **Known limitations:** this is not authentication, and a game still silent can be dropped by more than 8 connections arriving after it (it dials once). A local process that speaks the game's format before the game does is taken for it; telling processes apart would need the owner of the peer socket (PowerShell on Windows, `/proc` on Linux) and was not built. Not run against the real game: the check assumes the game's first message decodes with the tolerant decoder, which every live recording so far does. Board b36.
