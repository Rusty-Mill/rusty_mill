## 2026-10-12 - rusty_oauth, rusty_channel: NumericDate `exp` and `nbf`

- **Fixed:** `jwt::validate_claims` read `exp` and `nbf` with `as_i64`, which returns nothing for a fractional number or one above `i64::MAX`. For `nbf` that meant the claim was silently skipped, so a correctly signed token whose `nbf` was in the future but written as `4102444800.5` or `18446744073709551615` was accepted before its time. For `exp` it meant a fractional value was reported as missing, and with `require_exp: false` a malformed `exp` counted as absent, so the token never expired. Both are now read with the new `jwt::time_claim`.
- **`jwt::time_claim(claims, name)`:** absent is `Ok(None)`; an integer is exact; a fraction is rounded **up** to the next whole second, which keeps comparisons with whole-second clocks and leeways exact (rounding to the nearest second let a token through up to half a second early and rejected one up to half a second before it lapsed); a value beyond `i64` saturates (far future or far past) instead of being dropped; a present claim that is not a number (a string, `null`, a boolean, a structure) is an error, never "absent". `rusty_json` numbers are always finite, so no NaN case exists.
- **Changed behaviour:** a malformed `exp` or `nbf` is now rejected with "malformed `exp` claim: not a NumericDate" (before: `nbf` skipped; `exp` "missing" or, with `require_exp: false`, accepted). A valid fractional `exp` is now accepted. The expiry and activation boundaries are unchanged (`exp` is expired once `now - leeway >= exp`; `nbf` is not yet valid while `now + leeway < nbf`), and the comparison is widened to 128 bits so an extreme leeway or timestamp cannot overflow.
- **`rusty_channel` Teams verifier:** it does not call `validate_claims` and carried its own copy of the same `as_i64` reads. Its time checks are now one function, `check_times`, using `time_claim`; the 5-minute leeway and the boundaries are unchanged.
- **Affects:** `rleval-app`'s OIDC sign-in (through `validate_claims`) and the Teams verifier. Neither sets `require_exp: false`.
- **Verified:** eight new `rusty_oauth` tests and six new Teams tests cover fractions, values above `i64`, malformed types, absent claims, the exact boundaries and overflow. The original defect was reintroduced in the Teams verifier (the old `as_i64` reads) and caught. In `rusty_oauth`, each of these was broken in turn and caught: a malformed claim treated as absent (for `exp` and for `nbf`), saturation, rounding, both boundaries and the 128-bit widening.
- **Known limitations:** `rusty_oauth`'s token-introspection response still reads `exp` and `nbf` with `as_i64` into `Option<i64>`, so a fractional value there reads as absent; that is a public field type and was left alone. `rusty-mcp` has its own claim check (it accepts a token whose `exp` equals `now - leeway`, by design) and is unaffected. The behaviour of the real providers' tokens (do they ever send fractional values?) was not checked.
