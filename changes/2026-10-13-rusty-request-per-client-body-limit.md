## 2026-10-13 - rusty_http, rusty_request, rusty-mcp: a per-client response-body limit

- **Why:** a live check on 2026-10-13 found Bot Framework's JWKS (the Teams signing keys) is 909,694 bytes for 260 keys, 87% of the 1 MiB cap that `rusty-mcp`'s validator inherited from `rusty_http`'s `DEFAULT_MAX_BODY_LEN`. At about 3.5 KB a key there is room for roughly 39 more keys before a fetch of that document would fail closed.
- **Added:** `rusty_request::ClientBuilder::max_response_body_len(n)` sets the most bytes a buffered response (`send`) will read for that client; it is carried through redirects and retries. Over the limit is the same `InvalidResponse` ("... exceeded the maximum allowed size") as before, and a `Content-Length` body over it still fails before any of it is read. `rusty_http::async_tokio::AsyncTransport::read_body_with_limit(framing, max)` is the transport call underneath; `read_body` is now a call to it with the default.
- **Changed:** `rusty-mcp`'s JWKS client sets 4 MiB (`MAX_JWKS_BODY_LEN`), about 4.6 times the Bot Framework document. A larger JWKS fails the fetch ("JWKS fetch failed: ... maximum allowed size") instead of being read without bound.
- **Not changed:** the default limit (1 MiB) for every other `rusty_request` client; `rusty_http`'s `DEFAULT_MAX_BODY_LEN`, which also bounds the request bodies `rusty_http` servers accept; `send_streaming`, whose caller reads and bounds the body itself; the `tokio_native` transport, which `rusty_request` does not use.
- **Verified:** transport tests for all three framings at the exact boundary; `rusty_request` tests for the default, a raised limit with `Content-Length` and chunked bodies, exact boundaries for a lowered and a raised limit, and the redirect and retry paths; two `rusty-mcp` validator tests with real signed tokens (a 1.5 MiB JWKS is read, a JWKS over 4 MiB is refused). Each place the limit is passed on was dropped in turn (the transport call, the retry loop, the no-retry call, the redirect hop, the builder, the client) and a test failed each time; so did dropping the option from `rusty-mcp` and doubling its cap.
- **Known limitations:** the 4 MiB figure is a judgement, not a measurement of how fast provider key sets grow (one snapshot only). A fetch of 4 MiB is buffered and parsed in full (the 910 KB document parsed in 15 ms in a release build; the 4 MiB case was not timed). The streaming path is unlimited by this option on purpose. `rusty_request` still ignores proxy environment variables for the JWKS client, unchanged.
