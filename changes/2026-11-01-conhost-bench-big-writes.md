## 2026-11-01 - Own console host takes large writes; throughput bench against ConPTY

- **Fixed:** a single `WriteFile` or `WriteConsole` over 64 KiB, such as one big buffer written at once or Rust's stdout, failed on our console host with "The parameter is incorrect" (os error 87), where ConPTY accepts it. The host now reads such a write 64 KiB at a time, each slice once the last is emitted, so it still holds at most one slice per call. The call stays whole: no other call is taken until it completes, and a character split across slices arrives intact. Other APIs keep the 64 KiB per-packet limit (design §6.1, §7.4). The parity suite's two #1337 gaps (`print-x 7 32768` and `print-x 7 100000`) are closed and taken off its list.
- **Added:** `rusty_conhost`'s `conhost_bench` example, the Phase B throughput gate (design §9.2). It writes each `gen_workloads.py` file to ConPTY and to our host, times spawn to EOF, and fails when our host is more than 10% slower on any workload. On Beast (Windows build 26300, eight 4 MB workloads, 7 runs each), our host took 0.15x ConPTY's time on geomean through WriteConsoleW and 0.18x through raw writes, and 0.79x at worst (cursor_thrash, raw).
- **Known limitations:** under a stateful output code page (UTF-7, ISO-2022, HZ), a raw write or WriteConsoleA over 64 KiB is still refused, since slicing would lose the code page's shift state; WriteConsoleW is not affected. The bench measures throughput only, not that both hosts drew the same screen. Our host runs in the bench's process, while ConPTY runs as a separate process that repaints frames, so the ratio reflects architecture as much as parser speed.
