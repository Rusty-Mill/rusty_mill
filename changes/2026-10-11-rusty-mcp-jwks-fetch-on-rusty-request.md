## 2026-10-11 - rusty-mcp 0.8.0: JWKS fetch on rusty_request (sovereignty list item 3)

- **Changed:** the `jwt` feature fetches the JWKS with `rusty_request` (feature `tokio`) instead of `reqwest`. The request runs on the caller's own `tokio` runtime, so no private runtime or thread is started. Settings carried over from the old client: the request timeout, at most 10 redirects, no cookie jar, no proxy from the environment. No connection pool: fetches are minutes apart, and `rusty_request` does not retry a request that lands on a pooled connection the server has since closed (the old client did), which would also have blocked the next fetch for the refetch interval. `rusty-mcp` no longer depends on `reqwest` outside its tests.
- **Changed (breaking, pre-1.0):** `JwtValidatorError::Http` is removed. `rusty_request::ClientBuilder::build` cannot fail, so nothing produces it any more; `JwtValidatorError` now has only `NoAlgorithms` (still `#[non_exhaustive]`). Version 0.7.0 to 0.8.0. The only in-workspace user wraps the error in a `Box` without matching on variants.
- **Behaviour:** error text for a failed fetch now comes from `rusty_request`, so the wording after `JWKS fetch failed:` differs; the `TokenError::Unavailable` classification and the `JWKS endpoint returned <status>` and `malformed JWKS` messages are unchanged.
- **Compatibility changes to know about:** (1) The JWKS response body is capped at 1 MiB (`rusty_http`'s `DEFAULT_MAX_BODY_LEN`); a larger document is refused as `Unavailable`, where `reqwest` read any size. (2) HTTPS trust is now `rusty_tls`'s system anchors, not `reqwest`'s platform verifier. On Linux that is the system CA store. On macOS only the built-in roots are read: the user's Keychain trust settings are not consulted, so an enterprise CA trusted there will not be trusted for the JWKS fetch, and a built-in root the user has explicitly distrusted is still accepted (documented as a fidelity limit in `platform-bsd`, rustils#88). Other platforms were not checked. (3) Informational (`1xx`) responses before the final one now work; see the `rusty_request` fragment.
- **Verified:** `rusty-mcp` and gateway crate tests, clippy `-D warnings`, `cargo-shear` and the workspace policy scripts (see the PR). The 8 existing validator tests pass unchanged on the new client. Six new tests cover a failing endpoint, a malformed JWKS, a malformed URI, a server that never answers, a server that hangs up its keep-alive connection between fetches, and a `103` ahead of the final `200`; the timeout, failing-endpoint, keep-alive and `103` tests each fail with their code broken (checked).
- **Known limitations:** HTTPS under real `tokio` is covered by `rusty_request`'s own tests, not by a test in this crate (the validator tests use plain `http://` on localhost); custom or distrusted trust anchors are not tested at all. No before/after latency measurement was taken. An invalid `jwks_uri` is still reported on first use as `Unavailable`, not at build time.
