## 2026-10-21 - rusty_tonic: the gRPC server (phase 4b-3)

- **Why:** phase 4b-3 of the first-party `prost`/`tonic` plan, the counterpart of the client (4b-2, #842). The design was approved before any code (closures on a `Router`, `Incoming`/`Sink` instead of `Stream` traits, deadlines by dropping the handler, cancellation surfaced on the next read or write, an interceptor shared with the client, mTLS client identity left out).
- **Added:** `rusty_tonic::server`, behind the `rusty-tokio` feature (a default build is unchanged).
  - `Router::new()` with `unary`, `server_streaming`, `client_streaming` and `bidirectional`, each a closure registered under its `/package.Service/Method` path, and `Router::serve(listener, tls, ServeOptions) -> rusty_hyper::Server`. Handlers take and return the client's `Request<T>` and `Response<T>` (`Request.timeout` is the deadline the client sent). `Incoming<T>::message` reads request messages; `Sink<T>` has `send`, `set_metadata` (initial) and `set_trailers` (sent with an `OK` status).
  - A handler's `Err(status)` is a "trailers-only" response if nothing was sent, otherwise trailers after the replies. An unknown path is `UNIMPLEMENTED`; a call that is not gRPC (wrong method or content type, compressed, bad `grpc-timeout`) is refused with a status by the core's `RequestHead::from_headers`.
  - `grpc-timeout` is enforced: the handler is dropped and the call ends `DEADLINE_EXCEEDED`, after any replies already sent.
  - A client that cancels shows up as `CANCELLED` from the handler's next `Incoming::message` or `Sink::send`. A handler that is only computing is not interrupted until then or its deadline (no "stream reset" future exists in `rusty_h2`; adding one is a separate change).
  - Limits: request messages over `with_max_recv_message_size` (default 4 MiB) are `RESOURCE_EXHAUSTED`; replies over `with_max_send_message_size` (default none) fail the `send`, nothing is sent, and the call goes on. A unary or server-streaming call with no or several request messages, or a message cut short, is `INTERNAL`. `Router::with_interceptor` takes the client's `Interceptor`; its `Err` ends the call before the handler runs.
  - A handler that panics resets its stream, which a client sees as `INTERNAL`; the server goes on.
- **Changed:** `client::Response::new(message)` (a reply with no metadata, for handlers). `rusty_tls` becomes an optional dependency of `rusty_tonic` under `rusty-tokio` (for `TlsAcceptor`).
- **Tests (written first; all 31 failed on `todo!()`, one added after the mutation run):** `tests/server_calls.rs` (20: every shape through this crate's client, handler errors with details and metadata, trailers-only errors, errors after replies, unknown method, the deadline the handler sees, the interceptor, both limits, and a bare HTTP/2 client sending non-gRPC calls, zero/two/cut/compressed messages), `tests/server_lifecycle.rs` (8: deadline before and during a stream, no deadline, cancellation seen on send and on read, shutdown with a call in flight, 64 concurrent calls, a panicking handler) and `tests/server_tonic.rs` (7: a real `tonic` client on tokio — every shape, an error with metadata, an unimplemented method, a deadline that drops the handler, the receive limit). Run 40 at a time in parallel for load, and 11 mutations of the implementation (deadline, unknown-method code, interceptor, extra and cut request messages, both limits, `Closed` as `CANCELLED`, trailers, initial metadata, final status, a stream ending in error): one survived at first (a cut-short request, hidden by the unary "no message" error) and now has its own test.
- **Finding:** `rusty_h2` forgets a reset stream whose request was fully read, so a handler's write then fails `Closed` rather than `Reset(CANCEL)`; the server maps `Closed` on its own writes to `CANCELLED`.
- **Known limitations:** no compression, health checking or reflection; no peer address or client certificate for handlers (`AsyncTlsServerStream` has no `peer_certificate_der`; `rusty_hyper`'s handler has no peer); a handler that is only computing is not interrupted by a cancel.
- **Depends on:** #842 (the client; this branch is stacked on it).
- **Review round (baileyrd, #848):** a streaming handler that called `Sink::set_metadata` and then ended without sending a message (`Ok` or an error) lost that metadata, because the trailers-only response never included it. It is now in the first header block, ahead of the status and its own metadata. Three tests (empty success, an error before the first message, and the existing path with a message, where it must stay out of the trailers); the first two failed before the fix and fail again with the fix removed.
- **Review round (baileyrd, #842 finding carried here):** after `Sender::finish()` the request was half-closed and the `Sender` was gone, so the call's reply could no longer reset the stream: dropping the `Reply` or hitting its deadline sent no `CANCEL`, and a stalled response held a concurrent-stream slot indefinitely. `finish` now leaves its stream with the call (`Handoff`), so the reply side can reset it, and a cancellation that lands just before the handoff is honoured by `finish` itself. Four client tests (a reply dropped after `finish`, a deadline after `finish`, a reply dropped before `finish`, and a second call being admitted under `max_concurrent_streams(1)` once the first is given up on); they failed before the fix, and each of the three new branches fails its test when removed. `tests/client_lifecycle.rs` now has 18 tests; one older test got a longer deadline after failing twice in 60 parallel runs.
- **Review round 2 (baileyrd):** `Streaming::open` took the response future out of the call before awaiting the headers, so a caller that gave up on the wait from outside (an external `timeout`, or an abort) left a call `Drop` believed was over, and a stalled peer kept the stream slot. The future is now awaited in place, so `Drop` still cancels. Two tests (a client-streaming `response()` and a unary call timed out externally while the peer sends no headers: the server sees the reset and a second call is admitted under `max_concurrent_streams(1)`); both failed before the fix. `tests/client_lifecycle.rs` now has 20 tests.
