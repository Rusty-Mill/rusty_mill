## 2026-10-10 - rusty_bbp_host: prompt and runbook corrections from the first proving run

- **Changed:** the `post` tool description spells out the verdict item schema (`{id, ref, issue, fix}`, all strings; the Tester spent five to seven posts per turn discovering it), that op ids are unique per role across the whole task (three `OpConflict` refusals from fresh harnesses reusing an earlier turn's id), and that a run failing for a reason no code change can fix calls for a non-gate `request_decision`, not revise/resubmit (the iteration budget went on five identical candidates). The proving launchers prefix op ids with `t{turn}-`, read the messages before deciding, and treat a human answer or decision after the failure as "resolved, proceed" and its absence as "unresolved, request".
- **Changed (runbook):** Linux/WSL only; a `claude -p` login smoke test before the run; the moderator keeps polling at `escalated` until `resume` or `cancel`; `LSP` under `--tools ""` on Claude Code 2.1.296 is expected. New "Recovering from an environment fault": fix the environment, `rerun` the current candidate with the card's revision while the request is pending, wait for the fresh terminal report, then settle the request; when the fix needs a profile change the frozen digest forbids it, so the task is cancelled and reopened. Settlement only regrants the requester, so answering first would hand the Tester the same failed report.
- **Added:** `runner_e2e::an_environment_fault_is_recovered_by_rerun_then_settlement`: failed run, Tester request (no iteration spent, no turn), stale `--rev` refused, rerun, fresh passed report with nobody granted while the request is pending, settlement regrants the Tester, approve moves to `review`.
- **Known limitation:** prompts are text; whether the roles take the route is the next run's data.
