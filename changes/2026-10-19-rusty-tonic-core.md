## 2026-10-19 - rusty_tonic core: gRPC without I/O

- **Why:** phase 3 of the first-party `prost`/`tonic` plan (board cards t43-t46). The wire (`rusty_protobuf`) and message (`rusty_prost`) layers exist; this is the protocol layer both `rusty_a2a`'s gRPC binding and the gateway's `ext_mcp` client use `tonic` for. Design approved before any code (decisions 1-6, card t44). Scope is data and state machines only; `Service`, streaming, `Codec` and interceptors belong to the transport phase, where the async runtime is chosen.
- **Added:** `crates/libs/protocol/rusty_tonic`, Tier S (dependencies are `rusty_prost`, `rusty_base64`, `rusty_percent`; `tonic` is a dev-dependency oracle).
  - `Status` / `Code`: 17 codes, constructors, `with_error_info` / `error_info`, `to_trailers` / `from_headers` (`grpc-status`, percent-encoded `grpc-message`, validated non-OK `grpc-status-details-bin`).
  - `MetadataMap`: validated keys and values, `-bin` base64, reserved names refused, received headers that cannot be metadata skipped and counted.
  - `FrameDecoder` / `encode_frame` / `encode_message` / `decode_message`: any chunking, 4 MiB default receive limit checked while ingesting the prefix before a rejected body is copied, checked frame-length arithmetic, persistent errors, linear-time and bounded-memory buffering.
  - `parse_timeout` / `format_timeout`; `RequestHead` / `ResponseHead` / `ResponseStart`; `split_path`; `code_from_http_status`.
- **Tests:** 85, including 74 written first that failed on `todo!()` before the implementation. `tonic` 0.14 as an oracle in both directions on 4,000 random statuses with and without `ErrorInfo` details; the spec's examples; chunking invariance, corruption and random-byte sweeps on every parser; joined binary metadata, rich-status consistency, rejected same-push bodies, checked 32-bit frame lengths, and a stream with a partial frame always pending. 16 mutations (limit, compaction, compression flag, error finality, `%` escaping, details handling, code parsing, padding, reserved names, rounding, digit count, content-type and encoding checks) each fail a test.
- **Found while testing:** `tonic::Status::from_header_map` panics on a malformed `grpc-status-details-bin` (`.expect("Invalid status header, expected base64 encoded value")`), so a single bad header from a peer can crash a `tonic` client or server. This crate drops a malformed value instead; it is one reason to finish the migration (t46).
- **Known limitations:** no compression (a compressed message is `UNIMPLEMENTED`), no async, no HTTP/2, no services or streaming (phase 4). Framing is checked against the spec's grammar, not an independent recording, until live interop with `tonic` exists in phase 4. A malformed details header is dropped silently, as decided. The library builds on its declared `rust-version` 1.75 (checked with rustc 1.75.0 on the whole dependency chain); the tests need 1.85, the floor of the `tonic` oracle.
