## 2026-10-11 - rusty-mcp 0.9.0: JWT verification on rusty_oauth (sovereignty list item 4)

- **Changed:** the `jwt` feature verifies signatures and claims with `rusty_oauth` (`decode_unverified`, `rsa::verify_rs256`, `es256::verify_es256`, `JwkSet`, `validate_claims`) instead of `jsonwebtoken`. `jsonwebtoken` is no longer a dependency of `rusty-mcp` outside its tests (it signs the RS256 test tokens, since `rusty_oauth` only verifies RSA). `agentgateway-auth` keeps its own copy for `file_jwks`.
- **Changed (breaking, pre-1.0):** `JwtValidatorBuilder::with_algorithms` takes the new `auth::JwtAlgorithm` (`Rs256`, `Es256`, `#[non_exhaustive]`) instead of `jsonwebtoken::Algorithm`. There is no variant for `none` or any HMAC algorithm, so they cannot be configured. Version 0.8.0 to 0.9.0. Defaults are unchanged (RS256 and ES256).
- **Security behaviour kept:** the token's `alg` is checked against the allow-list before any key is looked up; a `kid` is required; the key must be of the family the algorithm needs; `iss`, `exp` and `nbf` are checked with leeway; `aud` is still left to the layer.
- **Stricter than `jsonwebtoken`, deliberately:** RSA moduli must be 2048 to 4096 bits (only the upper bound was enforced before; the bound matters because the key comes from a network document and `rusty_oauth` puts no limit on it); RSA exponents must be odd and at least 3 (the 33-bit upper bound was already enforced); two JWKS keys sharing a `kid` match nothing (the first used to win); base64 must be canonical; a token with `exp` equal to `now - leeway` is expired (`jsonwebtoken` accepted it; one second stricter); leeway is clamped to `i32::MAX` seconds so it cannot overflow the claim arithmetic.
- **Messages:** rejection reasons are fixed strings of ours, not the verifier's, so a token cannot put its own text into the `WWW-Authenticate` header; the offending `alg` is shown truncated to 16 characters.
- **Verified:** `rusty-mcp` and gateway crate tests, clippy `-D warnings`, `cargo-shear` and the workspace policy scripts (see the PR). The 12 existing validator tests pass unchanged. Added 15 unit tests (key bounds, claim classification, allow-list, leeway) and 14 end-to-end tests with real tokens: ES256 acceptance, an HS256 token keyed with the RSA public key, an RS256 token relabelled ES256, tampered payload, garbled and truncated signatures, not-yet-valid, expired inside leeway, no `exp`, malformed and deeply nested tokens, missing `alg` and `kid`, duplicate `kid`, oversized and undersized RSA keys. Eight protections were broken one at a time (allow-list, key family, size bound, claim classification, issuer, leeway clamp, exponent parity, signature verification) and each was caught.
- **Known limitations:** the ES256 path has one positive end-to-end test and uses `rusty_oauth`'s own signer; cross-checking against a second implementation's ES256 tokens was not done (RS256 is cross-checked against `jsonwebtoken`-signed tokens). No timing or throughput comparison with `jsonwebtoken` was taken. `rusty_oauth`'s RSA verification has no key-size bounds of its own; they are enforced here. Rejection reasons are matched on `rusty_oauth`'s claim-error wording, pinned by tests, so rewording it there fails them loudly.
