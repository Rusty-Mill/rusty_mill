## 2026-10-11 - rusty-mcp 0.9.0: JWT verification on rusty_oauth (sovereignty list item 4)

- **Changed:** the `jwt` feature verifies signatures with `rusty_oauth` (`decode_unverified`, `rsa::verify_rs256`, `es256::verify_es256`, `JwkSet`) and checks claims in the MCP adapter instead of `jsonwebtoken`. `jsonwebtoken` is no longer a dependency of `rusty-mcp` outside its tests (it signs the RS256 test tokens, since `rusty_oauth` only verifies RSA). `agentgateway-auth` keeps its own copy for `file_jwks`.
- **Changed (breaking, pre-1.0):** `JwtValidatorBuilder::with_algorithms` takes the new `auth::JwtAlgorithm` (`Rs256`, `Es256`, `#[non_exhaustive]`) instead of `jsonwebtoken::Algorithm`. There is no variant for `none` or any HMAC algorithm, so they cannot be configured. Version 0.8.0 to 0.9.0. Defaults are unchanged (RS256 and ES256).
- **Security behaviour kept:** the token's `alg` is checked against the allow-list before any key is looked up; a `kid` is required; the key must be of the family the algorithm needs; `iss`, `exp` and `nbf` are checked with leeway; `aud` is still left to the layer.
- **Stricter than `jsonwebtoken`, deliberately:** RSA moduli must be 2048 to 4096 bits (only the upper bound was enforced before; the bound matters because the key comes from a network document and `rusty_oauth` puts no limit on it); two JWKS keys sharing a `kid` match nothing (the first used to win); base64 must be canonical; leeway is clamped to `i32::MAX` seconds; timestamp arithmetic widens to `u128` before addition.
- **Messages:** rejection reasons are fixed strings of ours, not the verifier's, so a token cannot put its own text into the `WWW-Authenticate` header; the offending `alg` is shown truncated to 16 characters.
- **Original implementation evidence (before review corrections):** `rusty-mcp` and gateway crate tests, clippy `-D warnings`, `cargo-shear` and the workspace policy scripts (see the PR). The 12 existing validator tests pass unchanged. Added 15 unit tests (key bounds, claim classification, allow-list, leeway) and 14 end-to-end tests with real tokens: ES256 acceptance, an HS256 token keyed with the RSA public key, an RS256 token relabelled ES256, tampered payload, garbled and truncated signatures, not-yet-valid, expired inside leeway, no `exp`, malformed and deeply nested tokens, missing `alg` and `kid`, duplicate `kid`, oversized and undersized RSA keys. Eight protections were broken one at a time (allow-list, key family, size bound, claim classification, issuer, leeway clamp, exponent parity, signature verification) and each was caught.
- **Review corrections:** restored the former backend's odd RSA modulus requirement (including bounded powers of two) and canonical 32-byte P-256 coordinate width; retained the existing odd exponent requirement in 3..=2^33-1. NumericDate uses the former jsonwebtoken 11 contract: exact unsigned integers through u64::MAX and finite nonnegative floats below 2^64 rounded to seconds. Present malformed time claims fail closed; absent `nbf` remains optional. Expiry at exactly `now - leeway` retains the former acceptance. Added signed-token regressions, deterministic time boundaries, zero-prefixed coordinate tests, and an independent OpenSSL ES256 token with malformed scalar/key cases. Claim errors now originate locally and do not depend on OAuth error wording.
- **Primitive provenance:** RSA uses `rusty_rsa::BigUint`; ES256 uses `rusty_oauth::crypto::ecc` with that bigint. SHA-256 is re-exported from `rusty_rsa`. These paths do not use `rusty_pk`/`rusty_sha2`, and their validation evidence cannot be substituted.
- **Known limitations:** no timing or throughput comparison with `jsonwebtoken`. RSA bounds and canonical JWK coordinate width are enforced in the MCP adapter; the lower-level OAuth constructors are unchanged. Review-correction validation is recorded separately from the original implementation evidence.
