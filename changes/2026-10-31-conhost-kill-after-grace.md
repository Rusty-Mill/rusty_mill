## 2026-10-31 - Own console host ends programs that outlive the close grace

- **Fixed:** when an own-console session closes, every client still attached at the 2 s grace deadline is now terminated 5 s after CTRL_CLOSE, Windows' own bound on a CTRL_CLOSE handler, with `STATUS_CONTROL_C_EXIT`, the code CTRL_CLOSE ends it with. The console itself still closes at 2 s. Before, a program that ignored the closed console's errors kept running, and grandchildren were never killed. The host opens each client at its CONNECT, through the thread the CONNECT came from, which must belong to the client's pid, and lets go at its DISCONNECT; a client it can't verify is never ended. rusty_term waits for that kill, up to 6 s and only while a program is still attached, on a background thread that it joins before exiting, so closing a pane or window doesn't freeze the others. Clients that exit during the grace are untouched.
- **Added:** `platform_windows::condrv::ClientProcess` (`open`, `terminate`) and `rusty_conhost::OwnPtyMaster::wait_shut_down`, public API additions under design §11.2. **Changed:** `rusty_term::backend::OwnBackend` is no longer a unit struct; build it with `OwnBackend::new()` and drop it last. No new dependency or feature; `OpenThread` and `GetProcessIdOfThread` are a new Win32 admission (design D2).
- **Known limitations:** a client killed from outside before the host opens it frees its pid and thread id; only a new process that took both could be ended in its place. A client the host can't open, such as a protected process, still only gets CTRL_CLOSE, and is logged. After a host panic or engine error the console closes without ending clients, though rusty_term still kills its own shell, and if the host process itself is killed nothing ends them.
