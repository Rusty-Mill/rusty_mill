## 2026-10-13 - Mill Board: kanban MCP server and web UI

- **Added:** `crates/apps/rusty_mill_board`. Cards move through backlog, ready, building, qa, review, done and blocked; each move needs a capability and leaving a worked column needs the claim. Ten MCP tools and `POST /api/<op>` come from one operation table. The UI is a single page with drag-and-drop that follows the event log by polling. Durable storage is `rusty_multimodal_db_engine` (`replace_if` gives atomic claims); `--store` omitted means in memory. `--github-repo owner/name` runs a background reconcile with GitHub issues: the board owns the column (a `board:<column>` label, Done closes the issue), title and body are last-write-wins, unlinked open issues are imported as Backlog cards, and an issue closed on GitHub while its card is not Done is logged as drift.
- **Runner:** `crates/apps/rusty_mill_board/runner` (`mill-runner`), optional and separate: a JSON stage table maps columns to commands run without a shell, in a per-card git worktree under `rusty_sandbox` (write access to the worktree and scratch only, internet only when a stage asks); the runner commits afterwards and never gets `.git` writable. It acts through board roles, so it cannot triage or merge; startup checks each stage's role against the transition table. The board gains a Triage override on claims so a person can take a card back, a public `required_capability`, and a shared blocking HTTP helper (GitHub sync uses it too). ADR-0002.
- **Design:** `crates/apps/rusty_mill_board/docs/adr/0001-bbp-conductor.md` (Proposed): a separate conductor process hosts each Ready card as one BBP task through the `bbp` CLI, maps BBP states to columns, and carries the human gates as generic asks answered from the board. Paused while BBP is revised; nothing of it is built.
- **Tests:** 22 unit tests (domain rules, operation table, the sync policy against a fake forge, repo and timestamp parsing), a scenario run against both stores including reopen, three socket-level tests of the HTTP guard, status mapping, UI and MCP, and four of the GitHub adapter against a recording mock (exact requests, pagination, PR filtering, error mapping). Run by hand: restart persistence; drag-and-drop plus live sync across two headless-Chromium pages; the binary syncing against a stateful fake of the GitHub issues API (create, relabel on move, link persisted).
- **Runner limitations:** Linux only (Landlock). A command is not killed when a person moves its card, only noticed when it ends (bounded by `wall_secs`). Worktrees are not cleaned up after merge. A card body becomes a prompt and can come from an imported GitHub issue: moving to Ready is the human check, the sandbox bounds the damage. Tested with shell commands and a real sandbox. `claude -p` was tried through it: the Bun-based binary needs `/proc` and `/dev/urandom` readable, runs, and then needs credentials; in the build environment it logs in from the session's own token files, which the sandbox rightly withholds, so no agent run completed. `HOME` now defaults to the scratch directory.
- **Known limitations:** roles are trusted as claimed (the bearer token authenticates, not the role). The card write and its event are two engine writes, not one transaction. `events_since` scans the event rows, which is fine for a board and not for a long log. The UI polls every 1.5 s rather than streaming. The sync was never run against a real repo: the build environment's token was rejected (`401 Bad credentials`), though a read-only live test (`tests/github_live.rs`, ignored by default) shows TLS, the proxy path and error mapping work against api.github.com. Writes were only exercised against a fake and a recording mock; labels are created by GitHub on first use and need push access. It polls (no webhooks), mirrors issues only (not PRs), and uses one connection per request because pooled connections go stale between runs. The autonomous runner is not built; it is meant to be a client of the tools (through BBP). No real MCP client was run against it; only raw JSON-RPC over HTTP.
