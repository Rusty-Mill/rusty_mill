## 2026-10-11 - rusty_bullet: a simulated RLBot core and the game-facing bridge

- **Added:** `rb_rlbot_core`, an RLBot v5 core that plays on `rb_env` instead of Rocket League. Bots connect on 23234 with the existing `rb_rlbot_client` and get the real handshake, packets, input routing by agent id, state setting and stop. `Pacing::Lockstep` waits for every bot to answer each packet, so the same bots give the same match every time (tested by comparing two full runs). A `rb_rlbot_core` binary builds a match from `AGENT_ID:TEAM` arguments.
- **Added:** `rb_rl_game_bridge`: the launch arguments (`-rlbot RLBot_ControllerURL=127.0.0.1:<port> RLBot_PacketSendRate=240 -nomovie`), game-port discovery, a process probe, the listener the game dials, and RLBotCS `BridgeHandler`'s time-advance and packet-distribution rules, behind a `GameLink` trait with `SimGameLink` as its implementation.
- **Added:** `rusty_bullet/docs/research/RLBOT-BRIDGE-DLL.md`, how `Bridge.dll` sits between RLBot and the game, with RLBotCS file and line citations.
- **Changed:** `rb_rlbot_bridge` exports the inverse conversions `controller_input` and `physics` (additive).
- **Fixed (found by a test):** probing a port with a wildcard bind misses a socket on `127.0.0.1` on Windows; `tcp_port_is_free` tries both.
- **Verified:** 8 + 5 tests in `rb_rlbot_core`, 40 in `rb_rl_game_bridge`, clippy `-D warnings`, rustfmt; the built `rb_chaser_bot` joined the built `rb_rlbot_core` and the match started.
- **Added (ADR-0083, owner-approved):** the real game socket. The format was read from `Bridge.dll` (length-prefixed FlatBuffers) with a decompiler run outside the repo; `RL-GAME-SOCKET-FORMAT.md` records it as a table, `game_wire` implements it, `RocketLeagueLink` is a `GameLink` over any stream, and `rb_rl_game_probe` listens like RLBot and records live traffic. Checked both ways against buffers built by the DLL's own generated code; nothing decompiled is committed (only two byte fixtures).
- **Added:** bots in the real game. `rb_rlbot_core::Core` is generic over a new `MatchBackend` trait (`Simulation` implements it; the pre-existing API is unchanged), and `rb_rl_game_bridge::LinkBackend` implements it for a game. A self-paced backend is polled from the start and a bot's opening reply waits for the game's map, which an end-to-end test (a stand-in game, `Core`, a real client) found missing. `rb_rl_bridge` is the binary. Also found and fixed there: on shutdown `Core` dropped sockets with unread input, and Windows's resulting reset discarded the disconnect signal (7 of 15 runs lost it before; 0 of 15 after); it now shuts down the write side and drains.
- **Added:** `SpawnBot`. The codec encodes it with a full loadout (checked against the DLL's generated code like the other commands), `GameFolder` ties each spawned car to the player index it was spawned for by the command's id (so the game may answer in any order, and indices are stable when a car leaves), and `LinkBackend::with_spawning` sends one per configured bot two messages after the map loads and holds the match start until every car exists. `rb_rl_bridge` spawns by default; `--no-spawn` expects existing cars. A refused spawn (per-frame byte budget) leaves no promise behind.
- **Author-reported live run (Epic install, Freeplay, 2026-10-11):** the codec decoded 14,993 and 2,524 messages from a real game with none failing; the game accepted the bridge's `SpawnBot`, answered with a `PlayerSpawn` carrying its command id, and took `PlayerInput` for the new car, which `rb_chaser_bot` drove. The committed slices contain 250/51 messages and 513/115 physics frames, not the full sessions; exact capture-build provenance is unavailable (`tests/live_capture.rs`, the player name replaced by a placeholder); a test pins that the encoder still produces the accepted `SpawnBot` byte for byte, and that the real 34 pads are the simulation's table.
- **Fixed (found live):** an untimed match's scoreboard clock counts up, so `LinkBackend` now takes "untimed" from the configuration and reports an increasing clock; the readiness check no longer counts a human's car as a spawned bot; a human already in the game moves to the next index instead of vanishing when a bot is spawned for its index; the simulated `FieldInfo` goals are the size the game announces (1920 by 752 at z 312).
- **Added:** `rb_rl_game_probe --analyze` and `--commands`, and `rb_rl_bridge --record-in` / `--record-out`, to inspect real traffic.
- **Fixed (review of the whole diff, two reviewers, findings checked against the code before acting):** a stop (or last input) sent just before a client closed was dropped with the client, as was a stop followed by a bad message in the same read; a connection that reset before it was accepted could end the run; one client could flood the loop (reads are now capped per pass); `InitComplete` before the handshake was accepted; input sent before the match began answered its first lockstep packet; configured agent ids with spaces could never match and blank ones hung the start; NaN or infinite numbers from a bot reached the physics; a partial write on the non-blocking game socket could desynchronise the game's framing (unsent bytes now wait in an outbox); one unknown enum or missing field ended the session (now `Other`); a crafted message could force a large allocation (events and name bytes are capped); humans were reported as bots; a failing recorder could corrupt the stream; stale docs. Each has a regression test; the partial-write one was mutation-checked.
- **Known limitations:** only Freeplay on an Epic install has been tried; a timed match, several bots and Steam have not. Spawned bots get a standard Octane loadout in plain colours (unverified in the game); RLBot's colour swatches and configured loadouts are not modelled. Rendering and the stat events are not implemented. The simulated core does not model ball prediction, comms, rendering, loadouts or mutators other than match length.

- **Fixed (PR #623 follow-up):** stable packet slots and configured identities across demolition/removal; elapsed pad, replay and count-up clocks; atomic nonfinite state rejection and shared controller sanitization; readiness tied to the distributed actor mapping; truncated EOF and permanent oversize errors; actor-lifetime probe summaries, strict supported-event diagnostics, and exclusive recording files. All regressions use synthetic streams or existing captures; no new live-game evidence is claimed.
