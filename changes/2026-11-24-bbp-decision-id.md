## 2026-11-24 - BBP decision ids settle uncertain inbox sends (#703)

- **Added:** `bbp human --decision ID` (1 to 64 of `[A-Za-z0-9._-]`, exclusive with `--op`) writes the op as `by:<as>/dec:ID`, so a repeat of the same send replays by R15 and the same id with another payload is `op_conflict`. `--decision` needs `--fence` (an unfenced send's absence from the log would never be final). Required `--fence` is stricter than the CLI shape Nano approved (`bbp human --decision`). `bbp decision --dir D --task T --decision ID[,ID2]` counts only the task's human principal (an agent's own op strings never count) and prints `[{"decision","applied","rev"}]` from the log; `rev` is the task revision just after the `op_accepted` that carries the id.
- **Added:** Mill Board sends a decision that drops acted-on work under its Remediate card's id (command `n` as `<id>.<n>`). The card is filed at a new derived id that says its send carries an id. A retry, a stale-rev retry, or a send refused with `StaleRev` now reads the lookup: applied keeps the card (with the rev noted), not applied closes it. The board refuses a drop that is not one command before filing a card, writes a pending mark on the card before each send that carries its id, clears it only when BBP's answer accounts for that send (the id is in the log, or the send was refused before writing anything), and closes a card as not applied only when no mark is left open (a lost answer, a crash or an unreachable host leave the card as it is). It also checks after a committed send that the id reached the log (else it files the old-id card too), and treats an escalation as gone only when BBP itself no longer lists it. A card is also filed at the old id when the host cannot record ids (it predates `bbp decision`, probed before the send), and the lookup must answer for exactly the id asked or it is an error. If both a tracked and an old-id card exist for one decision (two retries whose probes differed), the old-id card decides and nothing is settled. A card filed at the old id (before this change, or on such a host) was sent without an id, so absence from the log proves nothing: it is never closed automatically, and a retry of it is sent as before. Any other refusal, or a host without `bbp decision`, keeps the old note to check BBP's log.
- **Changed:** `Escalations::act` takes the optional decision id and the trait gains `applied`; `inbox_act`'s `recorded` answer carries `settled` (`applied`, `not_applied` or `unknown`).
- **Known limitations:** no new event variant and no schema change: the log already records every accepted human op, so old logs read as "not applied" and replay is unchanged.
