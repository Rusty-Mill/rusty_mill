## 2026-11-04 - rusty_mux sessions survive a server restart (C45)

- **Added:** `rusty-mux-server` saves its sessions, windows, layouts and block names as `rusty_multimodal_db_engine` records, and each block's screen and scrollback as an RTCP file beside them. It saves every 5 s when something changed, and in full on a clean stop. The store is `--state DIR`, by default `$XDG_STATE_HOME/rusty_mux/<socket name>` or `%LOCALAPPDATA%\rusty_mux\<socket name>`. It is owner-only and locked to one server, and `--no-state` turns it off. On Windows every file in it is made owner-only, existing ones included, and a junction or link given as the directory is refused. The next server on that directory restores everything with the same ids. A shell block gets a fresh shell in its last working directory, below its saved screen and a one-line "restored" marker. The marker goes below the last row, and a saved alternate screen is copied onto the main screen first, so no saved text is lost. A block started with its own command comes back read-only, showing its saved screen until closed.
- **Added:** `rusty_mux_core::Mux::save` and `Mux::restore` (`Saved`, `SavedSession`, `SavedWindow`, `SavedBlock`, `RestoreError`), `Config::state_dir` in `rusty_mux_server`, and `platform_windows::fs::restrict_dir_to_owner`, which are public API changes.
- **Known limitations:** programs that were running are not restarted. Screen text is stored unencrypted until encryption at rest lands. On Linux the server has no clean stop yet, so a signal or crash can lose up to the last 5 s. A store that cannot be read is moved aside to `<dir>.bad-<seconds>`, and the server starts empty.
