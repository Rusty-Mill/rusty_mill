## 2026-10-24 - rusty_a2a: the gRPC client on rusty_tonic (stage B, PR1)

- **Why:** stage B of the `prost`/`tonic` replacement, client half (design check approved). It is not about dependency count (the server still uses `tonic` until PR2, and `tonic` itself leaves the graph only with the gateway's transport stage). It fixes two faults of the `tonic` client, found while reading its source: it was built with no TLS feature, so an `https://` agent URL (the crate's own doc example) was dialled as plain TCP and spoke cleartext HTTP/2 to a TLS port; and `tonic-0.14.6` `Status::from_header_map` (`status.rs:478`) unwraps the base64 of `grpc-status-details-bin`, reachable from `client/grpc.rs:339`, so a remote agent could panic a client's call with one malformed header.
- **Changed (`GrpcClient`):** the eleven RPCs go through `rusty_tonic::client::Channel`. The public methods keep their names and signatures. `https://` is verified against the OS trust anchors unless told otherwise. A malformed details header leaves the status's code and message, so `NOT_FOUND` still reads as `TaskNotFound`.
- **Added:** `GrpcClient::with_channel_options(endpoint, ChannelOptions)` (trust policy, client identity, per-call deadline, message limits) and the `client::grpc::EventStream` alias for the stream type the streaming methods already returned.
- **Changed (breaking, internal):** `ClientError::Grpc` holds a `rusty_tonic::Status` (was `tonic::Status`). Nothing in the workspace enables the `grpc` feature outside this crate.
- **Bridge (`src/grpc_bridge.rs`, private):** `rusty_tonic` runs on `rusty_tokio`; callers, the engine, `axum` and `reqwest` run on `tokio`. They meet only by message passing: a transport task on a process-wide two-thread `rusty_tokio` runtime is awaited from `tokio` through its `JoinHandle`, and a stream crosses a bounded `tokio::sync::mpsc` channel (16 replies read ahead, then HTTP/2 flow control pushes back). Neither side enters the other's runtime context. Dropping the awaited future or the stream aborts the transport task, which drops the call and resets its HTTP/2 stream. A design-check spike showed this working in both directions with `tokio::spawn` and `tokio::time` inside the application. The module goes when the crate leaves `tokio`.
- **Tests (written first; they failed to compile before the change):** `tests/grpc_client_transport.rs` (12) against servers built from `rusty_tonic`: `https://` with a pinned CA, an untrusted certificate refused, a malformed details header, a stream refused at the start keeps its status, an `ErrorInfo` reason picks the error over the bare code, a failing stream ends with one error, a dropped stream and a dropped call each free their `max_concurrent_streams(1)` slot (the stream case against a server that has gone quiet, so only the drop can end it), 300 events to a slow consumer in order, 40 concurrent calls from a one-thread `tokio` runtime, and an unreachable agent being `UNAVAILABLE`. The ten `tests/grpc_client.rs` tests, which drive `GrpcClient` against a real `tonic` server, pass unchanged: that is the interop oracle in this direction. 6 mutations (the abort on drop, the stop after an error, an open failure's status, the `ErrorInfo` reason, the version header, the `NOT_FOUND` mapping): all killed; two survived the first tests and each got one.
- **Known limitations:** `rusty_a2a`'s `server::push::tests::pinned_client_connects_to_the_validated_address_not_a_fresh_dns_lookup` needs DNS and fails in the sandbox, as on `main`. `grpc_convert` still reports conversion failures as `tonic::Status` and the client re-labels them (`bad_reply`); that goes with the server move in PR2. The `rusty_tokio` runtime is process-wide and not configurable yet.
