## 2026-10-10 - AES-GCM constant-time evidence (step 4) and a timing-collector fix

- **Added (rusty_aead, evidence):** `examples/taint_aes.rs` modes `gcm128-seal`, `gcm256-seal` (0 reports wanted), `gcm128-open` (exactly one, in `Gcm::open`: the public tag verdict) and `control-table` (a secret-indexed table lookup, which must be reported); `scripts/disasm_limits_aes.txt`, exact jump-count pins for `sbox`, `shift_rows`, `mix_columns`, `to_planes`, `from_planes`, `sub_word`, `bmul64`, `clmul64`, `gf_mul` (all 0) and `Aes::{encrypt_blocks, expand}` (4 and 17, each jump read and found to compare a public counter or index); eight timing tests (AES-128 and AES-256 key classes, plaintext classes, tag-mismatch position, and an A/A control for each workload), added to `collect.sh`. The existing `crypto-constant-time` CI job runs the taint modes and the pins through `rusty_aead/scripts/ct_check.sh` (CI does not run the timing series; those tests are ignored and run only through `collect.sh`). The building blocks are `#[inline(never)]` so a changed inlining decision cannot move a pin, and the key schedule counts its word index instead of dividing.
- **Verified (run):** planting a real branch on secret data in `mix_columns` makes the taint run report it and the jump pin fail; planting a secret-indexed table lookup in the key schedule makes the taint run report it (the jump pin correctly does not see it: it counts jumps, not memory accesses). My first two attempts at these mutations had no effect on the output, the compiler removed them, and passed undetected; they were redone with effects the compiler cannot remove.
- **Fixed (evidence tooling):** `timing_series.py` selected tests by libtest's substring filter, so a spec could run several tests at once and record whichever printed first. Exactly one earlier spec was affected, the "A/A X25519 (baseline)" row of the two 2026-10-09 ECDH evidence records; see `docs/research/crypto-evidence/ERRATUM-2026-10-10-timing-test-filter.txt`. Verdicts there are unchanged; that row cannot be attributed to X25519. The collector now passes `--exact`, with a regression test that fails without it.
- **Evidence records:** two full `collect.sh` records were taken and both FAILED, kept as produced: run 1 on `clippy rusty_aead` (three `needless_range_loop` lints in test code, fixed; an earlier local check had missed them because it grepped coloured output), run 2 on ECDH P-256 sparse-vs-dense (2 alarms of 40, allowance 1), a watch item from #576 in code this change does not touch. All five AES timing rows were within their allowance. A diagnostic found no growth of |t| with sample count (0.77, 0.38, 0.41, 0.63 from 4,000 to 256,000 samples). No threshold or allowance was changed and no third record was taken to obtain a pass. Details in `docs/research/AES-GCM-DESIGN.md` section 9.
- **Known limitations:** x86-64, one machine, rustc 1.98.1; evidence, not proof. The jump pins count conditional jumps and divisions only; memory-access dependence is covered by the taint run alone, which is one build and one run per mode. `ghash::ghash`, `Gcm::{ctr, seal, open}` branch on the public message length and are not pinned. The GHASH design assumes data-independent 64-bit multiply. Nothing is independently reviewed.
