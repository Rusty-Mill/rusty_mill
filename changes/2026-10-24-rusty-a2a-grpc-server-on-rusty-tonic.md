## 2026-10-24 - rusty_a2a: the gRPC server on rusty_tonic (stage B, PR2)

- **Why:** stage B of the `prost`/`tonic` replacement, server half (design check approved; PR0 is #1009, PR1 is #1014). With it `rusty_a2a` has no normal dependency on `tonic`: its only edge to `tonic` is now a dev-dependency, the independent oracle. The crates that still use `tonic` are `agentgateway-mcp` (its transport stage) and `rusty_tonic`'s optional `tonic-codec` feature.
- **Changed (server):** the eleven RPCs are routes of a `rusty_tonic::server::Router`; the nine unary calls and two streaming ones keep their bodies, now over `rusty_tonic`'s `Request`, `Response` and `Status`. `grpc_convert` reports `rusty_tonic::Status` (the `ErrorInfo` detail comes from `Status::with_error_info`, and the local copies of that and `error_info` go). Credentials, the protocol version and required extensions are read from the request's metadata as before.
- **Bridge (`grpc_bridge::server`):** handlers run on the transport's `rusty_tokio` runtime and the engine on the application's `tokio`. A handler hands its engine call to `tokio` (`on_app`) and any stream the engine returns to `feed`; both are awaited from the transport side and abort their `tokio` task when dropped, and a stream that stops early is an error, not an end: when the feed channel closes `feed` awaits the producer, so one cancelled by its runtime shutting down is `UNAVAILABLE` and one that panicked is `INTERNAL`, after the items already buffered, so an engine call stops waiting when its client leaves (this relies on PR0, which drops the handler on a cancel). `serve_grpc` gives the server a runtime of its own and stops both, on a thread of its own, when dropped.
- **Changed (breaking, internal):** `AgentServices::grpc_service()` is `grpc_router(app: tokio::runtime::Handle) -> rusty_tonic::server::Router`. `serve_grpc` returns `io::Result<()>` (was `tonic::transport::Error`), must be awaited from `tokio`, and returns only if the address cannot be bound. The `A2aService` trait, `A2aServiceServer` and the `tonic`-shaped `A2aServiceClient` are removed from `pb`; they live on as the test-only oracle (`tests/common/tonic_oracle.rs`). `pb::path` holds the eleven RPC paths, shared by client and server. Nothing else in the workspace enables the `grpc` feature.
- **Behaviour changes, toward the gRPC spec:**
  - An over-size request (over 4 MiB) is `RESOURCE_EXHAUSTED`; the `tonic` server answered `OUT_OF_RANGE` (observed).
  - A call past its `grpc-timeout` ends `DEADLINE_EXCEEDED`; `tonic` maps its timeout to `CANCELLED` (`tonic-0.14.6` `status.rs:644`).
  - A handler is dropped when its client cancels (PR0), where `tonic` also dropped it: no change for callers.
- **Tests (the oracle was moved first and the five existing server-side test files passed through it unchanged against the old server, which shows it faithful):**
  - `tests/common/tonic_oracle.rs`: the `tonic`-shaped client and server, with default "unimplemented" methods so an oracle server needs only the RPCs it uses.
  - `tests/grpc_client_tonic_oracle.rs` (4): `GrpcClient` against a real `tonic` server speaking the A2A messages (a reply, error details choosing the error, a stream, an unimplemented RPC): the client's independent oracle, which PR1 had from the old server.
  - `tests/grpc_server_transport.rs` (6): deadline (read from a bare HTTP/2 client's trailers, because a `tonic` client also enforces `grpc-timeout` itself and answers first), size limit, a stream cut short by the application runtime stopping while the transport stays up ends `UNAVAILABLE`, never `OK` (found in review), a client that gives up leaves the server serving, a taken address fails, dropping `serve_grpc` frees the port (this found that stopping the runtime at once left the listener open; the stop now waits for the server on a bounded thread).
  - `tests/grpc_server_semantics.rs` (4): protocol version refused with its reason and a missing one refused, an API key declared as `X-Api-Key` read from the lowercase metadata, `historyLength` honoured. They exist because mutations of the ported code survived without them.
  - `grpc_bridge::server` unit tests (9): `tokio::spawn` and timers work in a call awaited from the transport; errors come back unchanged; a dropped wait aborts the engine call; a panic is `INTERNAL`; a fed stream arrives in order, ends cleanly and stops its producer when dropped; a producer cancelled by its runtime or panicking after some items ends in an error after them.
  - 11 mutations of the new code: 10 killed; one survivor is equivalent (the closed-channel check in `feed`, which the abort on drop makes redundant). Treating a closed feed as a clean end is killed by both the unit and the wire test. The new tests ran clean 40-way, 8 times per file.
- **Known limitations:** `rusty_a2a`'s `server::push::tests::pinned_client_connects_to_the_validated_address_not_a_fresh_dns_lookup` needs DNS and fails in the sandbox, as on `main`. The older gRPC test files still pick a free port and rebind it, so they can hit `AddrInUse` under heavy parallel load (the new ones retry). A scheme-less gRPC endpoint (`host:port`, how the A2A spec writes an interface URL) is refused by `GrpcClient::new` with a clear error; the `tonic` client accepted it and failed its first call with "transport error". Whether such an endpoint means plaintext or TLS is not decided here. The server does not terminate TLS (unchanged).
