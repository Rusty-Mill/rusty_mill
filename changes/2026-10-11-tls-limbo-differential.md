## 2026-10-11 - rusty_tls: x509-limbo certificate differential finds and fixes three looser-than-webpki defects

- **Added:** `tests/handrolled_limbo.rs` runs 9,777 x509-limbo cases through the native path validator and webpki side by side. A ratchet file (`tests/data/limbo_divergences.txt`) pins the compared count, every skip reason and count, the count per outcome, a digest of every case's outcome, and every divergence from webpki, so a new divergence, lost coverage, or a flip among cases that agree all fail (the accounting is unit-tested without the corpus). CI runs it in the `rusty-tls-engine` job through `limbo_differential.sh`, which fetches the corpus from an immutable upstream commit, checks its sha256, and fails (never skips) if it cannot be fetched or does not match. `rusty_json` becomes a dev-dependency of `rusty_tls` for reading the corpus.
- **Fixed (security, opt-in engine only):** an intermediate CA whose `extendedKeyUsage` excluded server authentication was accepted as an issuer of server certificates; an end-entity certificate asserting `cA` was accepted; under a name constraint, a malformed `subjectAltName` entry was skipped and the certificate accepted. The default rustls engine was never affected. Each fix has a unit test that fails with it reverted, and reverting the end-entity fix is also caught by the ratchet.
- **Changed (CI planner):** `limbo_differential.sh` is one more file whose change selects the TLS engine jobs.
- **Findings recorded:** `docs/research/TLS-EVIDENCE-BAR.md` lists every remaining divergence. Two owner decisions: two name-constraint DoS cases (`pathological::nc-dos-1`, `-2`) are accepted by this validator and refused by webpki (no resource bound exists; the 0.65 s fixture timing is not one), and `anyExtendedKeyUsage` is accepted here and refused by webpki (pinned by a test).
- **Known limitations:** neither engine implements CRLs or the `pedantic` issuance lints; 25 limbo cases are not compared (client validation, custom key usage, max depth, unparsable time, no peer name). The pin is an upstream commit plus a hash; moving it is a deliberate bump. The step has not yet run on a GitHub runner.
