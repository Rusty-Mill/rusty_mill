## 2026-11-15 - ts-hub: TLS from an operator PEM (mesh hub slice H5)

- **Added:** `Hub::serve_tls(listener, acceptor)`: `/key`, the Noise upgrade and DERP behind a TLS handshake, the port a stock client reaches. `tls_acceptor(cert_pem, key_pem)` builds the acceptor from a PEM chain and a PKCS#8 key; a missing block or bad base64 is an error that names the file, and key bytes are never echoed.
- **Changed:** connection handling is generic over the stream (a private `Io` trait), so the same code runs on a socket or on TLS. `Hub::serve` is unchanged; DERP now splits the stream with `rusty_tokio::io::split`.
- **Limits:** a TLS connection takes its slot at accept, before the handshake, so a stalled handshake counts against `max_connections` and ends at `handshake_timeout`.
- **Closes:** with only the TLS port open, a client's `/key` fetch and Noise handshake are no longer readable or replayable in the clear.
- **Dependencies:** `rusty_tls` (workspace, `rusty-tokio` feature) for the acceptor; `rcgen 0.13` as a dev-dependency for test certificates (already used by rusty_tls's tests).
- **Duplication:** the ~35-line PEM reader repeats the mux server's `pem.rs`; a library cannot depend on that app, and moving a reader into `rusty_tls` is a public-API choice left to the owner.
- **Not in this slice:** ACME (separate gate); a TLS-capable `ts-derp`/`ts-control` client (H6); interop with stock `tailscaled`, which is not installed in the build environment, so it has not been run.
- **Tested:** verified-TLS `GET /key` returns the Noise key; DERP fast-start serves the `ServerKey` frame over TLS; a client pinning another certificate is refused; plain HTTP on the TLS port never gets the key; a silent handshake closes at the timeout; a stalled handshake holds a connection slot; bad PEM errors.
