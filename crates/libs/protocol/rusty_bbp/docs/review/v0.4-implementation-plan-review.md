# Review: v0.4 Implementation Plan

Reviewer: Claude (this session), 2026-10-08. Scope: the "Implementation plan", "Test strategy" and "Proving run" sections of the v0.4 spec, judged as a plan to execute, against Nano's engineering preferences (small, modular monolith, ports-and-adapters, no speculative generality, minimal justified dependencies, Result over panic).

## Verdict

**Sound direction, under-specified for execution.** The plan names the right shape (pure core, adapters behind traits, traces as tests) but leaves five things undefined that the first hour of coding will hit. None requires a spec change to the protocol; two suggest small ones.

## Findings

**P1 · blocking · Time is not an input.** Deadlines, request expiry and `turn_ended(deadline)` need a clock, but a pure core cannot read one. Fix: every command carries `now`, and the driver injects a `Tick(now)` command on a schedule. Deadline expiry is a generated event produced by `Tick`, never by the core observing time. Without this the model tests are non-deterministic.

**P2 · blocking · "Card is a fold" is true but insufficient.** Rules need indexed lookups the card does not hold: accepted `op` results, artifacts by id, verdicts by (candidate, run), open gate request, selected run secret hash, per-turn read set. Fix: a `TaskState` rebuilt from events with those indexes; the card is a projection of it. The crash-recovery property then reads "`TaskState::fold(events)` equals the live state after any prefix".

**P3 · blocking · Store contract is unstated.** Phases 2 to 4 "run inside one transaction" but the core is pure. Fix: the core is `fn handle(&TaskState, Command, now) -> Result<Vec<Event>, Rejection>`; the store trait is `append(task, expected_rev, events)` with optimistic `rev` check, plus `events(task, after)` for rebuild and `blob_put(bytes) -> (sha256, len)` / `blob_get(sha, range)`. The store computes the blob hash; the core never sees bytes, only `(sha, len, kind)`. `op` replay requires the accepted event to carry the result it returned (assigned ids), so the result is reconstructible from the log.

**P4 · blocking · "Every trace" is not enumerable as written.** The traces live in prose across five review files. Fix: `review/traces.md`, a numbered catalog (TR-01 ...) with source finding, the event sequence, and the expected rejection or transition. One test per row, named by id. The test strategy's "must fail with the fix removed" is then checkable row by row. About 35 rows.

**P5 · blocking · Proving-run scope will balloon.** As written it needs an MCP server, a sandboxed runner supervisor and a SQLite adapter before anything is proven. Fix: stage it. Stage 1 is in-process: scripted Coder and Tester call the core directly, a stub runner returns `passed` or `failed` on command, an in-memory store. Every proving-run bullet is demonstrable there. Stage 2 adds the SQLite store. Stage 3 adds MCP and one live model. The sandbox is a host requirement and never part of proving the protocol.

**P6 · non-blocking · Crate layout.** v0 listed five crates. Start with one, `bbp-core`, with modules `record`, `rule`, `lifecycle`, `state`, `budget`; add a crate only when an adapter exists (stage 2). A workspace with one member is fine to leave room.

**P7 · non-blocking · Dependencies.** Justified: `serde` and `serde_json` for typed bodies, `sha2` for blob and digest checks. Dev-only: `proptest` for the model tests. Avoidable: `ulid`. Artifact ids can be per-task integers like message ids (`art:17`), which drops a dependency and makes ids ordered. Suggest the spec change.

**P8 · non-blocking · "Transition table as data" is speculative generality.** Rows carry guards that call R3, R6, R17, which are code. A data interpreter buys nothing at one table. Fix: one `fn transition(state, &cmd, &TaskState) -> Option<Transition>` as a `match`, with an exhaustiveness test over (state × command kind) and a test that no two arms match. Same guarantee, no interpreter.

**P9 · non-blocking · Moderator is not a component in stage 1.** It is the driver loop: pull next command, call `handle`, append, repeat; plus `Tick`. Naming it a component invites a struct with state that duplicates `TaskState`. Keep it a function until the MCP stage forces otherwise.

**P10 · non-blocking · Time estimate.** "2 to 3 hours" covers the core's types and rules only. Realistic: core plus rule tests, one day; trace catalog plus trace tests, half a day; model and property tests, half a day; stage 1 proving run, half a day. About 2.5 days of focused work.

**P11 · non-blocking · Measurement inputs are missing.** The 16-task set and rubric are not in the repo. Not blocking the core; blocking the adoption decision. Add a `measurement/` placeholder with the rubric before stage 3.

**P12 · non-blocking · orch-core reminder.** Nano deferred the reconciliation until the protocol is solid. Stage 1 passing is the trigger to decide whether `bbp-core` absorbs or replaces orch-core's Board. Record the decision then; building fresh now is consistent with that.

## Decisions for Nano

1. Artifact ids: switch to per-task integers (`art:17`) and drop `ulid`? Recommended yes.
2. Proving run stage 1 in-process with a stub runner and in-memory store, MCP deferred to stage 3? Recommended yes.
3. `proptest` as a dev-dependency for model tests, or hand-rolled generator with no dependency? Recommended `proptest`.

## Order of work if approved

1. `Cargo.toml` workspace, `bbp-core` skeleton, `TaskState`, `Command`, `Event`, `Rejection`.
2. `review/traces.md` catalog.
3. Rules R1 to R18 in validation order, with per-rule tests.
4. `transition` match, entry actions, generated events, `Tick`.
5. Trace tests, then model and property tests.
6. Stage 1 proving run as an integration test.

## Amendments from ChatGPT's review of this plan (2026-10-08, branch b02aa6a)

ChatGPT agreed with the staged approach, the single crate, the match-based transition, no moderator struct, and answered yes to all three decisions. Five tightenings, all accepted:

- **A1 · Typed payloads reach the core.** P3 is amended: the store owns bytes and hashing, but the command carries the typed payload decoded by pure parsing code from the exact bytes being stored. The core validates candidate references, report consistency and the spec's brief reference from the typed value; the digest alone proves nothing about contents.
- **A2 · Outcome, not `Result<Vec<Event>, Rejection>`.** `handle` returns an `Outcome { events: Vec<Event>, response: Response }`. A rejection is an outcome with one `rejected` event and a rejection response; an accepted replay is an outcome with no events and the original response; a success carries newly assigned ids. Storage failures are a separate error type. Events persist operation receipts and per-turn read sets, not only counters.
- **A3 · Commit and dispatch ordering.** `append(task, expected_rev, events)` is atomic and durable. On a `rev` conflict the driver reloads and recomputes with the original `op` and the human's original expected `rev`; it never refreshes that precondition. Blobs are persisted before the events that reference them. Runner starts and inference starts are dispatched only from committed events, with retry-safe dispatch after a crash.
- **A4 · Clock boundary.** `now` comes from the driver, never from an agent-supplied field. A command arriving after a deadline but before the next `Tick` is processed as if a `Tick(now)` preceded it, so `Tick` frequency does not change behavior. At an exact boundary the deadline wins. Recovery issues a `Tick(now)` before re-running the entry action, so overdue deadlines fire first. `now` and credentials are excluded from `op` payload equality. Each case is a deterministic test.
- **A5 · Exit criteria per stage.** Stage 1 (in-memory, stub runner): rule and trace tests, independent invariants, replay and scheduling. Stage 2 (SQLite): durable append, crash and reopen, conflict, blob consistency. Stage 3 (MCP, live model): invocation fencing end to end, and verified sandboxing before any agent-generated code executes. The sandbox is outside the core but inside the acceptance gate.

On the decisions: integer artifact ids with explicit task scope, durable allocation and a noted wire-format change; in-process first; `proptest` with saved seeds and invariants independent of the implementation under test.
