# BBP v0.3 Review: ChatGPT

Source: ChatGPT, run by Nano in a fresh session on 2026-10-08 with `review/v0.3-review-prompt.txt`. Reproduced verbatim. Gemini was unavailable for this round.

## A. Verdict: BUILD WITH CHANGES
v0.3 is ready for a small executable state-machine prototype, but its stated safety guarantees still have counterexamples. The remaining work is to make token binding, run selection and event handling agree with the new table.

## B. Did v0.3 fix v0.2?
It fixes repository binding, frozen profile identity, the spec-change path, terminal-state resume, bounded turn counts and the proving-run participants. Run IDs do not yet fence obsolete executions, because "current run" depends on report arrival. Hidden token injection reintroduces a stale-call risk when a process survives across turns. Several required communication events have no normative transition. Removing attempt generations is reasonable once turn and run fencing actually hold.

## C. Findings

**F1 — blocking.** Section: Run and test report; Recovery; R16–R17; T9, T13.
Issue: A known run is accepted even when a newer execution has superseded it.
Failure scenario: Run 1 times out; recovery starts run 2. Delayed run 1 then reports passed. Since run 2 has no report, run 1 qualifies as current; T9 grants Tester, and approvals can reach approved. Run 2's subsequent failed report is then rejected by the artifact state gate.
Fix: Select the active run at run_started, immediately invalidate prior judgments, and mark the selected run pending. Only its final report may enable Tester or approval. Older results may be historical but cannot change eligibility. Permit exactly one immutable final report per run; otherwise a second report for the same run can change evidence without T13's "new run" condition. Validate that envelope, report and referenced log all name the same candidate/run.

**F2 — blocking.** Section: Host requirements → Token injection; Agent API; R14.
Issue: "Current token" attached to a persistent process does not identify the invocation that originated a call.
Failure scenario: Coder's first turn expires, but its inference is still running. The same role/task process receives another turn. A late tool call from the old inference arrives and gets the newly current token. R14 accepts it.
Fix: Capture the token in an immutable per-turn invocation or transport context before inference starts. Every call from that invocation keeps that token, even after the process receives a newer turn. Keeping tokens out of model-visible schemas is fine; choosing them at call arrival is not.

**F3 — blocking.** Section: Lifecycle → Transition table; Commentary; Test strategy; T5, T20–T24.
Issue: Essential actions are absent from the normative event model.
Failure scenario: Coder posts a non-gate request_decision, or finishes with plain pass. Neither matches a row. A human ask at a waiting gate also has no row granting the answering turn. The model-checking rule says unmatched triggers are rejected, so the promised continuations cannot start.
Fix: Explicitly define ordinary message admission, non-gate request opening, plain pass, and human ask/answer handling. Distinguish accepted events that leave state unchanged from invalid events. Make T19 an entry-action helper rather than a competing first-match row, and execute grants exactly once. In test, grant nobody until the selected run has a final report; T19 must not override T8's explicit wait.

**F4 — blocking.** Section: Capability matrix; Default schedule; T21.
Issue: The allowed communication paths still do not support the claimed ask/answer use of yield.
Failure scenario: During build, Coder asks Tester for clarification and yields to Tester. The default schedule grants only Coder there, so "target role has a turn in this state" provides no permission for Tester. Separately, a human asks Reviewer a question at merge_gate; Reviewer may read it but cannot post answer.
Fix: Define which roles may receive consultation turns in each state, independently of the default worker. Give those turns narrowly appropriate message permissions while preserving artifact gates. Add Reviewer's human-answer permission, or remove the promise that it can answer such questions.

**F5 — blocking.** Section: Recovery/resume; T18–T19; R17.
Issue: Resume targets are enumerated without restoring the prerequisites of those states.
Failure scenario: Test has a passed run but no Tester verdict. A budget exception escalates it; after extending the budget, the human resumes directly into review. Reviewer approves, and R17 permits merge approval without the Tester judgment normally required by T10.
Fix: Give each resume target an entry guard: approved spec for build; selected candidate/run handling for test; current Tester approval for review; complete current approval chain for a restored gate. Resuming into planning must clear the approved spec and downstream eligibility just as T2 does. If bypass is desired, make it a separate explicit human override rather than a side effect of resume.

**F6 — blocking.** Section: Evaluation order; R15; Human channel; Runner API; T2.
Issue: Exactly-once effects are defined only for Agent API mutations.
Failure scenario: A human rejection to planning succeeds but its response is lost. The task replans and receives a new approval. A delayed duplicate rejection then reaches T2 and clears the new approved spec. Runner writes accept an op parameter without an equivalent normative deduplication contract.
Fix: Require durable operation IDs and atomic result replay for every external mutation, including human and runner operations. Add expected subject/revision guards to destructive control commands so even a first delivery that arrives late cannot silently apply to newer work.

**F7 — non-blocking.** Section: R11; Reads and visibility; Test strategy.
Issue: Read accounting still mixes incompatible units.
Failure scenario: The "once per artifact id per turn" rule has no defined meaning for read(), which returns messages. Repeated ranges of one artifact are free after the first read, while the property "spent budget never decreases" conflicts with resetting reads_this_turn.
Fix: Charge message-page requests explicitly; name artifact-read deduplication as a separate rule. Scope monotonicity to task totals and individual turn totals. Keep host request-rate/response-byte limits separate from these logical allowances.

## D. Answers to Q1–Q4
- Q1: Keep the listed numbers provisional for the proving run. Record why each limit was hit before choosing defaults; do not automatically increase limits merely to make tasks pass.
- Q2: No. A change confined to flagged files can still break behavior elsewhere. Every new candidate should run the required profile set.
- Q3: Allow an inline human answer for an informational request, with an explicit rule that settles the pending wait. Keep binding accept/reject choices as decision records, and keep gate approvals as their existing events.
- Q4: Defer evaluator classes until the human-only protocol works. Later, choose them by the decision's subject and required expertise, not vendor labels alone.

## E. Missing pieces
- A deterministic distinction between command validation, state transition, entry actions and generated events. "First matching row" cannot substitute for that ordering.
- Crash tests around atomic run selection, artifact/report persistence, charging, deduplication and turn grants.
- Explicit lifecycle handling for run_started, runner failure and restart. Their effects should be represented in the executable model rather than residing only in commentary.
- A pending-run representation on the card, so "execution started" and "evidence ready" cannot be confused.

## F. What to cut
Do not restore attempt generations; correctly scoped turn and run identities are sufficient. Keep cross-vendor decisions and Delta integration deferred. Replace the assertion that prior reviews found "no architectural problems" with the narrower conclusion that no wholesale redesign was recommended.

## G. Top three changes
1. Select and fence runs when they start, with one final report per run.
2. Bind hidden tokens to originating invocations rather than current process state.
3. Complete the executable event model, including communication, resume guards and external-operation replay.

## H. Confidence
High on the traces above, based on the supplied v0.3 rules and tables. I have not assessed implementation behavior, sandbox enforcement or empirical cost/success. The next useful step is a bounded pure-core prototype that turns these traces into failing tests, rather than adding more protocol features.
