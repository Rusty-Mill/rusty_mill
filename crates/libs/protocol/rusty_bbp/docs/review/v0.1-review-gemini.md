# BBP v0.1 Review: Gemini

Source: Gemini, run by Nano in a fresh session on 2026-10-08 with `review/v0.1-review-prompt.txt`. Reproduced verbatim.

## A. Verdict
BUILD WITH CHANGES. The architectural pivot in v0.1—specifically adding the headless `runner`, content-addressed `blob` decoupling, and strict candidate revision binding (R18)—resolves the fatal flaws of v0. However, the interaction between strict turn serialization (R14), attempt lifecycles (R15), and the state transition table creates systemic deadlocks in both the `planning` and `test` states that will freeze the system during real-world runs.

## B. Did v0.1 Fix v0's Problems?
v0.1 successfully addressed server-side cursor loss, untyped evidence hallucinations, and working tree execution ambiguities. However, the fix for write concurrency—the turn token (R14) paired with attempt generations (R15)—is incomplete: it defines no protocol-level handoff mechanism for non-terminal turns, meaning an agent that needs a peer's input (`ask`/`answer`) or an asynchronous test run deadlocks waiting for the moderator to guess when to reassign the turn. Additionally, making fragments completely opaque to the store safely eliminates rejection loops, but omitting a maximum length check on fragment strings reintroduces an unbudgeted memory and injection vector.

## C. Findings

- id: F1 · severity: blocking · section: Task lifecycle & Rules (R5, R14, State × kind matrix)
  - issue: Deadlock during `planning` and `build` on collaborative sub-dialogues (`ask` / `answer`).
  - failure scenario: In `planning`, Planner holds the turn (R14) and posts an `ask` to the Coder regarding technical feasibility. Coder cannot call `post` with an `answer` because it does not hold the turn (R14 rejects with `not_your_turn`). The Planner cannot proceed without the answer; if it calls `pass`, it forfeits its turn, but the moderator has no defined rule or event mechanism to transfer the turn token to the Coder based on message recipients. The turn times out, triggering `attempt_cancelled` and wasting attempt budget.
  - fix: Add a `yield_to: role` field to the `pass` message and define an explicit rule: when an agent posts an `ask`, it must either yield the turn to the target role or the moderator must automatically grant the next turn to `to[0]`.

- id: F2 · severity: blocking · section: Interfaces — Runner & Rules (R14, R15)
  - issue: The Runner has no mechanism to acquire a turn or write artifacts under active turn enforcement.
  - failure scenario: Coder submits a candidate via `put_artifact`. This moves state from `build` to `test` and ends the Coder's turn. The Runner is triggered out-of-band and attempts to execute `put_artifact` for `log` and `test_report`. However, R14 mandates that every non-`pass` write requires holding the turn, but the Moderator turn schedule specifies the `test` state turn order as `Tester`. If the Runner writes without a turn, the store must reject it under R14; if the Runner requires a turn, the Moderator schedule fails to grant one to `runner`. Furthermore, if Runner execution spans past the attempt deadline, its delayed artifact post fails R15 (`stale_attempt`).
  - fix: Explicitly exempt the `runner` principal from R14 (turn enforcement) in the capability matrix and rule text. Have the Moderator grant a dedicated attempt generation exclusively for the test execution window.

- id: F3 · severity: blocking · section: Task lifecycle — State table & Rules (R5, R6, State × kind matrix)
  - issue: Impossible transition from `planning` to `plan_gate`.
  - failure scenario: In the lifecycle table, leaving `planning` requires: "Planner `propose` of the spec → `plan_gate`". However, under the State × kind matrix, `verdict` on a proposal is accepted in `planning`. If R7 applies, a `decision` to accept the spec requires an `approve` verdict from another vendor, or human intervention. If the Planner simply issues a `propose`, the lifecycle advances immediately to `plan_gate` before the Tester or Coder can review it, completely bypassing the cross-vendor proposal review mechanism defined in R7 and the state table. Conversely, if consensus is required, the state machine has no transition trigger on `decision`.
  - fix: Update the lifecycle table: `planning` transitions to `plan_gate` only upon a `decision` (outcome: `accept`) settling the spec `propose`, rather than directly on the raw `propose`.

- id: F4 · severity: non-blocking · section: Data model — Candidate manifest & Rule R18
  - issue: Candidate manifests reference diffs without ordering, baseline dependency hashes, or tree target states.
  - failure scenario: Coder posts a candidate with `diffs: ["art:DIFF1", "art:DIFF2"]`. `DIFF2` modifies code introduced in `DIFF1`. If a storage adapter returns json keys or array items unordered, or if the Runner applies diffs in parallel or arbitrary order, `patch` fails with `status: error`.
  - fix: Define in the schema that the `diffs` array must be applied sequentially in index order (0…n), and add a mandatory target working tree path prefix or pre-computed tree hash to the candidate manifest.

- id: F5 · severity: non-blocking · section: Rules — R4 & Data model — Artifact record
  - issue: Opaque fragments are unconstrained in length, allowing cache-stuffing and bypass of R8.
  - failure scenario: An agent attempting to evade the 1,200-character prose cap in R8 places a 20,000-character prompt injection or hidden rationale directly inside the URI fragment (e.g., `art:01HSPEC#<massive text>`). Because fragments are completely opaque to the store (R4), it passes validation without deducting message character budgets.
  - fix: Cap URI fragment length at 128 characters in R4.

- id: F6 · severity: non-blocking · section: Integration edges — Delta review threads & Principals
  - issue: Identity conflation between Delta host user and BBP `human` principal.
  - failure scenario: In Delta review threads, subagents and human reviewers write to the same thread. An agent acting via Delta CLI emits a thread comment containing an approval string. The BBP Delta adapter naively translates thread comments into a `human_approval` event, violating R13.
  - fix: Mandate that the human channel adapter cryptographically signs or checks authenticated session metadata confirming the author principal is strictly `kind: human` before translating any Delta action into a BBP human event.

## D. Answers to Open Questions (Q1 to Q6)
- Q1 (Tester writing diffs): Diff additions must flow through Coder. Allowing Tester to write diffs directly into candidates creates race conditions over the candidate manifest and splits repository ownership; Tester should post `diff` artifacts as attachments to `finding` records for Coder to absorb.
- Q2 (R7 proposal verdict qualification): Any assigned agent of a different vendor must qualify. Restricting it to Tester/Reviewer needlessly bottlenecks design decisions during `planning` and `build` when the Coder or Planner could provide the necessary cross-vendor consensus.
- Q3 (Default budget numbers): Messages: 50, Bytes: 5MB, Reads: 250, Iterations: 4. A 4-iteration cap bounds infinite regression while allowing adequate room for the 1–2 rework cycles typical of complex PRs.
- Q4 (Reviewer seeing Tester findings): No. Total isolation preserves the core value proposition: fresh, unbiased evaluation by construction without anchoring on another model's reasoning.
- Q5 (Blob retention and size): Max size 10MB; retention scoped strictly to task lifetime plus 30-day post-close archive. Prevents local disk exhaustion while preserving auditability during evaluation runs.
- Q6 (`request_decision` deadlines): Inherit the turn deadline. Introducing independent timers complicates the Moderator's state machine without adding utility; if a decision is not answered before the turn window expires, the task should escalate deterministically.

## E. Missing Pieces
1. Working Tree Conflict Clean-up and Base Rebase: The spec tracks `base` as a git commit hash. If the upstream repository moves during a long multi-turn iteration, the candidate becomes unmergeable at the `merge_gate`. A defined mechanism for re-basing a candidate onto an updated `base` commit is missing.
2. Crash Recovery for In-Flight Turns: If an agent process crashes while holding a turn token (R14), the system must wait out the entire turn deadline before the moderator triggers `attempt_cancelled`. An explicit heartbeat or `abort_turn` tool is needed for the host process to release the token cleanly upon agent failure.
3. Structured Test Harness Configuration: The Runner executes a command (e.g., `cargo test`), but the document lacks an artifact schema defining sandbox constraints (timeout limits, network egress policy, allowed filesystem mounts).

## F. What to Cut
1. `supersedes` message field (Data model / R12): Adds store complexity, cursor indexing branchiness, and validation rules. In a true append-only blackboard, new assertions naturally supersede older ones via timestamp ordering and explicit message references; a dedicated mutable-like pointer is unnecessary.
2. `scope: all` vs `scope: addressed` on reads: Agents should read all messages visible to their capability. Creating filtering sub-modes adds client complexity for negligible token savings.
3. The `Documenter` and `Triage` references in rationale: Although cut from the matrix, historical references remain in earlier narrative sections and should be completely scrubbed to prevent confusion.

## G. Top Three Changes in Priority Order
1. Fix the Runner Execution Lifecycle: Exempt the `runner` principal from R14 turn tokens and add an explicit `test_executing` sub-state or attempt window so test reports can be recorded without violating concurrency rules.
2. Implement Explicit Turn Handoffs in R14: Add a `yield_to` parameter to `post` / `pass` or define deterministic turn-passing rules for `ask` / `answer` sequences to prevent deadlocks.
3. Align Planning State Transitions with Consensus (R7): Require a confirmed `decision` record to trigger the transition from `planning` to `plan_gate`, making cross-vendor spec approval functional.

## H. Confidence and Limitations
- Confidence: High. The protocol semantics, distributed invariants, race conditions, and state transitions were thoroughly evaluated against the provided specification.
- What could not be assessed: Specific real-world token-to-dollar savings versus a classic relay loop (untestable until the 16-task evaluation harness runs), and exact private CLI behavior of the Delta worktree integration.
