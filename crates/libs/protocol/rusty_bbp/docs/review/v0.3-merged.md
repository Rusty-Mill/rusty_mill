Two fresh-session reviews of v0.3; Gemini was unavailable. Both: BUILD WITH CHANGES. Both close with the same recommendation: the next step is a bounded pure-core prototype that turns these traces into failing tests, not a fifth round of prose.

## 2. Raised by one, accepted

- **`error` run has no exit** (Claude F3). `test` with a final report `status: error` escalates with `from: test`; entering `test` with an `error` selected run starts a new one.
- **Human and runner mutations need idempotency and expected-revision guards** (ChatGPT F6). Every external mutation carries an `op`; destructive control commands (`human_rejection`, `resumed`, `cancelled`) carry the expected subject or card revision and are rejected on mismatch.
- **Budget checks after effects** (Claude F16). Budget evaluation is a generated event after a row's effects, not a competing row.
- **Evaluation order** (Claude F12). `op` lookup precedes the terminal check.
- **Spec check at submission** (Claude F13). Drop `spec` from the manifest; the store stamps the approved spec on the candidate record.
- **`request_decision` must address `human`** (Claude F10), and the store sets its deadline from task configuration.
- **Task brief** (Claude F7). A `brief` artifact kind, written by the human at `task_opened`; the gate spec must ref it.
- **Per-run runner secret** (Claude F15). `run_started` mints a secret the supervisor presents; the run id alone is not a credential.
- **Pending run on the card** (ChatGPT E). `run: {id, status: pending | final}`.
- **Narrow the claim** (ChatGPT F). Rounds two and three recommended no wholesale redesign; they did not certify the architecture.

## 3. Open questions settled

- Q1 budgets: provisional; record why each limit was hit before changing it. Never raise a limit to make a task pass.
- Q2 skip `test` on narrow revise: no. Unanimous.
- Q3 inline human answer: yes, with a rule that an `answer` to a non-gate `request_decision` settles it; accept/reject stays a `decision`.
- Q4 evaluators: deferred. Unanimous.

## 4. What both reviewers say to do next

Stop adding protocol features. Write v0.4 as the implementation spec with the fixes above, then build the pure core: records, rules in evaluation order, the transition table as data, and a model checker. Every trace in rounds one to four becomes a failing test first. The proving run follows.
