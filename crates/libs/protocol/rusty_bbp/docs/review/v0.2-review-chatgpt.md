# BBP v0.2 Review: ChatGPT

Source: ChatGPT, run by Nano in a fresh session on 2026-10-08 with `review/v0.2-review-prompt.txt`. Reproduced verbatim.

## A. Verdict: BUILD WITH CHANGES
The revised boundaries are worth implementing, but several permitted event sequences still bypass approval freshness or leave the task stuck. Fix those sequences in an executable state-machine model before connecting live agents.

## B. Did v0.2 fix v0.1?
Yes: the initial plan gate, artifact gating, execution-token identity, report discovery, human-only decisions and runner credential separation now have concrete answers. Candidate approval still does not bind the exact current test evidence. Spec amendments and human waits lack complete continuation paths. Per-turn read accounting is not fenced by those otherwise-improved tokens. The new approved/closed distinction is sound, but recovery must preserve its prerequisites.

## C. Findings

**F1 — blocking.** Section: Test report; Task lifecycle; R3, R16–R17.
Issue: "Latest report" can replace the evidence behind an existing approval.
Failure scenario: Report A passes; Tester and Reviewer approve candidate C. While at merge_gate, a delayed rerun publishes failed report B for C. R17 still accepts human approval because a Reviewer approve on C exists.
Fix: Give each authorized run a generation/run ID and immutable profile identity. Bind verdicts and merge approval to the selected report/run. Replacing that evidence invalidates downstream verdicts and returns to test. Historical results may be retained, but cannot become current merely by arriving last.

**F2 — blocking.** Section: Decision body; artifact gating table; Task lifecycle; R17.
Issue: A spec amendment enters a gate that cannot produce its new approval subject.
Failure scenario: The human supplies changes_spec after plan approval. BBP enters plan_gate, but Planner can write a revised spec only in planning, and no new triggering request_decision exists.
Fix: Revoke downstream authorization and the active turn; return to planning. Store the revised spec and use the normal request_decision → plan_gate path. Old plan approval must cease authorizing candidates immediately.

**F3 — blocking.** Section: Turns and tokens; State × kind matrix.
Issue: Unconditional return from yield conflicts with state-changing actions.
Failure scenario: Tester yields to Reviewer during test; Reviewer escalates. The unconditional yield-return rule then grants Tester a turn in escalated, contrary to its human-ask-only schedule. A yielded turn timing out also rolls the attempt while yield promises return within the same attempt.
Fix: Restrict yields to roles useful in the current state. Return to the yielding role only if state, attempt and candidate remain unchanged and no human wait intervened; otherwise use the new state's schedule. Editing after failed tests requires revise → build.

**F4 — blocking.** Section: request_decision; Turns and tokens; Recovery; Task lifecycle.
Issue: Human waits and resume do not have a complete, guarded continuation.
Failure scenario: Coder requests a decision during build; its turn ends. The human answers without changing the spec, but no rule clears the pending deadline or restores Coder's turn. The old deadline can later escalate completed work. Recovery also says resume works "from any state," conflicting with terminal states and the lifecycle table.
Fix: Persist the pending request and continuation. Settlement cancels its deadline and resumes the correct role. Restrict resume to specified non-terminal states and validate target prerequisites, including current test/review evidence; never reopen closed or cancelled.

**F5 — blocking.** Section: Reads and visibility; Agent API; R11, R14.
Issue: Per-turn reads lack turn identity.
Failure scenario: An old or off-turn process calls get_artifact. Its allowance is undefined; implementations can charge another turn or permit unmetered reads. A delayed read from the same principal is indistinguishable from a new-turn read.
Fix: Require the caller's live execution token on charged agent reads. Charge the token's turn atomically. Keep the free card and explicitly authorized runner/human reads separate.

**F6 — blocking.** Section: Turns and tokens; budgets; Recovery.
Issue: Work can remain unbounded without accepting messages.
Failure scenario: An agent repeatedly reaches its deadline without posting. Each timeout rolls the attempt, while message, byte and build-iteration budgets remain unchanged. Resuming after an exhausted task budget also has no defined workable policy.
Fix: Add a finite timeout/attempt or total task-runtime allowance and escalate at exhaustion. Require an explicit, recorded budget extension when resuming exhausted work; ordinary resume must not silently reset counters.

**F7 — blocking.** Section: Candidate manifest; Runner API; R4, R17; Q1.
Issue: Task, repository and execution configuration are not fully bound.
Failure scenario: A candidate references the approved spec but names a different repository from task_opened.repo. No stated validation rejects it; the runner can test the wrong repository. A mutable "default" profile similarly weakens reproducibility.
Fix: Require candidate.repo to equal the task's canonical repository and resolve base within it. Freeze the required profile configuration or digest. Define the tree-hash algorithm and verify the report/log candidate identities agree. Include R17 explicitly in put_artifact's rule list.

**F8 — non-blocking.** Section: R14–R15, R18; Recovery tests.
Issue: Duplicate-result lookup precedence is unclear.
Failure scenario: A candidate submission succeeds and ends its token, but its response is lost. A retry can encounter token_expired or terminal before returning R15's original result.
Fix: After authenticating principal/task, look up accepted op and compare its immutable payload before checking current token/state. Returning that original result is not a new write. Test retries after turn end, state change, cancellation and closure.

**F9 — non-blocking.** Section: Proving run before v0.3.
Issue: The stated proving run cannot exercise its gates faithfully without Planner and Reviewer.
Failure scenario: The human stub approves a candidate, but R17 requires a Reviewer approval; valid candidate submission also requires a previously approved Planner spec.
Fix: Use deterministic Planner and Reviewer stubs through the normal APIs now. Replace them with live models later. Do not bypass admission rules with privileged fixtures.

## D. Answers to Q1–Q5
- Q1: Use a small, fixed set of required profiles, even if initially it contains one. Require all required profiles to pass; bind their configurations and results to the candidate.
- Q2: Defer waivers initially. A failed report cannot currently reach merge_gate through normal approvals. If added, define a human-only waiver of an exact run/profile with reason and expiry, and an explicit path to review; never relabel failure as passed.
- Q3: Keep numbers configurable and measure them. First define byte accounting, finite retry/runtime limits, bounded runner output, rejected-request rate limits and budget-extension semantics.
- Q4: Keep Reviewer sessions fresh per candidate for the first comparison. Relaxing that now changes the experiment and weakens the independence claim.
- Q5: Leave cross-vendor decisions deferred. Later, designate evaluators per decision class; vendor difference alone does not establish independent judgment.

## E. Missing pieces
- A complete transition table covering human decisions, yields, timeouts, reports, restart and resume, with guards and precedence.
- A host contract for dependencies available inside the no-egress sandbox, output/storage limits, and cancellation of running workloads.
- The actual 16-task evaluation set and success rubric. They are not included, so the adoption criterion cannot yet be assessed.
- Align the rejection property with R11: budget rejection explicitly changes escalation or turn state, not only the rejection counter.

## F. What to cut
Keep Appendix B deferred. Treat Delta as an integration hypothesis: a fresh thread alone does not establish the sandbox properties required elsewhere in this draft. Stop optimizing for exactly eighteen rules or five records; coherence matters more than the count.

## G. Top three changes
1. Bind approvals to an authorized, immutable test run and profile.
2. Complete spec-change, human-wait, yield and resume transitions.
3. Fence charged reads and bound timeout/recovery loops.

## H. Confidence
High on these internal protocol contradictions and event sequences. This is a static review of the supplied v0.2 document; no implementation, sandbox, live-agent behavior or external-product claims were validated.
