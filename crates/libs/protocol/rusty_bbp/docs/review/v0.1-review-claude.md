# BBP v0.1 Review (integrated lens)

## A. Verdict

**BUILD WITH CHANGES.** The core shape (single-writer store, typed records, candidate binding, runner as sole evidence source) is sound and worth proving. But the candidate write path is ungated by state or turn, so a Coder can swap the candidate under the merge gate and defeat R18; that and four smaller gaps must close before the proving run.

## B. Did v0.1 fix v0's problems?

Mostly. R18 makes "approve A, merge B" unrepresentable, but candidate writes are checked only by R11/R15/R16/R17, so the candidate can be *replaced* in `review` or `merge_gate`: the same failure in new clothes (F1). R7 is now representable, but "different vendor" has no reference principal, so the proposer can settle its own proposal with one Tester signature and, via `changes_spec`, alter the human-approved spec without a gate (F3). R15 also applies to the runner, whose work is bound to a candidate, not a turn, so long test runs are discarded by deadline churn (F4). The runner principal fixes evidence provenance but equates an isolated worktree with isolation; test code is agent-authored executable code (F5).

## C. Findings

**F1**
- severity: blocking
- section: Interfaces / Agent API (`put_artifact`), Rules R14, R18, Task lifecycle, State × kind matrix
- issue: Messages are gated by state (R5) and turn (R14); artifact writes are not. Nothing stops a `candidate` write in `test`, `review` or `merge_gate`; it becomes current, so R18 points approvals at an unreviewed revision.
- failure scenario: Reviewer approves C1; state `merge_gate`. Coder writes candidate C2 with an extra diff; store accepts; runner reports on C2. Human approves "the current candidate"; `human_approval` names C2, passes R18, task closes. Tester and Reviewer never saw C2.
- fix: Apply R5-style state gating and R14 to `put_artifact`: `candidate` only in `build` by the turn-holding Coder; `diff` only in `build`; `spec` only in `planning` (or on a `changes_spec` decision). Additionally, at `merge_gate`, R18 should require that a Reviewer `approve` verdict exists whose `subject` equals the approved candidate.

**F2**
- severity: blocking
- section: Rules R18, Event `human_approval`, Task lifecycle `plan_gate`
- issue: R18 says every `human_approval` names the task's current candidate, but at `plan_gate` no candidate exists (Coder writes the first one in `build`). As written, plan approval is either unrepresentable or unbound, and the test strategy's "binding" property cannot be stated for it.
- failure scenario: Planner proposes spec S1 → `plan_gate`. Store rejects `human_approval` (`stale_candidate`, no candidate), or accepts it with an empty binding; Planner then writes S2 during `build`; the candidate manifest names S2; nothing records which spec the human approved.
- fix: `human_approval` carries `gate` and `subject`; at `plan_gate` the subject is the `spec` artifact referenced by the triggering `propose`; R18 applies to `merge_gate` only. Candidate manifest `spec` must equal the approved spec or the task returns to `plan_gate`.

**F3**
- severity: blocking
- section: Rules R7, Decision body `changes_spec`, Capability matrix, Open question Q2
- issue: (a) "an agent of a different `vendor`" names no reference: different from the decision author? the proposer? Planner and Coder may post `decision`, so a Coder can propose, get one Tester `approve`, and decide its own proposal. (b) A `decision` with `changes_spec` after `plan_gate` changes the approved spec with no human gate; "a decision never changes gate state" is exactly the problem. (c) The Reviewer cannot read `propose` messages and never holds the turn in `planning`/`build`, so the second signature is always the Tester.
- failure scenario: Coder (openai) proposes "drop AC3"; Tester (anthropic) approves; Coder posts `decision accept, changes_spec=AC3`; Planner narrows the spec; human approves the merge believing AC3 was delivered.
- fix: R7: verdict author's vendor differs from both the proposer's and the decision author's vendor, and the decision author is not the proposer. Agent decisions may not carry `changes_spec`; a spec change requires a human `decision` or a return to `plan_gate`.

**F4**
- severity: blocking (feasibility)
- section: Task card, Read operations, Rules R15, Attempts, Runner, Task lifecycle `test`
- issue: Agents cannot discover artifact ids: no list operation, runner posts no messages, events are not readable, and the card has no `test_report` field, so the Tester cannot satisfy R3. Separately, the Tester's turn in `test` starts while the runner is still running; if the suite outlives the deadline, the generation increments and the runner's write fails R15.
- failure scenario: Tester turn deadline 10 minutes; suite takes 14; attempt 3 starts; runner's `test_report` with `attempt: 2` → `stale_attempt`; runner reruns under attempt 3; same outcome.
- fix: Add `test_report` (latest report for the current candidate, or null) to the task card and a `test_report_stored` event. In `test`, the moderator grants the Tester's turn only after that event. Exempt runner artifacts from R15 or bind them to `candidate` instead of `attempt`.

**F5**
- severity: blocking (security)
- section: Principals and roles (Runner), Interfaces / Runner, Risks "Prompt injection via artifacts", Non-goals (no push credentials)
- issue: "Nothing it reads can instruct it" misses that the runner *executes* agent-authored code (tests, `build.rs`, proc-macros). An isolated worktree is not a sandbox; any credential in the runner's environment, including the `origin` remote, is the Coder's transitively.
- failure scenario: Coder's diff adds a test that reads `~/.git-credentials` or `GITHUB_TOKEN`, pushes a branch, and prints "ok". Runner reports `passed`. The non-goal "no agent holds push credentials" is violated by a passing test.
- fix: Add a host requirement next to the Reviewer-freshness one: the runner executes untrusted code and must run with no network egress, no credentials and a read-only mount of the base; and the `log` blob must be the only channel out. Also reword the risk row: the Reviewer reads Planner-written Markdown and code comments, so isolation limits context, not injection.

**F6**
- severity: non-blocking
- section: Rules R16, R11
- issue: `op` scope is undefined (global vs per principal per task), and the interaction with rejection is unspecified: if the first attempt was rejected (`not_your_turn`) and the agent retries the same `op` after its turn arrives, R16 as written returns the original rejection forever. Replays must also not re-charge R11.
- failure scenario: Coder posts op=7 just before `turn_granted`; rejected; retries op=7; gets the cached rejection; loops until escalation.
- fix: Scope `op` to (principal, task); record `op` only for accepted writes; replays are free under R11.

**F7**
- severity: non-blocking
- section: Candidate manifest, Rules R4, R17
- issue: Manifest fields are not validated: `spec` and `diffs` may name artifacts of the wrong kind, another task, or nothing; `iteration` duplicates card state and can lie.
- failure scenario: Coder lists a `diff` from task T05; it applies; runner passes; Reviewer inspects a diff the Planner never saw.
- fix: Apply R4 (same task) plus kind checks to `spec` and `diffs` at `put_artifact`; drop `iteration` from the manifest.

**F8**
- severity: non-blocking
- section: Rules R11, Read operations
- issue: Reads are charged per call regardless of payload; a Reviewer paging a large diff, or a client retrying under at-least-once delivery, exhausts `reads` and escalates the *whole task*.
- failure scenario: 2 MB of diffs at a 64 KB range cap is 32 reads per artifact; the Reviewer exhausts 200 reads before writing anything; task escalates.
- fix: Charge `bytes` for `get_artifact` and `messages` for `read`, make `reads` per role, and treat exhaustion as `pass`-with-finding rather than task escalation.

**F9**
- severity: non-blocking
- section: Task lifecycle `planning`, State × kind matrix
- issue: "Planner `propose` of the spec → plan_gate" is not checkable: any Planner `propose` could trigger it, or none.
- failure scenario: Planner proposes "use crate X" with a spec ref while still drafting; task jumps to `plan_gate`; human approves a half-written spec.
- fix: Transition on Planner `request_decision` whose `refs[0]` is a `spec` artifact and `to` includes `human`.

**F10**
- severity: non-blocking
- section: Moderator ("Tester if it asks"), Rules R14, Q1
- issue: No mechanism lets the Tester "ask" for a turn: only `pass` is allowed out of turn. And a Tester `diff` has to be picked up by a Coder-written manifest, requiring a Coder turn after the Tester's.
- fix: In v0.1, Coder writes all diffs; Tester expresses test gaps as `finding`. Revisit after measurement.

## D. Open questions

- **Q1:** Coder only. Removes the turn-handoff problem in F10 and one writable kind.
- **Q2:** Any assigned agent of a different vendor from both proposer and decider, via `finding` with `reply_to`, not a `verdict`. Verdicts should stay candidate-bound; reusing them for proposals muddies R3/R18.
- **Q3:** no opinion on numbers; make `rejections` an explicit budget field since the moderator already caps it.
- **Q4:** No in v0.1; expose only the Tester's typed *verdict* on the current candidate, then measure.
- **Q5:** Per-blob cap at the host range cap times a small multiple; retain until task `closed` plus a fixed window.
- **Q6:** Own deadline. Turns are minutes, human decisions are hours; inheriting guarantees spurious escalation.

## E. Missing pieces

- Artifact discovery and event reads (F4); today only the fold is visible.
- Base drift: nothing says what happens when `base` falls behind the default branch; apply failure is an undifferentiated `error`.
- Runner sandbox contract, resource limits and a timeout outcome (F5).
- Task cancellation is in the human channel but not in the state machine or event table.
- Multiple commands and flaky-test policy: one `command` and one status cannot express "lint passed, integration flaked".
- Reviewer freshness across iterations: one session per task means the iteration-3 Reviewer saw iterations 1 and 2.

## F. What to cut

- `iteration` from the candidate manifest (derived state).
- Tester as `diff` writer (Q1).
- `verdict` on proposals; use `finding` with `reply_to` for the second signature and keep `verdict` candidate-only.
- The `reads` budget as a task-level escalation trigger (F8); keep bytes and messages.
- The `advisory.tokens` card field until measurement needs it; `usage` events already hold it.
- The A2A and AG-UI integration rows; one sentence in Non-goals suffices.

## G. Top three changes

1. Gate `put_artifact` by state and turn, and require a Reviewer `approve` on the exact candidate at `merge_gate` (F1).
2. Fix R7's vendor reference, forbid agent `changes_spec`, and bind `plan_gate` approval to a spec id (F2, F3).
3. Add `test_report` to the card plus a stored event, grant the Tester's turn only after it, and exempt runner writes from R15; state the runner sandbox requirement (F4, F5).

## H. Confidence

Medium-high on protocol logic (F1 to F10 follow from the document's own tables). Low on Delta and DeltaDB: I cannot verify "no public API", "replicated CRDT", subthread inheritance or the agentic-safety statements; check delta.dev docs and Zed's announcements and treat the integration table as hypotheses. I could not assess whether real models tolerate an eighteen-rule rejection surface without looping; the proving run is the right test.
