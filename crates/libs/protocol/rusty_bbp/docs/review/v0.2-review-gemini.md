# BBP v0.2 Review: Gemini

Source: Gemini, run by Nano in a fresh session on 2026-10-08 with `review/v0.2-review-prompt.txt`. Reproduced verbatim.

## A. Verdict
BUILD WITH CHANGES. Draft v0.2 makes major leaps in distributed rigor—specifically by bounding writes to execution tokens (R14), establishing the runner supervisor boundary, and formalizing two-phase revision pinning (R17). However, blocking protocol-level contradictions remain around runner authorization (R16 vs R18), turn deadlocks during attempt rollovers, and an unresolvable race condition when handling base drift in the `approved` state.

## B. Did v0.2 Fix v0.1's Problems?
v0.2 successfully resolved the non-deterministic cursor hazards, bounded URI fragment length abuse, and eliminated proposal-verdict ambiguities by deferring cross-vendor decisions to Appendix B. However, the introduction of execution tokens and attempt lifecycles created two new edge cases: R14 lacks an explicit bypass mechanism for the runner supervisor (which must post reports without an execution token), and the rollover mechanism for expired attempts leaves yielded roles trapped in abandoned attempt generations. Furthermore, decoupling the `approved` and `closed` states via out-of-band `merge_receipt` events introduces an unmonitored window where base drift cannot be remedied without violating candidate immutability.

## C. Findings

- id: F1 · severity: blocking · section: Rules — R14, R16 & Interfaces — Runner API
  - issue: Rule R14 invalidates runner writes, conflicting directly with R16 and the runner supervisor model.
  - failure scenario: Coder submits a candidate, moving state to `test`. The out-of-band runner supervisor executes tests and invokes `runner_put(candidate, "test_report", bytes, op)`. Under R16, runner writes need no token. However, R14 states: "Every Agent API mutation, pass included, carries a live execution token" and rejects with `bad_token`. Even though `runner_put` is listed under "Runner API", the rules table enforces R14 across all non-human store writes without an explicit exception for the runner principal.
  - fix: Amend R14 text explicitly: "Every mutation from an agent principal carries a live execution token. Human and runner principals are exempt from execution tokens and are authenticated via their respective channel credentials."

- id: F2 · severity: blocking · section: Task lifecycle — Turns and tokens & Rules (R14, R15)
  - issue: Attempt rollover invalidates outstanding `yield_to` return turns, causing task deadlocks.
  - failure scenario: In `build`, Coder holds turn 1 (attempt 1) and issues an `ask` to Tester with `yield_to: tester`. The moderator grants Tester turn 2 (attempt 1). Tester takes longer than the turn deadline to respond. The moderator rolls the attempt: emits `attempt_cancelled(attempt 1)`, `attempt_started(attempt 2)`, and revokes Tester's token. The spec states: "when it ends, the turn returns to the yielding role in the same attempt". Because attempt 1 is dead, the scheduled return to Coder fails R15/R14, and the default schedule restarts from the top of the state machine or hangs indefinitely because neither role holds a valid token for attempt 2.
  - fix: Specify that when an attempt rolls while a `yield_to` delegation is active, the delegation stack is cleared, and the moderator immediately issues a fresh `turn_granted` for attempt N+1 to the default primary role for that state (e.g., Coder in `build`).

- id: F3 · severity: blocking · section: Task lifecycle — States (`approved`, `build`) & Candidate manifest (R17)
  - issue: Handling `base_drift` from `approved` violates candidate binding invariants.
  - failure scenario: A candidate is approved at `merge_gate`, transitioning the task to `approved`. Before the human completes the merge, upstream main moves. The human records `human_rejection(reason: base_drift)`, moving state back to `build` and bumping `iteration`. The Coder rebases the diffs and tries to submit a new candidate. However, the plan gate approved a spec whose acceptance was bound to the original base commit context; furthermore, if `iteration` exceeds the budget during this rebase loop, the task transitions to `escalated` from `build`, leaving the repository in an ambiguous state where code was approved but cannot be merged or closed without a complete re-run of the test and review pipeline.
  - fix: Make `approved → build` on `base_drift` explicitly clear all existing candidate-bound approvals while preserving the approved `spec` id. Add an optional fast-track transition: if diff contents are byte-identical after rebasing, allow the Runner to produce a new report and skip directly to `merge_gate`.

- id: F4 · severity: non-blocking · section: Data model — Test report & Rules (R3)
  - issue: Runner exit codes and report status can disagree without core validation.
  - failure scenario: A compromised or buggy runner supervisor generates a report where `exit_code: 1` (test failure) or `failed: 4`, but sets `status: "passed"` in the JSON payload. R3 checks only that `report.status == "passed"`. Tester/Reviewer sees `status: passed`, writes an `approve` verdict, and code with failing tests advances to `merge_gate`.
  - fix: Require `bbp-core` in R3/R16 to structurally validate consistency on `test_report` writes: if `status == "passed"`, `exit_code` must be `0` and `failed` must be `0`.

- id: F5 · severity: non-blocking · section: Rules — R11 (Accounting and budgets)
  - issue: Per-turn read budget exhaustion can be weaponized by a malicious or looping model to starve task progress.
  - failure scenario: Coder enters a tight retrieval loop fetching artifacts, exhausting `reads_per_turn` (40 reads). Under R11, exceeding `reads` immediately ends the turn and records `turn_ended(budget)`. The moderator grants the next turn back to Coder (or Tester). The agent immediately repeats the behavior. Because `reads_per_turn` resets every turn, total task read consumption ballooned without tripping the global task message or byte budget until `iterations` or wall-clock run out.
  - fix: Track cumulative task-level reads alongside `reads_this_turn` in the task card budget (e.g., `max_task_reads`), and escalate the task if total reads cross the limit.

- id: F6 · severity: non-blocking · section: Interfaces — Agent API (`post` tool signature)
  - issue: The `post` tool signature exposes `token` directly as an LLM argument.
  - failure scenario: The host passes the token to the model in the system prompt or tool response. A smaller model (e.g., Hermes or local 8B) fails to copy the opaque string exactly, emits `token: "tok_???"`, or drops the parameter when executing MCP tool calls, tripping `bad_token` rejections and burning attempt counts.
  - fix: Inject the execution token at the MCP transport/adapter layer (as an HTTP header or environment session wrapper) rather than making it a visible tool parameter that the model must manually emit on every tool invocation.

## D. Answers to Open Questions (Q1 to Q5)
- Q1 (Run profiles): Support a named profile set with aggregated status. Software tasks require linting, typechecking, and testing; bundling these under a single compound command makes log triage difficult, whereas independent profiles allow selective caching and targeted remediation.
- Q2 (Flaky test waivers): Permit waivers exclusively through the human channel via `human_approval(candidate, waive_tests=true, reason=...)`. Agents must never waive test failures; human waivers must be recorded as explicit auditing events in the immutable event log.
- Q3 (Budget numbers): Messages: 40; Bytes: 5MB; Reads per turn: 30; Task total reads: 150; Iterations: 4. Keeps context windows lean and prevents token bleed while allowing ample headroom for two full build/test/review rework cycles.
- Q4 (Reviewer fresh session scoping): Keep fresh session per candidate. Reusing sessions across candidates re-contaminates the Reviewer with its own prior rejected feedback and causes stubborn anchoring bias on re-evaluations.
- Q5 (Appendix B cross-vendor evaluators): No opinion. Keep decisions human-only until basic v0.2 mechanics are proven in execution.

## E. Missing Pieces
1. Working Tree Cleanliness Assertion: The candidate manifest specifies commit base and ordered diffs, but the protocol has no invariant requiring the runner to verify that the base commit itself passes tests prior to applying diffs. Broken main branches will cause spurious candidate rejections.
2. Explicit Heartbeat / Cancellation Hook: When an agent stalls or an inference provider times out mid-turn, the system must wait out the full deadline before rolling the attempt. An adapter-level `abort_turn(token, reason)` tool is needed for the host supervisor to terminate frozen runs proactively.
3. Artifact Size Pre-flight Limits: While R11 meters bytes, an agent attempting to post a 50MB unified diff will crash or hang single-threaded embedded database adapters during base64 ingestion before R11 can even reject it. An explicit `max_artifact_bytes` hard limit (e.g., 2MB) must be checked at the adapter envelope.

## F. What to Cut
1. `changes_spec` in human `decision` body: Plan alterations after the plan gate are already handled cleanly by `human_rejection` returning the state to `planning`. Having `decision` mutate specs mid-flight creates dual paths for spec invalidation.
2. `log` as a distinct artifact kind: Merge `log` into `test_report` as a direct embedded property or require the runner supervisor to store raw output in standard storage and reference it by blob hash directly. Having both creates unnecessary record-linking overhead without access control differences.
3. Appendix A (Delta integration details): Keep the core spec focused on protocol invariants. Adapter-specific behavior for non-API beta products belongs in external operational runbooks.

## G. Top Three Changes in Priority Order
1. Exempt Runner from R14: Formally decouple the runner supervisor from agent execution tokens in R14 to ensure `runner_put` operations are admitted by the store.
2. Inject Execution Tokens at the Adapter Boundary: Remove `token` from the agent-facing MCP `post` tool schema and bind it to the MCP transport session to eliminate LLM parameter-copy errors.
3. Formalize Attempt Roll Deadlock Resolution: Specify moderator behavior for handling open delegations (`yield_to`) when deadlines trigger attempt cancellations.

## H. Confidence and Limitations
- Confidence: High. The evaluation comprehensively covers the state machine, concurrency boundaries, distributed failure modes, and MCP protocol integration points.
- What could not be assessed: Concrete token economy trade-offs (unverifiable until benchmarked on the 16-task evaluation harness), and host-level container sandbox escapes in multi-tenant environments.
