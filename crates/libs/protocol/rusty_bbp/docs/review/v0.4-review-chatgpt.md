# BBP v0.4 Review: ChatGPT

Source: ChatGPT, reviewing main at f355519, pasted by Nano on 2026-10-08. Reproduced verbatim. Each item is applied as an erratum (E1 to E6) in the v0.4 spec header.

Reviewed v0.4 on main at f355519. My recommendation: build the pure core next, but correct these six issues in its first implementation/tests. The spec is still internally inconsistent in a few important places.

1. **Rerun does not actually select a new run.** T12 invalidates verdicts and enters test. The test entry action starts a run only when none exists or the old report is error. Rerunning a pending, passed or failed run therefore leaves the old run selected, contradicting the promised stale_run protection. Correction: rerun must unconditionally select a fresh run and secret, clear report eligibility, and revoke the previous run. Entry actions must not start a second one.

2. **Replanning can revive a candidate whose plan approval was revoked.** T2 clears the approved spec and approvals, but retains the candidate/run. Resume(test) requires only a candidate. An old candidate with an error report can consequently be rerun after replanning, receive fresh Tester/Reviewer approvals, and pass R17 even though its stamped spec is no longer approved. Correction: deselect the candidate/run when returning to planning, or require candidate.spec == current approved_spec throughout resume, testing, verdicts and merge approval. Historical records can remain.

3. **Budget escalation can recurse inside one transaction.** Phase 4 evaluates budgets after effects. An exceeded total generates escalated, which is processed as another command in the same transaction. That command still sees the same excess and can generate escalated again; T3 also accepts it while already escalated. Correction: generate escalation once per newly detected exhaustion, consume that trigger, and do not recursively re-evaluate an unchanged violation. Preserve the original from state. Also state whether the current after-effects policy intentionally permits the limit-crossing operation.

4. **A pending human decision does not reliably keep work paused.** Coder can open a request in build and end its turn. Restart then reruns build's entry action and grants Coder before the request is settled. The same bypass occurs when the human asks Tester a side question: after that consultation, the default Coder turn resumes despite the outstanding request. Correction: use one scheduler eligibility check for entry, restart, consultation return and settlement. An unresolved request must retain its wait and continuation. Explicit command effects are also needed: phase 2 currently says unmatched commands keep the turn running, while plain pass and non-gate requests are supposed to end it.

5. **The promised inline human answer is rejected.** The spec allows a human answer to settle a non-gate request_decision, but R10 permits answer only when replying to ask. Correction: add the narrow human-answer exception for an open informational request_decision. Keep accept/reject choices as decision records.

6. **Replay tests contradict the replay contract.** R15 correctly returns the original result for an identical accepted op before checking rev. But the tests require a duplicate human rejection with stale rev to be rejected. Correction: separate two tests: same op and payload after revision changes returns the original result with no new effects; new op carrying an old expected revision rejects stale_rev. Otherwise the acceptance tests could force an implementation that breaks safe retries.

What is now settled: invocation-bound tokens address the stale-call problem; selected-run credentials and one final report provide the right enforcement mechanism; repository ownership, frozen profiles, consultation roles and external-operation IDs are materially improved.

I would not do another broad design round. Put these exact traces into the core tests, resolve the contradictory clauses alongside that code, then run the scripted proving exercise. This was a static review of the specification; the repository at this commit contains documents, so no implementation or tests were executed.
