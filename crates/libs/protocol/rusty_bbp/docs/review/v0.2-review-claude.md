# BBP v0.2 review (integrated lens)

## A. Verdict

**BUILD WITH CHANGES.** The core (append-only store, revision-bound approvals, execution tokens, runner as supervisor) is sound and the proving run is the right next step. But v0.2 leaves several holes in the state machine and rule ordering that would make the proving run fail or pass for the wrong reasons; all are small spec fixes, none require a rethink.

## B. Did v0.2 fix v0.1's problems?

Mostly yes: candidate replacement after review is now impossible (gating table plus turn end on submission), approvals are bound to exact revisions (R17), and the runner no longer depends on a turn. Two fixes are incomplete. Binding reports to candidates rather than turns means a report can land for a candidate at any time in `test`, `review` or `merge_gate`, but nothing stales verdicts when it does, so the evidence chain R3/R17 claims is only as good as the first report. The `approved`/`cancelled` and `changes_spec` additions created dead ends in the state machine (F2, F4) because `resumed` targets and the gating table were not updated to match.

## C. Findings

**F1** · blocking · Test report, R3, R17, Runner API
- issue: A new `test_report` for the current candidate does not stale verdicts or approvals, and R17 at `merge_gate` checks only "a Reviewer `approve` exists", not that the candidate's current report is `passed`. Runner writes are accepted in `test`, `review` and `merge_gate` with no token, and the moderator may re-trigger runs.
- failure scenario: Report A `passed`; Tester and Reviewer approve; task reaches `merge_gate`. Runner crash recovery re-triggers, report B `failed` is stored for the same candidate. Human approves. R17 passes: the Reviewer approve exists. The merged candidate has a failing current report.
- fix: Add to R17: the current report of the candidate is `passed`. Add: a `test_report_stored` for the current candidate stales verdicts on it and, in `review`/`merge_gate`, returns the task to `test`.

**F2** · blocking · Decision body, Task lifecycle, Artifact gating table
- issue: "A decision with `changes_spec` after plan approval returns the task to `plan_gate`", but `spec` may only be written in `planning`, and `human_approval` at `plan_gate` must name the spec in the triggering `request_decision`. Nobody can produce or approve a changed spec from `plan_gate`.
- failure scenario: In `build`, human decides `changes_spec`. Task enters `plan_gate`. Planner has no turn (gate states grant turns only to answer asks) and cannot store a spec anyway. Only `human_rejection` → `planning` escapes, which is a second human action to undo the first.
- fix: `changes_spec` moves the task to `planning`, and the approved spec is cleared so R17's `spec_mismatch` fires on the old candidate.

**F3** · blocking · R14, R15, Proving run
- issue: Rule evaluation order is unspecified. If R14 (live token) runs before R15 (idempotent replay), a replay after the turn ended gets `token_expired`, contradicting the proving-run requirement "a lost `post` response replayed safely".
- failure scenario: Coder's `put_artifact(candidate)` is accepted; the submission ends the turn (cause `candidate`) and kills the token. The response is lost. Coder retries with the same `op` and the now-dead token → `token_expired`. The agent believes submission failed.
- fix: State that `op` lookup precedes every other rule, and a matching accepted `op` returns the original result regardless of token state.

**F4** · blocking · Task lifecycle (`escalated`, `approved`), R11
- issue: Budget exhaustion or an expired `request_decision` moves any non-terminal state to `escalated`, but `resumed` targets are only `planning`, `build`, `test`, `review`. `merge_gate` and `approved` cannot be restored.
- failure scenario: Task in `approved`, human has merged but not yet recorded the receipt. Coder posts `ask` messages until `messages` is exhausted → `escalated`. Human resumes to `build`; `build` → `test` needs a new candidate, which increments `iteration`; the merged work must be re-submitted, re-tested, re-reviewed and re-approved, or `iterations` runs out and the task re-escalates. A merged change has no `merge_receipt` and the task can never reach `closed`.
- fix: `escalated` records the `from` state; `resumed` may target it. Also exempt `merge_gate` and `approved` from message-budget escalation (just reject).

**F5** · blocking · Candidate manifest, R4, Runner API
- issue: `repo` in the manifest is Coder-controlled and R4/R17 never compare it to the `task_opened` repo. The supervisor "checks out `base`" from it.
- failure scenario: Coder stores a manifest with `repo` set to a fork containing a `base` where the tests trivially pass. Runner checks out the fork, applies diffs, reports `passed`. Reviewer sees only diffs. Human approves a candidate for the wrong repository; the mismatch is only visible at merge time.
- fix: R17 adds `candidate.repo` equals the task's repo (`repo_mismatch`), or drop `repo` from the manifest and take it from the task.

**F6** · non-blocking · Capability matrix, Turns and tokens
- issue: Reviewer reads no messages but gate states "grant turns only to answer a human `ask`", and the Reviewer may `request_decision`. It can never see the ask or the answer.
- failure scenario: Reviewer requests a decision in `review`; human answers; Reviewer's next turn starts with no way to read the answer and posts `revise` on a guess.
- fix: Reviewer reads messages from `human` whose `to` includes `reviewer`.

**F7** · non-blocking · Turns and tokens (`yield_to`)
- issue: Whether the yielding role's token stays live during the yield is unspecified. If it does, two tokens are live, breaking "one turn at a time"; if not, the "return" needs a new `turn_granted` and deadline, which is not described. "Yields do not nest" has no rejection code.
- failure scenario: Coder yields to Tester; Coder's token remains valid; Coder stores a candidate while Tester is mid-turn; `candidate_submitted` moves state to `test` under the Tester, whose turn now has a stale premise.
- fix: `yield` ends the yielder's turn (`turn_ended(yield)`), and the return is a fresh `turn_granted`. A `pass` with `yield_to` during a yielded turn rejects with `yield_nested`.

**F8** · non-blocking · R11, Reads and visibility, Risks
- issue: Read budget resets per turn and the default schedule immediately regrants the same role, so a read-exhausted turn is a free restart. Each ranged `get_artifact` chunk is a read, so a large diff can exhaust 40 reads by itself.
- failure scenario: Reviewer reads a 2 MB diff in chunks, hits `turn_budget_exhausted`, gets a new turn, repeats. Nothing bounds this loop.
- fix: Charge one read per artifact id per turn, and add `turns` to the budget (escalate when exceeded). Also put the `rejections` cap on the card as a budget; the Risks table promises a cap that no rule defines.

**F9** · non-blocking · Task lifecycle (`escalated` → `test`), Recovery
- issue: `test` grants the Tester's turn only on `test_report_stored`, which already happened before escalation. Resuming to `test` grants nobody a turn.
- fix: On entry to `test` with a current report, the moderator grants the Tester's turn.

**F10** · non-blocking · Task lifecycle (`planning` → `plan_gate`), `request_decision` deadline
- issue: Any Planner `request_decision` whose `refs[0]` is a spec moves to `plan_gate`, including an ordinary question about the draft. And because the gate is triggered by a `request_decision` with its own deadline, a slow human sends the task to `escalated` from `plan_gate`, requiring a resume before approval.
- fix: Trigger on `to: ["human"]` plus a `gate: "plan"` body field; a gate-triggering `request_decision` carries no deadline.

**F11** · non-blocking · Task card
- issue: `turn.token` is on a card readable free by every role. R14's principal binding makes this harmless today, but it is a needless secret on a public record.
- fix: Card shows `turn.role` and `deadline` only; the host delivers the token privately as stated.

**F12** · non-blocking · Verdict body, R3
- issue: `revise` with an empty `blocking` list is accepted, so the Coder gets no actionable item. Also `escalate` as a verdict duplicates `request_decision`.
- fix: `revise` requires at least one `blocking` entry (`blocking_required`); cut `escalate` from verdict values.

## D. Open questions

- **Q1.** One report per run with `profiles: [{name, status, exit_code}]` and overall `status` = worst. Keeps R3 citing one artifact while exposing lint vs unit results.
- **Q2.** No waiver in v0.3; allow a human-triggered re-run (new report, which under F1's fix stales verdicts). A waiver would let Tester `approve` on a `failed` report, undoing R3.
- **Q3.** Set from the proving run; but reads must count artifact ids, not ranges (F8), or 40 is unusable for a Reviewer.
- **Q4.** Keep per-candidate until measured. It is the only structural defense against anchoring on the previous verdict and manifests make it cheap.
- **Q5.** No opinion.

## E. Missing pieces

- **Repository access for agents.** The Coder writes diffs against `base` and the Reviewer judges them, but BBP exposes only artifacts. Neither can read the tree. Say how the host provides a read-only checkout at `base` and that it is a host requirement.
- **Who runs tests the Coder wants to run.** The Coder cannot execute anything before submission; expect most iterations to be spent on compile errors. Consider a Coder-triggered dry run (report with `candidate: null`, not a submission) or accept the cost explicitly in Measurement.
- **Prompt injection via `log`.** Tester reads all artifacts, including raw runner output, which Coder-written tests control. The Risks row covers only the Reviewer.
- **Turn-grant signaling.** Pull-only agents need to learn they have a turn; "the host delivers the token" is the only hint. State the host contract.
- **Wall-clock task budget.** Turn deadlines exist; nothing bounds a task's total duration.

## F. What to cut

- **`attempt`.** Tokens already carry a deadline and die on `turn_ended`; attempts add a third counter (with iteration and turn), two events, and the phrase "does not spend an attempt" with no attempt budget to spend. Bind tokens to (task, principal, turn, deadline).
- **`escalate` verdict value** (F12).
- **`usage` event and `advisory.tokens`.** Host-reported, unenforceable; belongs in Measurement, not the protocol.
- **`to` field's rule R9.** Visibility is decided by role, so `to` is advisory routing; keep the field, drop the rule or label it advisory as the principles require.
- **Appendix B** can shrink to its two open questions.

## G. Top three changes

1. F1: current report must be `passed` at `merge_gate`, and a new report stales verdicts.
2. F2 and F4: fix the dead ends (`changes_spec` → `planning`; `resumed` may target the escalated-from state).
3. F3 and F5: specify `op` lookup before R14, and bind `candidate.repo` to the task.

## H. Confidence

Medium-high on the state machine, rule interaction and token findings; they follow from the document text alone. Medium on LLM practicality (iteration counts, Reviewer-without-tree) since nothing is measured yet. I could not assess the A2A/AG-UI/MCP positioning or the Delta claims in Appendix A; I relied on no facts about those systems, and the one check worth doing is whether MCP tool calls can carry a per-call `token` without the host adapter touching it, which the "adapters never re-stamp" requirement depends on.
