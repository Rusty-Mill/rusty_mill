# BBP v0.1 Review: ChatGPT

Source: ChatGPT, run by Nano in a fresh session on 2026-10-08 with `review/v0.1-review-prompt.txt`. Reproduced verbatim.

## A. Verdict
BUILD WITH CHANGES. v0.1 resolves several v0 problems, but its normal plan-to-build workflow still cannot execute consistently as written. The next revision needs a few precise contract corrections, rather than more roles, integrations or message kinds.

## B. Did it fix v0?
Yes: separating blobs from artifact records, stateless reads, typed verdicts, advisory token accounting and explicit host responsibility for fresh sessions are meaningful fixes. R16 now states the right idempotency guarantee. Candidate binding is improved, but plan approvals and implementation approvals have been conflated. Turn fencing and restricted-role input discovery remain incomplete. The new runner establishes provenance only if its trusted supervisor is isolated from the code it executes.

## C. Findings

**F1 — Blocking: the plan gate has nothing valid to approve.**
Section: Candidate manifest; Event; Task lifecycle; R18.
Issue: human_approval requires the current candidate, but planning produces a spec; a candidate is introduced only in Build.
Failure scenario: Planner proposes the spec and enters plan_gate. The human cannot supply the required candidate ID. Manufacturing an empty candidate would still leave its approval invalidated by the first real implementation candidate.
Fix: plan approval names an immutable plan/spec revision; merge approval names an implementation candidate. Each candidate must reference the approved plan. Replacing implementation invalidates candidate approvals, while changing the plan requires a new plan approval.

**F2 — Blocking: artifact submission bypasses the state machine.**
Section: Agent API → put_artifact; R5/R14/R17/R18.
Issue: put_artifact applies neither state nor turn checks, yet uploading a candidate changes the task's current candidate.
Failure scenario: while a human examines candidate A at merge_gate, Coder uploads B and makes it current. The listed rules also permit this after Closed.
Fix: distinguish storing an artifact from submitting it for execution. Candidate submission must atomically require Build, the active Coder turn and the approved plan. Define state permissions for each artifact-producing operation, including narrowly scoped Runner writes.

**F3 — Blocking: the "turn token" is not actually a token.**
Section: turn_granted; Attempts; Agent API; R14/R15.
Issue: turns identify a role, while the API exposes no turn or attempt identity. Attempts rotate only on timeout.
Failure scenario: Coder finishes one turn, but a delayed write arrives when Coder receives another turn in the same attempt. Both checks pass. An off-turn pass is also permitted even though pass ends a turn.
Fix: issue a unique execution token bound to task, principal, attempt, turn and deadline. Require it for every agent mutation, including pass, and invalidate it when that turn ends. An adapter must never stamp an old process's request with the new current generation.

**F4 — Blocking: the required test report is undiscoverable.**
Section: Candidate manifest; Reads; Runner; R3.
Issue: the candidate lists spec and diffs, but not later runner reports. Runner cannot post messages; task_card exposes no report ID; no listing operation exists.
Failure scenario: Runner finishes successfully, but Tester and Reviewer cannot discover the artifact R3 requires them to cite.
Fix: persist a report-ready event and expose candidate-scoped report IDs through the authorized task view. Make those inputs available before granting the dependent verdict turn.

**F5 — Blocking: runner identity is not an execution-security boundary.**
Section: Runner; Principals; Risks; R3/R17.
Issue: a worktree isolates edits, not the privileges of executed code. The statement that nothing the runner reads can instruct it is false: it deliberately executes submitted code.
Failure scenario: a changed test accesses an inherited BBP credential, supervisor socket or host file and fabricates trusted evidence or performs an unauthorized external action.
Fix: place a trusted supervisor outside the workload's sandbox. The workload receives no BBP, push or deploy credentials and cannot access supervisor state. The supervisor captures status and writes reports. State filesystem, environment and network restrictions as host requirements; merely removing origin credentials from a checkout is insufficient.

**F6 — Blocking: event replay loses budget state, and exhaustion can block recovery.**
Section: Event; Task card; R11; Human channel.
Issue: reads and rejected writes change counters, but no specified events reconstruct them. "Each write" being charged also appears to include the escalation required after exhaustion.
Failure scenario: rebuilding the task card loses read/rejection counters, or an exhausted budget prevents escalated/resumed from being recorded.
Fix: persist an atomic accounting ledger or accounting events and define how the card derives from them. Give necessary control operations independently bounded capacity. Explicitly scope agent assignment/turn checks so human responses do not require an agent turn. Resolve whether task_card consumes read budget.

**F7 — Blocking: R7's second signature does not approve the recorded decision.**
Section: Decision body; Verdict body; R7; Q2.
Issue: an approve verdict on a proposal authorizes a decision whose outcome and changes_spec can differ. Reviewer cannot read proposal messages; request_decision cannot be a verdict subject.
Failure scenario: another vendor approves proposal P, then Coder records reject or a different spec-change target while citing that approval. A genuine negative verdict cannot authorize rejection through the stated rule.
Fix: if keeping cross-vendor decisions, approve an immutable proposed-decision object containing the exact outcome and proposed change. The final decision must match it, and its evaluator must be able to read it. Any change to the human-approved plan must still return to the plan gate. Vendor diversity is corroboration, not a replacement for human authority.

**F8 — Blocking specification gap: nested references and task isolation need explicit validation.**
Section: Artifact records; Candidate manifest; get_artifact; R4.
Issue: R4 names message fields, but not candidate.spec, candidate.diffs or report.log. Kind-based access alone does not establish task access.
Failure scenario: a T1 candidate references a known T2 diff, or a T1 process requests that artifact directly.
Fix: validate every nested reference for expected kind and same-task ownership. Every tool must enforce the process's bound task and assignment. Do not expose raw blob reads that bypass artifact authorization.

**F9 — Non-blocking: distinguish event delivery from a live projection.**
Section: supersedes; Reads.
Failure scenario: m41 targets Coder; m42 supersedes it and targets Tester. Coder reads later and receives neither. Therefore live-only reads cannot promise delivery of every accepted message.
Fix: provide an append-only delivery feed with supersession notices; retain live-only results as a separate snapshot view. Also test that an idempotent retry returns its original success after that operation has ended the turn or changed state.

**F10 — Non-blocking, but correct the safety claims.**
Section: Test report; Task lifecycle; R18.
Issue: a candidate-bound report may say failed or error, and merge approval currently closes the task before any merge occurs.
Failure scenario: the patch fails to apply, agents approve its error report, and the task closes even if the human's subsequent merge fails or merges another revision.
Fix: define required run profiles and whether approval requires passed results or an explicit human waiver. Either define Closed as approved handoff, or close only after a merge receipt identifying the actual revision. R18 makes stale approvals rejectable inside BBP; it does not make an external wrong-revision merge impossible.

## D. Answers to Q1–Q6
- Q1: Route test changes through Coder initially. Tester proposes changes; the candidate remains one explicit composition.
- Q2: Use designated evaluators, not any agent. Bind their judgment to the complete decision object; defer this feature if it delays the proving run.
- Q3: Configure limits explicitly and measure. Define what counts, including duplicate writes, reads, rejected attempts and control operations, before choosing numbers.
- Q4: Initially no. First make candidate and runner evidence discoverable; later evaluate a clearly labeled candidate-scoped findings view.
- Q5: Require per-blob, per-task and read-response limits now. Define retention/deletion policy separately from append-only history while a task is active.
- Q6: Use a durable request deadline independent of turn duration. Waiting for a human should not consume an agent's execution lease.

## E. Missing pieces
Define permitted state transitions for control events, cancellation's resulting state, legal resume targets, and recovery after a runner or moderator crash. Pin repository identity, full base revision, ordered diffs and the resulting tree identity in execution/merge evidence. Include the configured test profile in the report.
The proving run should use deterministic human/Planner/Reviewer stubs where necessary. You cannot test stale human approval while deferring the human gate entirely.

## F. What to cut or qualify
Defer Delta integration from the normative protocol. Its current [thread documentation](https://delta.dev/docs/agents/threads) distinguishes fresh new threads from inherited subthreads/forks, so specify the exact launch mode rather than treating every route alike. A documented UI capability does not establish an automatable adapter contract.
Prefer "a freely writable replicated log alone cannot enforce these global admission rules" over a blanket dismissal of CRDT storage. Choosing one transactional authority is sufficient; BBP need not settle distributed-database theory.
Remove "drop any rule the proving run never exercises." Unexercised safety rules need adversarial tests; their absence from one successful task is not evidence they are unnecessary.

## G. First three changes
1. Separate plan authorization from candidate authorization.
2. Enforce real execution tokens and state permissions on artifact submission as well as messages.
3. Complete runner isolation, report discovery and durable accounting, then run the crash/retry/stale-approval tests.

## H. Confidence
High on the internal contradictions and concrete failure sequences. This is a static review; no implementation or interoperability tests exist. I verified the cited Delta thread documentation, but have not established a supported Delta automation API or independently verified every DeltaDB/security assertion in the draft.
