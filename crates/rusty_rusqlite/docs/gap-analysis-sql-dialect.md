# Gap analysis — rusty_-rusqlite vs. real SQLite's SQL dialect

Generated by the parity-loop process, this session's third pass. The first
two passes (`gap-analysis.md`, and this session's vtab epic + re-scan)
compared this crate against **`rusqlite`'s Rust API surface** — a
consuming library's method names. This pass compares against a different
reference: **real SQLite's own SQL query language** — the grammar this
crate's tokenizer/parser/engine (`src/token.rs`, `src/ddl.rs`,
`src/dml_insert.rs`, `src/dml_select.rs`, `src/eval.rs`, `src/engine.rs`)
actually accepts and executes, independent of what Rust methods wrap it.

**Reference pinned at:** SQLite's "Query Language Understood by SQLite"
grammar (sqlite.org/lang.html), as of this session (2026-08-16) — SQLite's
SQL dialect is stable/versioned by SQLite's own release, not `rusqlite`'s.

**Assessment path:** spec-extraction (no comparable Rust crate to diff
against — this is a grammar surface, not an API surface). A background
research pass read `src/ddl.rs`, `src/dml_insert.rs`, `src/dml_select.rs`,
`src/engine.rs`, `src/connection.rs`, `src/token.rs`, and `src/storage.rs`
directly and confirmed every "not supported" row below by grep (zero
matches repo-wide) rather than assumption — file:line citations are in
that research pass's findings, summarized here.

**RustyMill sibling check:** no sibling repo implements a SQL
parser/grammar (`rusty_db` remains the only namespace repo with an
adjacent purpose, and it's an ORM layer, not a grammar — same conclusion
as the original `gap-analysis.md`). Every row below is `none found`.

**Key finding, stated plainly:** this crate's SQL surface is narrower than
either earlier gap-analysis pass implied. Most strikingly, **`WHERE`
clauses cannot combine conditions at all** — no `AND`/`OR`/`NOT`, no
parenthesized grouping. `parse_comparison` parses exactly one `operand op
operand` and stops. This is more foundational than the previously-flagged
`UPDATE`/`DELETE`/`JOIN`/`IN`-subquery gaps (all of which were explicitly
called out as "separate, pre-existing gaps" at various points during this
session's vtab work) and wasn't itself named in any of those call-outs —
it surfaced only once this pass actually read the parser code rather than
inferring scope from what got mentioned in passing.

## Part 1 — Pure additions (implemented this pass, no architecture change)

Ordered roughly by foundational-ness / dependency. None of these touch an
existing public Rust signature — they add new AST variants, new parser
branches, and (for `UPDATE`/`DELETE`) new `Connection::execute` dispatch
arms, the same shape every prior `parity-gap` issue in this session has
taken.

| # | Feature | Category | Est. size | Notes |
| - | --- | --- | --- | --- |
| D1 | `WHERE` boolean combinators (`AND`/`OR`/`NOT`, parenthesized grouping) | fn/type | M | Currently: `parse_comparison` parses exactly one comparison and stops (`dml_select.rs:300-318`). No `Expr::And`/`Or`/`Not` variants exist. The single highest-priority gap in this pass — almost every other `WHERE`-using feature (`LIKE`, `BETWEEN`, `IN`, multi-condition filters) is more useful once this exists. |
| D2 | `LIKE`/`GLOB`/`BETWEEN` operators | fn/type | S | Keyword-based operators (unlike `=`/`<`/etc., which are punctuation) — `parse_comparison` only consumes punctuation as an operator today. New `Expr`/`BinaryOp`-adjacent variants + `eval.rs` semantics (`LIKE`'s `%`/`_` wildcards, `GLOB`'s `*`/`?`/`[...]`). |
| D3 | `IN` operator, literal-list form (`col IN (1, 2, 3)`) | fn/type | S | Pure expression addition — new `Expr::InList` variant, no subquery execution needed. `IN (SELECT ...)` (subquery form) is out of scope here — folded into the Subqueries new-subsystem item (S16) since it needs the same nested-query-execution capability. |
| D4 | `CASE WHEN ... THEN ... ELSE ... END` expressions | fn/type | S | New `Expr::Case` variant + `eval.rs` branch; no parser/engine-layer dependency beyond D1 (a `WHEN` condition is itself a boolean expression). |
| D5 | `DISTINCT` in `SELECT` | fn | S | Post-process the already-materialized row `Vec` for row-level dedup; no execution-model change. |
| D6 | `CREATE TABLE` constraint parsing: `UNIQUE`, `CHECK`, `DEFAULT`, `AUTOINCREMENT` | type | M | `is_column_constraint_keyword` (`ddl.rs:252-254`) hard-codes only `PRIMARY`/`NOT`. Parsing only — new `ColumnDef` fields. Enforcement is D7. |
| D7 | Constraint enforcement: `PRIMARY KEY`/`UNIQUE`/`NOT NULL`/`CHECK` at insert time | fn | M | Currently parsed-but-ignored (`PRIMARY KEY`/`NOT NULL`) or not even parseable (`UNIQUE`/`CHECK`, pending D6). Two rows with the same declared `PRIMARY KEY` value insert successfully today — a real correctness gap, not just a missing-feature one. **Behavior change, not an API break**: existing `execute()`/`create_module` calls' Rust signatures don't change, but code that was inserting constraint-violating rows will start seeing errors it didn't before. Documented plainly in `RELEASE_NOTES.md`, not gated as `breaking-change` (no public signature changes). |
| D8 | `CREATE TABLE IF NOT EXISTS` | fn | S | `storage.rs:113-116` always errors `TableAlreadyExists` on a name collision; needs a suppress-the-error path threaded through from the parser's `IF NOT EXISTS` flag. |
| D9 | `DROP TABLE [IF EXISTS]` | fn/type | S | Currently: `connection.rs`'s own test asserts this returns `UnrecognizedStatement`. New `DropTable` AST + `Database::drop_table` + dispatch arm. |
| D10 | `ALTER TABLE` (`ADD COLUMN`, `RENAME TO`, `RENAME COLUMN`) | fn/type | M | Real SQLite's `ALTER TABLE` is itself a narrow subset of general schema alteration (no `DROP COLUMN` until SQLite 3.35, no type/constraint changes) — matching that same narrow real-world subset, not inventing a broader one. |
| D11 | `CREATE INDEX`/`DROP INDEX` | fn/type | S | Scope cut, stated plainly: this engine's storage is a plain `HashMap`/`Vec` (`ARCHITECTURE.md`'s non-goal — no B-tree/page storage yet), so an index can't actually accelerate anything. Parsed and recorded as schema metadata only, same honest-inert-plumbing precedent `PRAGMA foreign_keys` already established — `CREATE INDEX`/`DROP INDEX` succeed, `sqlite_master`-equivalent introspection (if any exists) could list them, but every scan remains a full scan. |
| D12 | `INSERT OR REPLACE`/`OR IGNORE` conflict resolution | fn | S | `dml_insert.rs`'s `INSERT INTO` parsing is unconditional — no `OR`-clause branch. `OR ABORT`/`OR FAIL`/`OR ROLLBACK` deferred (see Part 3) — SQLite's default behavior already matches plain abort-on-conflict once D7 lands, so those three add no new behavior over the post-D7 default. |
| D13 | `INSERT ... SELECT` | fn | S | `dml_insert.rs:50` hard-requires `VALUES`; needs a branch that runs the nested `SELECT` (reusing `execute_select`, no new execution capability — the source rows are fully materialized before insertion, same "eager, not streaming" pattern `TableSource::scan` already uses) and inserts its output rows. |
| D14 | `GROUP BY`/`HAVING` | fn | L | Bigger than the others, but not a new subsystem — extends `execute_select_with_aggregates`'s existing whole-table aggregation path with a bucket-by-key step before aggregating, then a post-aggregation `HAVING` filter. Reuses `Aggregate`/`Value`/`Row` infrastructure already shipped for whole-table aggregates and window functions. |
| D15 | `UNION`/`INTERSECT`/`EXCEPT` (compound `SELECT`) | fn/type | M | Each side already executes via the existing `execute_select`; combining is a pure Rust-side `Vec<Vec<Value>>` operation (dedup for `UNION`/`INTERSECT`, set-difference for `EXCEPT`) — no new execution model. `UNION ALL` (no dedup) included. |
| D16 | `WITH` (non-recursive CTEs) | fn/type | M | Elegant fit for this crate's existing `TableSource`/virtual-table machinery (issue #90's abstraction): execute a CTE's `SELECT` once, materialize its rows, register the result as an ephemeral `TableSource` for the duration of the outer query, then let the existing single-table `FROM` resolution find it by the CTE's name. No new subsystem — a new *use* of an already-shipped one. `WITH RECURSIVE` deferred (see Part 3) — genuinely different execution shape (iterate to a fixed point), a separate concern from plain CTEs. |
| D17 | `UPDATE` (single table, `WHERE`-filtered) | fn/type | M | No parser/AST/dispatch exists at all today — confirmed by `hooks.rs`'s own `Action::Update` doc comment ("not yet reachable — no `UPDATE` statement exists yet"). Depends on D1 for a useful `WHERE` clause, but a trivial `UPDATE t SET a = 1` (no `WHERE`) doesn't strictly need it — sequenced after D1 anyway since almost every real-world `UPDATE` has a multi-condition `WHERE`. |
| D18 | `DELETE` (single table, `WHERE`-filtered) | fn/type | S | Same "doesn't exist at all" starting point as D17, `hooks.rs`'s `Action::Delete` doc comment confirms. Structurally simpler than `UPDATE` (no `SET` clause to parse) — sequenced right after it. |

## Part 2 — New-subsystem candidates (flagged, not implemented without sign-off)

Both of these change this crate's fundamental execution model, not just add
a new statement type. Filed as issues per the skill's own rule ("a
`new-subsystem` gap doesn't get to skip this step for being big"), but
**not implemented automatically** — see the loop's step 3.4 stop-and-ask.

| # | Feature | Why it's new-subsystem |
| - | --- | --- |
| S1 | `JOIN` (`INNER`/`LEFT`/`CROSS`, `ON`/`USING`) | `Select.table_name` is a single `String` (`dml_select.rs:75`) — the entire column-resolution path (`eval.rs`, `engine.rs`, `Database::scan`) assumes one table's schema in scope. A join needs: a `FROM`-clause table *list* with aliases, a join algorithm (nested-loop is the natural fit for this crate's in-memory model), and qualified column resolution (`t1.a` vs `t2.a`) threaded through every place `Expr::Column` is currently resolved against a single schema. This is a change to the core row-source abstraction the whole engine is built around, not an additive statement type. |
| S2 | Subqueries (scalar subquery in expression position; `IN (SELECT ...)`) | `Expr` has no variant that can trigger nested query execution, and `eval.rs` (expression evaluation) currently has no dependency on `engine.rs`/`Database` (deliberate layering — expressions are evaluated against already-fetched row data, not against the database itself). A subquery-capable `Expr` variant would need `eval.rs` to reach back into query execution, which is a real architectural boundary crossing, not a new leaf feature. |

## Part 3 — Explicitly deferred (not filed as issues this round)

Logged so scope trimming is visible, not silent (same convention the
original `gap-analysis.md` established):

- **`WITH RECURSIVE`** — plain `WITH` (D16) is in scope; recursive CTEs
  need iterate-to-a-fixed-point execution, a genuinely different shape
  worth its own future pass once plain `WITH` exists to build on.
- **`CREATE VIEW`/`DROP VIEW`** — closely related to CTEs (a view is a
  named, persistent, reusable subquery) but not itself asked for in this
  pass's scope; revisit once D16/S2 land and views become a thin layer on
  top.
- **`CREATE TRIGGER`** — a substantial standalone subsystem (event-driven
  execution hooked into `INSERT`/`UPDATE`/`DELETE`) that this pass's scope
  didn't name; not evaluated in depth here.
- **`INSERT OR ABORT`/`OR FAIL`/`OR ROLLBACK`** — SQLite's default
  conflict behavior already matches plain abort-on-conflict once D7
  (constraint enforcement) lands, so these three named modes add no new
  observable behavior over the post-D7 default; only `OR REPLACE`/`OR
  IGNORE` (D12) actually change behavior.
- **JSON1 functions** (`json_extract`, `json_array`, etc.) — an optional,
  compile-time extension even in real SQLite, not core dialect. Lower
  priority than anything in Part 1/2.
- **FTS5** (full-text search) — likewise optional/compile-time in real
  SQLite, *and* itself implemented as a virtual-table module — meaning
  it's a candidate for this crate's existing `vtab` machinery (issue #90's
  `TableSource` abstraction) rather than core-dialect work at all. Worth
  revisiting as a `vtab` example module (alongside `SeriesTab`/`CsvTab`/
  `ArrayTab` from issues #96/#97) rather than folding into this pass.
- **`ATTACH`/multi-database** — `ARCHITECTURE.md`'s existing non-goal
  (single implicit `"main"` database); unrelated to SQL-dialect coverage
  specifically, already a known deferred item from the original
  `gap-analysis.md`.
