# Changelog

All notable changes to this repo are documented here.
Format: Added / Changed / Deprecated / Removed / Fixed / Security, newest first.

## [Unreleased]
### Added
- Lens track records read `bbp why`'s D112 fields (#599): `Rule::Line.min_authors` is required, `Rule::Reopen` carries the items it woke, `Item.cites` (its artifact refs) replaces `executed`, `Change::Report` (a final holdout report on the current code) replaces `Change::Failing`, and `Rule::Line.holdout` names the report BBP found still valid at settlement. Golden truth is that report's golden profiles: failed means drop, passed means accept, and a job citing that report gets none from it. D92's four interim limits (unknown minimum, possibly woken items, withheld golden truth, executed evidence as a citation) are gone; `Wake` is removed. A history without `min_authors` is an error.
- Lens track records (#599, D92, D93). `orch-lens::record` scores each blind `Review` or `LookHarder` job on its claim's latest settlement (the latest status step that changed the status) at `±(1 + contested + 2·upset)`. A job whose own items decided the accept or drop line is pivotal: it is scored only against ground truth (a golden set failing on the candidate current at settlement), else unscored and counted. A `Human` or `Choose` settlement is never pivotal. `Tally` reports points, assigned, scored, pending, pivotal and pivotal-with-truth; `lens run` shows each lens `record: P points over N blind reviews (S scored, V pivotal)` once per pass, reading each claim through `bbp why --claim`, and logs a record it can't read.
- `orch-store`: `lens-records.mmap` (`rusty_orch::LensRecordRecord::v1`) holds one row per job, keyed by board, lens, claim, epoch and kind, with `save_lens_review` and `lens_reviews`. A row is saved before the scheduler state; saving the same job again unions its items and keeps `unsure` set, so a job rerun after a crash or a failed post keeps every item it posted, once. A job's row is first saved `pending` (serde default `false`) before its first post, or before an empty answer's or a refused reply's row, and cleared by the save after it; a write-ahead over a row still pending marks it `unsure`.
- Conservative limits until BBP's history carries more (OPEN_QUESTIONS Q35), each only adding unscored pivotal jobs: an unknown `min_authors` reads losing the lens as an author as pivotal; a human reopen into the settlement's epoch that may have woken an item makes every job on the line pivotal (an evidence reopen's item counts as live); golden truth is withheld on the `bbp why` path, which names no candidate; a job with executed evidence gets no golden truth; a job with a post whose answer was lost (`unsure`), or whose row is still `pending`, is never scored, and counts as pivotal on a line settlement.
- `rusty_orch lens run --alien` (off by default): after the ordinary passes, the config's `alien` lens hunts each eligible claim whose current candidate it has not hunted yet, and saves the hunt and probe rows that `lens alien report` reads (#708 slice 4c, D99). Eligible means irreversible (until #596's value score exists), every review lens's blind pass and owed look-harder recorded, and a candidate whose diffs touch `.rs`. It reads through its own `bbp mcp` session, posts nothing, and runs probes through `SandboxProbes`. A claim it can't hunt before any call (role refused, diff over `MAX_DIFF`, base not a full commit id, no cleared provider, or a candidate tree that can't be built, checked once before the first call) is one stderr line and is tried again next run; a ceiling ends the pass. Leftover probe trees are removed at start, a missing toolchain, repository or `alien` entry fails the run before any pass, and each task in `--state` is bound to one BBP directory. `orch-lens`: `LensConfig::alien` (`id`, `prompt`, CLI `providers`), `schedule::reviews_settled`, and `context::raw_prefix`, a prefix with no post protocol. `Session::candidate_diffs` now returns the candidate's base with its diffs (`Diffs::Read`).
- `rusty_orch::lens::probes::SandboxProbes`: the alien lens's probe runner (#708 slice 4d, D96, D97). Per probe it builds a scratch worktree of the candidate (base plus each diff), writes the probe to `tests/` of the crate its site names (matched by `[lib]` name for `crate::` sites), and runs `cargo test --offline` (build, then run) under `rusty_sandbox` with no network endpoints and a 10-minute limit per invocation; only a failing candidate is run again on base. A candidate timeout or kill is `BuildError`; a base timeout or kill is not run. Each tree has its own temp dir, `HOME` and cargo home, base never shares the candidate's build cache, the cache is emptied per hunt, and host-side writes refuse symlinks. `rusty_orch __sandbox` is the sandbox helper. `rusty_orch` now depends on the in-workspace `rusty_sandbox` and `rusty_worktree`.
- `rusty_orch::lens::bbp`: `Session::candidate_diffs(id)` reads a code candidate and then each of its diffs with `get_artifact`, in order, and returns each diff's text (#708 slice 4b, D98). Each artifact's first read is charged once to the lens principal (R11), never to the claim's budget. A role without `Read(Candidate)` or `Read(Diff)` gives `Diffs::Forbidden` and makes the claim ineligible. The refused read is free, but reads that succeeded before it were already charged. Any other failure is an error. `orch-lens`: `Card::current` is the claim's current candidate; `alien::touches_rs` decides Rust eligibility from a diff's header paths, including Git's quoted and escaped paths; `alien::MAX_DIFF` (128 KiB) is the largest diff a hunt runs on, and a larger one is skipped, never truncated.
- `orch-lens`: `call::ask_raw` asks a raw (non-post) question over a provider list, metered exactly as a job's call, and returns the settled cost and tokens; job and raw calls share one metering core. `hunt::hunt` runs one alien hunt: one enumerate call, the §5 ranking, at most 3 hunt calls, and each probe through a `Probes` port on the candidate and, when it fails there, on base. It returns a `HuntRow` and a `ProbeRow` per probe that ran; once the enumerate call is made the hunt is recorded whatever follows (#708 slice 4a, D78).
- `orch-lens::breaker` (#598): a pure cost breaker. A window closes at 40 calls or $5 and trips when no claim settled in it and the claims' scores moved less than 4 in total. `observe` (the default) reports a would-trip; `enforce` returns the detail for `bbp pause --reason breaker`. The lens config takes an optional `breaker {window_calls, window_usd, min_score_move, mode}` key. Nothing calls it yet.
- `orch-lens::taint` (#598): a post's class is raised to the highest class its lens's context admitted, and never lowered. `orch-store` keeps one taint table per BBP task in `taints.mmap` (`rusty_orch::TaintRecord::v1`). Nothing calls it yet.
- `rusty_orch lens run`: one `bbp mcp` session per lens, prefixes from the task brief, an optional rules file and each lens prompt, and the meter restored and saved in the orch state directory. It runs passes of one round per lens until a pass starts no job, a round halts, or `--max-passes` (default 20) is reached. The scheduler's memory does not survive the process yet.
- `orch-lens`: `post::protocol()` (the strict reply format and its limits, with an example that parses) closes every lens prefix, and `post::allowance()` tells each job what it may post, ahead of its suffix.
- `rusty_orch::lens::bbp`: one `bbp mcp` session per lens (D54). `Child` runs the session with credentials scrubbed and a 30-second deadline per request. `Session` reads new messages page by page for claim bodies and evidence notes, merges `claims_delta` cards, gives settled `claim_line`s, and posts as its lens with the brief ref and one op id per logical post (`lens-<run>-<n>`), resending a post lost in transport once under the same op. `orch-lens`: `Card::from_view` builds a card from a `ClaimView`, its body and notes.
- `orch-lens`: `round::round` runs one lens runner round: it schedules the board's cards, calls each job, posts a non-empty answer through the new `Board` port and records it. Provider failures are recorded and the round goes on; a task ceiling, an unsaved meter, a refused post or a missing lens prefix ends it with nothing recorded for that job. `Job` now carries the lens's `tools` and `Models::get` takes them; `State::abandon` drops a job uncounted.
- `orch-store`: `Store::save_meter`/`load_meter` keep one lens experiment meter per name in a new `meters.mmap` (`rusty_orch::MeterRecord::v1`); a name collision or a duplicated task is refused as corrupt. `orch-store` now depends on `orch-lens`.
- `orch-lens`: `Meter::snapshot`/`restore` (held reservations settle at their amount and count as calls after a crash) and `Meter::release`. `call` saves the meter after every reservation, before the provider is asked; an unsaved reservation is released and ends the job as `End::Unsaved`.
- `orch-lens`: `call::call` runs one lens job over its providers in fallback order. It fits the context to each window, reserves the worst case on the meter and caps output at `MAX_OUTPUT_TOKENS`. `Unavailable`, an unfit context and the experiment ceiling (paid only) pass to the next provider; `Permanent`, `Transient` and task ceilings end the job.
- `rusty_orch lens check <config> [--assertions <file>] [--repo <dir>]`: loads the lens config and the operator's assertions, builds every provider and reports which would be admitted, including an HTTP provider whose key variable is unset, without calling a model or inspecting a container.
- `rusty_orch::lens::container`: under a container clearance, every Codex lens question first inspects the container through the runner's local rootless podman (`--remote=false`, remote-engine variables removed). It requires the exact asserted mounts, a read-only machine-id from a file the runner cannot change, no privilege, devices, added capabilities, shared namespaces or API-key environment. Codex then runs via `podman exec` by the checked id.
- `rusty_orch::lens`: a `host_cleared` assertion may name the dedicated container a provider runs in, with its exact mounts. A machine-bound no-overage entry then counts only against the container's id, and a container clearance never grants Claude, which runs on the host. Codex stays unavailable under it until the container check lands.
- `orch-lens`: the lens runner's pure core: `Model` port, reply protocol, config checks, context assembly, data classes, tiering, money meter and scheduler (ADR-0021).
- `orch-openai`: one OpenAI-compatible chat completion over plain HTTP/1.1 to loopback and private addresses only, for llama-swap (ADR-0020).
### Changed
- `orch-lens`: `Board::post` fails with `PostError { posted, unsure, error }`, keeping the ids that landed before a failure; `round::Report.reviews` lists the round's blind jobs, including a refused reply (no items) and a job whose post failed partway (its landed items). Such a job, if anything landed or may have, counts as answered and isn't asked again, so no fresh evidence is posted beside it; with nothing landed it is abandoned and asked again as before. `round` takes a write-ahead port (`round::Ahead`) and halts with `Halt::Unsaved`, posting nothing, when it fails. The unused aligned/misaligned `record::Record` is replaced.
- `orch-codex`: a lens question takes its reply from the last completed `agent_message` in the `codex exec --json` events instead of a last-message file, so nothing is written to disk and Codex can run in a container. `CodexAgent::lens_argv` no longer takes a reply path. A missing, textless or blank final message is refused, never replaced by an earlier one.
- Providers are `AgentId` tokens instead of the closed `Agent` enum (ADR-0019). `orch-store` writes the id and reads the old variants; errors print the id (`codex`, not `Codex`).
### Fixed
- A lease now bounds the BBP validator profile's `read_roots` (ADR-0017): at freeze each must be a system root or within the lease, and not beneath a confined member's write root, and it is frozen as the path it resolved to. A leased profile with a toolchain outside the system roots now needs that path in the lease. Cancel freezes a never-frozen task unleased, so a pool the lease cannot confine no longer blocks it.
### Added
- Permission leases (ADR-0017): `Grant.lease` holds read/write paths and an end; delegation never widens it. The hosting configuration's `lease` is granted on each run's fence, and the BBP host confines every assigned pool member's sandbox to it, requires canonical lease paths, refuses swappable roots, a changed or ended lease, and passes the end to `bbp mod --deadline-unix`, enforced by each harness group's holder. Assignment records move to schema v2; v1 records still load as unleased.
- `run --cancel <reason>` cancels a hosted goal under a fresh generation through the new `TaskHost::cancel`, which finds each Implement card's BBP task without a checkpointed handle and waits until `bbp quiesce` finds nothing of it running, then reconciles the card's execution as cancelled and retires the assignment so the state cannot be resumed. BBP configuration gains `end_grace_secs`.
- Pool members can declare `sandbox: {read, write, env}`: BBP then runs their harness under `rusty_sandbox`, out of reach of the BBP directory, with MCP relayed to a broker outside the sandbox.
- A pool member's `sandbox` may set `checkout`: its harness then works in a git worktree of the BBP repository, sharing the object store read-only and writing only its own worktree.
- BBP configuration `slots` admits hosted work machine-wide: every moderator sharing the slot directory runs at most the configured agent harnesses and validator runners at once, and a slot is freed only when its process tree is gone.
- `run --card <id> --board <url>` records each hosted run's assignment generation with its Millboard card before any host command, through `card_execution_link` or the compare-and-set `card_execution_recover`, and stops when the card carries a later generation.
- Hosted commands carry an assignment fence: each `run` or `maintain` process takes over its assignment at the next generation, persisted first, and the BBP host refuses superseded generations and diverged holders.
- Provider-neutral factory assignments and durable card execution links, with
  aggregate delegation/call budgets and generation-fenced recovery.
- Windows inspection launch uses stdin for bundled source, retaining `-I`, deadlines and output bounds instead of exceeding the command-line limit.
- Cargo metadata revision fingerprints are deterministic across unordered Cargo collections while preserving meaningful graph, target, manifest and application-defined metadata changes.
- Stage 1 revision-bound proposed-change impact through `inspect --impact`, joining CI dependency evidence, Millboard ownership and complete RemindMe durable requirements; detects requirement revision changes and expands requirement-linked projects to their Cargo packages (ADR-0016).
- Opt-in `maintain` connects versioned repository findings to one sandboxed BBP task, with deterministic scope, durable recovery, human approvals, reverse-dependency validation and explicit draft PR publication (ADR-0015).
- Required CI evidence for pause/adoption across Orch processes; real deadline-ending launch-loop recovery coverage.
- Durable provider-neutral launcher failure pauses across Orch restarts, explicit owner reset, scoped MCP tool approvals and an LLD profile with bounded linker parallelism.
- Runnable Codex author/Claude reviewer BBP launchers in the host package, per-turn MCP contracts and an opt-in Linux real-provider smoke. Reviewer built-in tools are removed by fixed launcher arguments.
- Required Linux CI acceptance for the confined Orch CLI lifecycle, durable moderator restart and receipt-only completion, plus separately recorded timeout/cancel/kill recovery modes. Sandbox refusal cannot satisfy acceptance.
- Review fixes for hosted tasks: isolated work roots, replaceable bad answers, expired-request recovery, portable manifest publication, and owned runner cleanup before restart.
- Optional BBP TaskHost integration (#767): provider-neutral pools, frozen task rosters, durable open/adopt, unmetered resume, fenced human gates, moderator recovery and receipt-only completion.
- ADR-0013 (Proposed): BBP task host. An `Implement` card opens one Blackboard Protocol task through a new `TaskHost` port in `orch-dispatch` (`open`/`poll`/`relay`, `Progress::{Working,Gate,Closed,Cancelled}`, `Outcome::Waiting`); rusty_orch is the BBP human principal, gates surface as Board questions answered with `bbp human` verb lines, and the new `orch-bbp` crate drives the `bbp` CLI through `orch_cli::CommandRunner` (the layer check forbids linking `rusty_bbp_host`). Design only; no code in this change. Amended after design review: crash-recoverable open-or-adopt, gate fence persisted on the Board question, `bbp show` as the inspection contract, `approved` as a gate, decoded `Response` replies, a `Supervisor` seam for the detached moderator.
- `orch-claude` crate: `Agent::Claude` over `claude -p --output-format json --tools Read,Grep,Glob --permission-mode dontAsk --permission-prompts none --restricted --strict-mcp-config --setting-sources "" --disable-slash-commands --no-session-persistence --max-turns 20 [--model] --json-schema <schema>`, prompt on stdin, the repository root as working directory, the reply read from the envelope's `structured_output`, a `claude auth status` probe before each run mapped to the unavailable prerequisite, `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_BASE_URL`/`CLAUDE_CODE_USE_BEDROCK`/`CLAUDE_CODE_USE_VERTEX` scrubbed, login and rate-limit text told apart. `rusty_orch run` gains `--repo` (env `ORCH_REPO`; `--codex-repo`/`ORCH_CODEX_REPO` kept as aliases) and `--claude-model`; `Agents` serves `Agent::Claude`. Default routing unchanged. ADR-0012.
### Changed
- Docs: the Gemini CLI is discontinued; the planned Gemini adapter is dropped (README, ARCHITECTURE, AGENTS.md, ADR-0001 update, ADR-0012). `Agent::Gemini` is kept as a routing label so persisted records stay readable; no code change.
- `orch-cli`: `CommandRunner` gains the required `run_in(cwd, argv, stdin, timeout, remove_env)`; `run_scrubbed` and `run` are provided over it. `FakeCommand` records working directories. `output_schema(stop)` moves here from `orch-codex`, which re-exports it. In-family: `AgentsConfig.codex_repo` and `Args.codex_repo` are renamed `repo`, and both gain `claude_model`.
- `StopRule::BestEffort` now does what the goal contract promised: the adapters withdraw the `question` kind from Research, Triage, and Design cards, the prompt tells the agent that nobody will answer and to write an `assumption` entry stating what it takes as true before continuing, the parser rejects a question reply as a transient agent error, and Codex's output schema omits the `question` variant. The text report lists live assumptions in their own block. `CodexAgent`/`OllamaAgent::with_stop_rule` (default `Checkpoint`); `cli::run_with` builds the runner after the goal file is parsed while `cli::run` keeps its four arguments. Signature changes in-family: `orch_cli::allowed_kinds`/`format_spec`/`parse` take a `StopRule`, both adapters' `render` take one, and `orch_codex::output_schema(stop)` replaces `OUTPUT_SCHEMA`. `Checkpoint` output is byte-identical to before. ADR-0011; amends ADR-0004; resolves the ADR-0009 note.
- `orch-store` crate and `rusty_orch run --state <dir>` (env `RUSTY_ORCH_STATE`): the plan, board, and ledger of a goal are saved as one snapshot record in the embedded `rusty_multimodal_db_engine` after every dispatcher run and answer round, and a later run on the same directory and goal file resumes from them with the call counts intact. The snapshot is rebuilt through the domain's own constructors on load; a changed goal file is refused by fingerprint; one process holds a directory at a time; the wall clock stays per invocation. `orch-dispatch` gains the additive `Ledger::from_counts`. A partial answer round is checkpointed before an input error is reported. Failed replacements may recover a whole new aggregate with a preceding persisted revision, while failed initial inserts may reopen at generation 1; revision is not a count of successful save returns. Resumed ceilings cover persisted calls, not calls lost to abrupt termination. The snapshot format is positional bincode tagged `rusty_orch::GoalRecord::v1`; any layout change needs an explicit migrating reader or a new tag that rejects old files. `orch-store` is the family's one crate with registry dependencies (`serde`, and the engine's pins transitively); it and the `rusty_orch` binary declare `rust-version` 1.89. `run::execute` keeps its four-argument form and `run::execute_resumable` adds persistence; `Args::state` is a source change for external struct literals and new `RunError` variants are source changes for exhaustive matches. ADR-0010.
- `rusty_orch` binary crate: `rusty_orch run <goal.json> [--ollama-model] [--codex-repo] [--codex-model] [--interactive] [--json]`. Parses one JSON goal file (goal contract, human-authored tasks with index-based `depends_on`/`target`, optional routing) with `rusty_json`, runs it through the dispatcher over a composite of the Codex and Ollama adapters, enforces the wall-clock budget between runs, answers blocked questions from stdin when asked, and prints a text or JSON report. Std-only argument parsing. Exit codes 0/3/4/2/1. stdout carries only the report; questions and progress go to stderr, and a progress line is built only from fixed categories, ids, and counts, never from adapter or model error text; a blank answer stops the round without another model call. `routing` must be an object when present. `orch_cli::parse_ref` is now public. ADR-0009.
- `orch-cli` `render`: a `Role::Review` card now sees every live entry the reviewed task wrote, and the answers to them, under `UNDER REVIEW`, resolved at render time; authors no longer guess entry ids in review refs.
### Changed
- `orch-dispatch`: the additive `ClassifiedError` classification lets runners distinguish counted transient failures, counted permanent failures, and unmetered unavailable prerequisites without changing `AgentError(String)`. Missing Codex login now leaves the same card resumable without consuming `max_calls`; true permanent failures still fail it immediately. ADR-0008.
### Fixed
- Execution-link adoption no longer attempts an invalid persistence CAS for an
  identical replay; assignment replacement, ancestry, and grant validation now
  fail closed for stale descendants, cycles, duplicate IDs, and escalation.
- `orch-dispatch`: adapters now declare agent/role capability, so a routed but unsupported role fails its card once before call accounting or backend setup instead of consuming its retry budget (#440). ADR-0007.
- `orch-ollama` real-binary test asserts a per-run nonce appears in an entry body instead of merely a non-empty reply, matching `orch-codex` (#441).
- `orch-cli` `render`: explicit entry refs now follow supersession chains and show the newest live entry's id, kind, and body. Aliases of the same live entry are rendered once and are not repeated in card history (#439).
- `orch-cli` `render`: a card's own live entries and the answers to them are inlined, so a card resumed after a `Question` sees its `Answer` (#448).
### Added
- `orch-cli` crate: the CLI-adapter core extracted from `orch-ollama` (process seam, JSON reply parser, prompt core with a per-adapter footer, `fake` test doubles). `CommandRunner::run_scrubbed` removes named variables from the child environment. ADR-0004 amended.
- `orch-codex` crate: `Agent::Codex` over `codex exec --sandbox read-only --ephemeral --ignore-user-config --ignore-rules -C <root> --output-schema --output-last-message -`, strict `anyOf` output schema, prompt on stdin, `OPENAI_API_KEY` scrubbed, `not logged in` and `rate limited` told apart by stderr. `research_review` example (Codex researches, Local reviews). ADR-0006.
- `orch-cli`: the `review` kind for `Role::Review` cards (`verdict`: approve or changes_requested; exactly one per reply). Shared `excerpt` helper.
### Changed

- `orch-core`: an agent-authored `Decision` must cite a live approving `Review` by a different author; self-approval is rejected with the existing `DecisionNeedsApproval`. ADR-0005 updated.
- `orch-ollama`: `StdCommand` spawns the child as a process-group leader and kills the whole group (unix `kill -KILL -- -<pgid>`, Windows `taskkill /T /F`) on timeout or overflow; pipe threads are joined for at most `JOIN_GRACE` (2s) and detached otherwise, so the deadline is a hard bound. ADR-0004 updated.
- `orch-core`: `Board::append` refuses an agent-authored `Decision` unless a ref points at a live approving `Review`; new `BoardError::DecisionNeedsApproval`. Applies to supersessions. ADR-0005.
