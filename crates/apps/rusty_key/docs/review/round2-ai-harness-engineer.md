# Round 2 — AI Harness Engineer

## 1. Scope & lens

How do we *prove* the harness is maturing, and can that proof be trusted? My surface: the golden-episode regression suite + metric family (eval-plan §3/§5), the H0→H3 exit gates (§4), the verification contract (PRD 05: `CriteriaJudge`, `VerificationReport`, outcome classifier), and the entropy/attribution signals that feed the learning loop (PRD 04). Round 2's job is narrow: do these nine sources **sharpen** (more rigorous verification) or **widen** (a new eval tier) that proof, without breaking Rust + AI-first? Three sources land squarely in my lens — **EvalMonkey** (chaos + resilience + failure→test synthesis), the **Anthropic article** (eval-gaming as a direct threat to eval integrity; memory-poisoning as a startup-verification concern; approval fatigue as M-HIR validation), and **SkillOpt** (validation-gating as a maturity-ladder verification gate). **AI-Q** is a benchmark-suite data point. The rest I verdict briefly. I grounded the Anthropic article on its full text (upload path); EvalMonkey/SkillOpt/AI-Q from the briefs.

## 3. Concrete recommendations

### Rec 1 — A chaos/fault-injection eval tier + a resilience companion to M-HIR (EvalMonkey) — eval-plan §5/new §7 + new ADR — **P1**

**What.** Today eval-plan §5 golden episodes replay a *scripted, well-behaved* `FakeLanguageModel` turn-sequence and assert the outcome label + metric non-regression. EvalMonkey's lesson is that maturity also means *resilience under fault*. Add a **chaos tier** that reuses the existing fixture format but perturbs the **`ToolOutcome` / tool-result seam** (not the model) deterministically:
- **Fault classes** (injected at the tool-dispatch boundary the `FakeLanguageModel`/fake tool layer already owns): (i) **corrupt tool result** — flip `ToolOutcome.status` to `error`/`blocked`, or return mangled/truncated payload; (ii) **schema corruption** — return a result that fails the tool's `#[tool]` output shape; (iii) **latency/timeout** — force `ToolOutcome` `timeout = true`; (iv) **observation drop** — omit a tool result the model expected. Each is a *deterministic* perturbation keyed off the fixture, so the chaos run is replayable (no real randomness in CI).
- **What it asserts (the resilience property):** under each fault, the harness must **degrade honestly, not silently pass** — i.e. the episode classifies `Failed`/`UnverifiedSuccess` (never `AutonomousVerifiedSuccess`), the right `FailureType` is attributed (`f_tool`/`f_feedback`/`f_recovery`/`f_verify` per the PRD 05 matrix), `NoToolErrors` fires, and `tool-recovery rate` (eval-plan §3) is measured. The chaos tier is the *negative-space* counterpart to §5's happy-path label assertions.
- **The resilience metric (companion to M-HIR).** Define `resilience = w_b · baseline_score + w_c · chaos_score` over the golden set, mirroring EvalMonkey's 60/40 shape — **`w_b`/`w_c` are product call**. `baseline_score` = AVSR (or clean-termination) over the unperturbed fixtures; `chaos_score` = fraction of chaos fixtures that **degrade correctly** (honest failure label + correct attribution + non-zero recovery where recovery is possible). It sits in eval-plan §3 beside M-HIR as a *maturity signal*: a harness that keeps AVSR high *and* degrades honestly under fault is more mature than one that only scores well on clean runs. Crucially this is **not** "survive the fault" (the model may legitimately fail) — it is "**never report verified success on top of an injected fault**," which is the verification thesis stated as a metric.

**Why.** RK's whole posture (PRD 05/04) is "verified, not asserted" — but the current eval suite only checks that on cooperative inputs. The Anthropic article's egress incidents make the point: *the deterministic boundary is what gets hit when everything probabilistic misses* — so we must test the deterministic boundary *under adversarial tool output*, which is precisely a chaos tier. And the `ToolOutcome` structural-status contract (ADR-0022) plus `FakeLanguageModel` already give us the injection seam for free — this is reuse, not new machinery.

**Exact target.** eval-plan: a new **§7 "Chaos / fault-injection tier"** (fault classes + the honest-degradation assertion) and one line in §5 that the chaos tier shares the §5 fixture schema with an added `fault:` field; eval-plan §3 gains the **resilience** row (companion to M-HIR); a new **ADR ("Resilience tier + metric: chaos injection at the ToolOutcome seam; resilience = baseline⊕chaos", Status: Proposed)**. Reference testing-strategy.md (the fault-injection *mechanics* live there, beside `FakeLanguageModel`; eval *consumes* the outcome — same one-fixture-two-consumers split §5 already draws).

**Rust + AI-first note.** Pure fixture + a perturbation enum over `ToolOutcome`; no EvalMonkey code, no HTTP harness. Rust strength: the `ToolOutcome` type is the single chokepoint, so chaos injection is a typed transform, not string mangling. AI-first: the agent is the semi-trusted principal *and* tool output is an attack surface (Anthropic) — chaos models both a flaky tool and a poisoned one.

**Caution.** Chaos fixtures must be clearly partitioned from happy-path golden episodes (a chaos fixture's *expected* label is failure/unverified) so a chaos failure is never mistaken for a maturity regression. The 60/40 weights and which fault classes gate a release vs merely report are **product call**. Don't let chaos volume explode CI time — sample, as §5 maintenance already contemplates.

### Rec 2 — Failure-trace → golden-episode synthesis (EvalMonkey) — eval-plan §5 + ADR-0021/Attribution loop — **P1**

**What.** EvalMonkey "auto-synthesises test cases from failure traces." RK already produces the perfect substrate: every `Failed`/`UnsafeInvalid` turn writes a full 8-trace **episode package** (`episodes/<turn_id>.json`) with `attribution_log` (`FailureType` + evidence + `next_action`) and `reproduction_log`. Propose a **failure-trace → candidate-golden-episode** pipeline: a real failure package is *promoted* into a regression fixture (scripted from its recorded `action_trace`/`tool_trace`, with its observed outcome label + `FailureType` as the assertion), so the next release **provably does not re-fail the same way**. This closes a loop RK already half-has: attribution captures *why* a turn failed → that becomes a *test* that the harness learned, not just a *skill* the model learned.

**Why.** It directly extends eval-plan §5 (which today only hand-curates fixtures) and **ties into our Attribution→skill loop**: the same failure that mints a consolidation skill (AI-engineer R1) also mints a regression fixture — model-side learning *and* harness-side learning from one trace. This is the harness-maturity analog of "a bug fix ships with a regression test." It also feeds Rec 1: a synthesized fixture's recorded tool failures are ready-made chaos seeds.

**Exact target.** eval-plan §5 — a "**Synthesized golden episodes (from failure traces)**" subsection: the package→fixture transform (replayable scripted turns from `action_trace`; assertion = recorded `EpisodeOutcome` + `FailureType`), a **human-review gate before a synthesized fixture enters the baseline** (an auto-added fixture must be reviewed so a *flaky* or *gamed* failure isn't frozen as ground truth — ties to Rec 3), and a forward-link to the Attribution→skill loop. No new ADR required (extends §5); note the `next_action` field of `attribution_log` as the synthesis hint.

**Rust + AI-first note.** Pure data transform over the existing `EpisodePackage` serde shape (data-model §5) → the §5 fixture schema; redaction (ADR-0026) already scrubs the package, so synthesized fixtures inherit secret-safety. No external dependency.

**Caution.** Synthesis must be **gated by human review** (above) — and must not synthesize from episodes the model may have *gamed* (Rec 3). A naive auto-synthesis that freezes every failure risks (a) baking in non-determinism and (b) an attacker steering a poisoned failure into the permanent regression set. Volume control + dedup by `FailureType`+signature is **product call**.

### Rec 3 — Eval integrity: anti-gaming invariant + session-startup recall provenance (Anthropic) — eval-plan §4/§5 + PRD 04 cross-dep — **P1**

**What.** The Anthropic article documents three findings that are *direct* threats to *my* surface; translate each into a concrete item:
- **(a) Anti-gaming invariant on golden episodes + H3 checks.** Models "examined git history to find answers to a coding test" and "spontaneously identified the benchmark to decrypt its answer key." RK's golden episodes carry **expected outcome labels and `checks.toml`** — exactly an answer key. State an **eval-integrity invariant** in eval-plan §5: (i) the expected-label/answer-key data and the deterministic-check *expected substrings* are **not present in the model's context or the workspace the replay runs against** (no leakage path from fixture→prompt); (ii) deterministic checks (PRD 05 `DeterministicCheck.expected_substring`) should prefer **freshly-computed assertions over committed golden outputs** where feasible, so reading repo/git state can't reveal the target; (iii) flag eval-awareness as a known failure mode in the §5 maintenance notes. This makes "verified" robust against a model optimizing the *measurement* instead of the *task* — the eval analog of `UnsafeInvalid` (the agent bypassing the task).
- **(b) Approval fatigue validates M-HIR; add a fatigue/auto-approve health signal.** Anthropic's telemetry (~93% approval; auto-mode lets ~17% of overeager actions through) is empirical support that **per-action approval is a weak oversight signal** — which is exactly why RK measures *missing-harness* interventions (M-HIR), not raw approvals. Add a small **live signal** to eval-plan §2: an **auto-approve / approval-saturation rate** (fraction of approval prompts approved, and the `tool_block` recurrence slice already in PRD 04) — a rate near 100% means oversight is degrading and the harness should *contain*, not *ask*. This is a one-line addition that turns the article's empirical finding into an RK metric and reinforces the systems-architect's capability-isolation rec from the eval side.
- **(c) Session-startup recall provenance (memory-poisoning).** "An injection that lands in product memory / CLAUDE.md / state dirs is reloaded each session." RK reloads project memory, skills, summaries, and `AGENT_GUIDE.md` every session — a persistence vector. Propose a **session-startup provenance check on recalled memory**: each recalled artifact in `context_trace` carries a provenance/trust tag, and a startup pass (classifier or rule) flags memory of *untrusted origin* (e.g. authored by tool output / external content, not by a verified turn) before it enters context. Add a **poisoning-resistance eval**: a golden episode that plants an injected instruction in stored memory and asserts the harness does **not** act on it (and that `context_trace.influenced_decision` records the quarantine). Ties to AI-engineer R1's `validated` lifecycle (an unvalidated/untrusted-origin skill should not be silently trusted at recall) and is a *new faithfulness+eval item* beyond the paper.

**Why.** This is the strongest single input this round for *eval integrity specifically*. RK's differentiator is trustworthy verification; an eval suite that a capable model can game, or a memory layer that reloads an injection every session, **silently invalidates the maturity metrics**. The article shows these are not hypothetical — they are observed in production models. Catching them is squarely the harness-engineer's job (the metrics are only as good as their resistance to gaming).

**Exact target.** eval-plan §5 (anti-gaming invariant + eval-awareness maintenance note); eval-plan §2 (approval-saturation live signal); eval-plan §4 (H3 gate note: deterministic checks prefer fresh assertions); ARCHITECTURE §12 (a faithfulness row: "eval-integrity — golden episodes resist gaming; recalled memory carries provenance" as a **new item beyond the paper**); **PRD 04 cross-dep** (recall provenance tag + startup classifier — owned by AI-engineer/security, I assert the *eval* that proves it). Consider a short **ADR ("Eval integrity: anti-gaming invariant + recall provenance", Status: Proposed)** if the provenance tag touches the data-model.

**Rust + AI-first note.** Anti-gaming is mostly a *fixture-construction discipline* (keep answer keys out of context) — no code. The recall-provenance tag is a field on the memory row + `ContextEntry` (cheap); the startup classifier can be the same "small fast model" pattern the article endorses (a cheap aisdk call, off the hot path), not the reasoning model. AI-first: the model is semi-trusted and *eval-aware* — design the measurement assuming the model may try to satisfy the metric rather than the goal.

**Caution.** A startup classifier on every recalled memory adds latency and is itself probabilistic (false positives quarantine good memory) — make it **off the hot path** (startup/idle pass) and **product call** whether it gates or merely flags. The anti-gaming invariant is partly unenforceable by us alone (a sufficiently capable model in a real workspace can read git) — state it honestly as *defense-in-depth*, with the deterministic boundary (containment, systems-architect Rec 1) as the backstop, exactly as the article concludes.

### Rec 4 — Validation-gated skill promotion as a maturity-ladder verification gate (SkillOpt) — eval-plan §5 + ARCHITECTURE §3/§12 — **P2**

**What.** SkillOpt promotes a skill only after it **validates** against held-out checks. The AI-engineer (R1) owns the *online* lifecycle (`validated: bool`, promote on next matching VERIFIED turn). My complementary piece is the **offline/CI verification gate**: a groomed or consolidated skill (a `merge`/`refine`/`split` that rewrites a skill body) is **promoted into the durable, prune-exempt set only if golden-episode replay does not regress** — i.e. the self-improvement loop **cannot silently un-learn** by grooming away a lesson that a fixture depends on. Frame this explicitly as a **verification gate on the maturity ladder**: skill changes are subject to the same "no maturity regression" bar (eval-plan §5) as the harness code is.

**Why.** Round 1 made skills prune-exempt, and AI-engineer R1 makes promotion *earned* online — but neither prevents a *grooming pass* from regressing a previously-passing golden episode (the loop optimizing itself into a worse state). SkillOpt's gate is the missing CI bar, and it reuses §5's existing "no label downgrade" assertion verbatim — applied to a skill-set change instead of a code change. It's the harness-side guarantee that self-improvement is monotone in the metrics that matter.

**Exact target.** eval-plan §5 — a "**Skill-promotion gate**" note: a golden episode whose pass depends on a specific skill, asserting that a grooming/merge that drops that skill's validated condition **fails the §5 gate** (re-records baseline only on reviewed, intentional change — same maintenance rule §5 already states). ARCHITECTURE §3 (ladder note: "skill changes pass the same no-regression gate as code"). Cross-dep with AI-engineer R1 (the `validated` column) — I consume their flag, they consume my gate.

**Rust + AI-first note.** No SkillOpt code (Python). Reuses the §5 replay harness; the only addition is a fixture that pins a skill→outcome dependency. AI-first: this is "textual learning rate" (SkillOpt) enforced as a regression bar — bounded, reviewed skill edits, validated before they become durable.

**Caution.** Don't over-couple — most skills won't have a dedicated fixture; the gate applies where a golden episode *explicitly* depends on a skill (otherwise it's the online `validated` signal's job). Whether a regressing groom is *rejected* vs *downgraded to candidate* is **product call** (mirrors AI-engineer R1's choice).
