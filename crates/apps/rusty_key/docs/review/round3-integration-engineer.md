# Round 3 — Integration Engineer

## 1. Scope & method

The paper's central output artifact is the **episode package**: "an auditable record containing eight trace types plus a patch, a verification report, a final report, and a final-outcome record" (p.8–9, Fig 3; Table 4 enumerates the eight). The eight classes (p.2, line 83): **action, tool, context, verification, failure-attribution, intervention, entropy, outcome**. RK promises all eight in the `EpisodePackage` struct ([PRD 05](../prd/05-compose.md) §"EpisodePackage (versioned; all eight traces)") and the on-disk JSON ([data-model §5](../architecture/data-model.md#5-episode-package--episodesturn_idjson-h3-prd-05)). The schema is complete. **My question is narrower than the schema: for each declared trace, is there a named RK component that *produces* it, with the fields the metric family ([eval-plan §3](../dev/eval-plan.md)) reads?** A field that appears in the JSON but has no emitter is not captured evidence — it is a hole the H3 completeness gate ([eval-plan §4](../dev/eval-plan.md)) will trip on.

I traced each class from paper → schema → producing component → emit path (`EvidenceJournal::record_episode` → `episodes/<turn_id>.json`). The result is one solid divergence (already ADR-pinned), two **genuinely unproduced** classes, and two **partially-produced** ones where the struct exists but the producer is unspecified. MCP I assess separately (§5).

## 3. The two unproduced classes (P0 — these break the H3 completeness gate)

### 3a. `action_trace` has no emitter — and it is not a synonym for `tool_trace`

This is the headline finding. The paper is explicit that the **action trace** and the **tool trace** are *distinct* classes capturing *different* resources: the action trace records "externally meaningful operations such as `read_file`, `edit_file`, `run_tool`, `write_report`, `update_task_state`, `inspect_diff`, and `declare_complete`" and "captures externally meaningful operations rather than every token of internal reasoning" (p.9 §Trace schemas; p.14 §Trace recording). The tool trace separately "records every command invocation with exit code, duration, timeout status, and recovery status" (p.14). In Table 4 they map to *different* runtime resources (action → "all / overall episode coherence"; tool → "tool budget; test-time compute") and *different* failure types.

RK conflates them. The only producer in the observe layer is the `Tracer`, whose `Episode` holds **`tool_events: Vec<ToolEvent>`** and nothing else (PRD 04 §"What it captures"). The kernel `on_event` hook feeds it exactly two event shapes — a tool call (`name`, `args`, `status`, `result`) and a turn/final marker (PRD 01 §Observability). So:

- **`run_tool`** maps onto a `ToolEvent` — fine.
- **`update_task_state`** (the agent calling `set_task`/`complete_task`) *is* a tool call in RK ([PRD 03](../prd/03-feed.md) §"Memory tools"), so it lands in `tool_events` — but as a generic tool event, not as a distinct action class.
- **`write_report`** (`verification_report` tool), **`declare_complete`** (`complete_task`), and **`inspect_diff`** are likewise tool calls — but the paper's *point* is that the action trace is the **episode-coherence spine** abstracted *above* the raw tool log, the thing an auditor reads to see "what the agent did" without wading through every `read_file`. RK has no component that projects `tool_events` into that ordered `ActionEvent` spine, and `ActionEvent` itself is referenced (`Vec<ActionEvent>`, PRD 05 line 379) but **never defined as a struct anywhere** — unlike `ContextEntry` and `ToolEvent`, which are.

**Why it matters (integration lens):** the H3 gate asserts `action_trace` is "present and well-formed" (eval-plan §4). With no producer and no struct, an H3 episode package either ships an empty `action_trace: []` (fails completeness) or — worse — someone wires it as a copy of `tool_trace` and the package *looks* complete while the paper's distinction is silently lost. The paper's whole "episode coherence" diagnostic (Table 4 row 1) evaporates. **Recommendation:** name the producer. The cleanest seam is in `compose` at package-assembly time: a small `action_trace` projector that walks `episode.tool_events` (in order) and maps each to an `ActionEvent { op, target, ts }` over the fixed paper vocabulary (`read_file | edit_file | run_tool | write_report | update_task_state | inspect_diff | declare_complete`), classifying by tool name. Define `ActionEvent` in `observe` beside `ToolEvent`. This is doc-only now (PRD 04 §Tracer + PRD 05 §EpisodePackage), ~15 lines of spec, and it removes the largest fidelity hole in the pipeline.

### 3b. `context_trace` has no emitter — `orient()` returns a string, not `ContextEntry`s

The **context trace** "records which project memory artifacts were consulted, what they contributed, and whether the contribution influenced agent decisions" (p.9). It is the trace the paper leans on hardest in the Implications: "Memory is auditable only when its use is traced … The context trace records which memory artifact was consulted, what it contributed, and whether it influenced a decision. This converts project memory from an invisible prompt ingredient into an analyzable runtime resource" (p.12). RK's `ContextEntry { artifact, contribution, influenced_decision }` is correctly modelled (PRD 05 line 392; data-model §5) and is read by **two** metrics — context-trace meaningfulness (eval-plan §3) and the recall hit-rate proxy / H2 cross-session-recall gate (eval-plan §2/§4).

But the producer — the feed layer's `orient()` / `recall()` — returns a **plain `String`** (PRD 03 §"Context assembly": `pub async fn orient(&self, history) -> String`; `recall()` likewise returns the rendered `## Relevant memory` block). Nowhere does feed emit structured `ContextEntry` records. The `(why: "<query frag>")` annotation in the recall output block (PRD 03 §"Output block") is the *raw material* for `contribution`, but it is baked into prose, not a struct. And critically, **`influenced_decision` is unknowable at orient time** — orient runs *before* the kernel; whether a recalled memory actually changed the agent's behaviour is a *post-hoc* judgement the paper assigns to the trace, and RK has no component that makes it. ARCHITECTURE §12 flags `context_trace` as "now added" (to the schema), but adding the *field* is not adding the *producer* — the same trap as 3a.

**Why it matters:** the H2 maturity gate is literally defined as "Cross-session recall surfaces the planted fact ≥ X% … recalled and used — `context_trace.influenced_decision` — in session B" (eval-plan §4). If `influenced_decision` is never produced, the H2 gate is unmeasurable and H2 cannot be certified — a load-bearing rung of the ladder. **Recommendation (two-part seam):** (1) have `recall()` additionally return a `Vec<ContextEntry>` alongside the rendered string (each scored candidate that made the top-k becomes an entry with `contribution = primary|supporting`, derived from the score tier it already computes); `orient()` threads it to `Session`. (2) For `influenced_decision`, pin a v1-honest heuristic and a seam: v1 sets `influenced_decision` by lexical overlap between the recalled artifact and the agent's action_trace/reply (cheap, off hot path), with the LLM-judged version as a documented future fill (the same "small fast model" pattern Round 2 R2 already pinned for return-value inspection). Mark `unused` contributions explicitly so meaningfulness can be computed as the paper intends. Target: PRD 03 §Recall/§"Context assembly" + PRD 05 §EpisodePackage.

## 4. The two partial classes (P1 — struct exists, producer underspecified)

### 4a. `tool_trace` is missing `exit_code`, `timeout`, and `recovered`

The paper's tool trace "records the command, the exit code, the duration, the timeout status, the failure type, and whether the agent recovered" (p.9; reinforced p.14). RK's on-disk `tool_trace` element claims exactly these — `{"name","status","exit_code","duration_ms","timeout","recovered","result"}` (data-model §5; PRD 05 line 380). But the **producing** struct, `ToolEvent` in PRD 04, has only four fields: `name`, `args`, `outcome`, `duration_ms`. So:

- **`exit_code`** — `bash` knows it (PRD 03: "Non-zero exit code: `ERROR (exit {code})`") but it is *formatted into a string*, not carried structurally. No field on `ToolEvent` holds it.
- **`timeout`** — likewise folded into a `"TIMEOUT: …"` string (PRD 03 §Shell tool). ADR-0022's `ToolStatus` is `ok | error | blocked` (data-model §7) — **there is no `Timeout` status**, even though PRD 03's `ToolFn` doc-comment and the `AiSdkTool` adapter both claim `ToolOutcome` carries `Ok | Error | Blocked | Timeout | Truncated`. That is an internal contradiction: the serde enum (data-model §7, the SSOT) lists three; PRD 03 lists five. Timeout currently collapses into `error`, so the dedicated `timeout` bool in the package has no distinct source.
- **`recovered`** — **nothing produces this at all.** "Whether the agent recovered" is a cross-event judgement (did a later step succeed after this one failed?), and no component computes it. Yet the **tool-recovery rate** metric is defined directly on it: `count(tool calls with recovered == true) / count(failed tool calls)` (eval-plan §3), and it is one of the paper's named metrics (p.10). Unproduced field → dead metric.

**Why it matters:** these three are precisely the fields that make tool *stability* "an analyzable runtime resource rather than an incidental engineering nuisance" (p.12–13 §"Tool stability is a harness problem") — the paper's repoA case hinges on the full-regression *timeout* being surfaced, not hidden (p.11 §"What the case reveals", obs. 2). **Recommendation:** (1) add `exit_code: Option<i32>` and `timeout: bool` to `ToolEvent` in PRD 04, sourced structurally from the `bash`/tool boundary, not parsed from the result string (this is the same "status is structural, not sniffed" discipline ADR-0022 already mandates — extend it to exit/timeout). (2) Resolve the 3-vs-5 `ToolStatus` contradiction: either add `Timeout`/`Truncated` to the data-model §7 enum (preferred — it is the SSOT and PRD 03 already assumes them) or strike them from PRD 03. (3) `recovered` is a derived field — produce it in the same `compose` package-assembly projector proposed in 3a: walk the ordered events, mark a failed `ToolEvent` `recovered = true` iff a later event on the same tool/target succeeds within the episode. Document it as derived-at-assembly so it is owned somewhere.

### 4b. `verification_trace` has no `CheckResult → VerifyEntry` producer

The verification trace "records the type of verification attempted (bug reproduction; deterministic behavioral check; registered test; targeted test; full regression; lint; patch review; manual evaluator check), the method, the result, the requirements covered, and the agent's interpretation" (p.9). RK models `VerifyEntry { type, method, result, covers[], interpretation }` and pins the eight-member `method` vocabulary correctly (data-model §5; PRD 05 line 405) — this is good fidelity on the *shape*. The producers exist too: `Verifier::verify` yields `Vec<CheckResult>`, `CheckRegistry::run_all` yields `Vec<CheckRunResult>`, and `CriteriaJudge` yields a `JudgeResult`. **But nothing maps those three producer outputs into `VerifyEntry`.** `CheckResult { name, passed, detail }` (PRD 05) has no `method`, no `covers`, no `interpretation`; `CheckRunResult` has `covers` (via the `DeterministicCheck`) but no `method` tag; the judge has an interpretation (its `reason`) but it is not threaded into a `VerifyEntry`. The `covers[]` requirement-coverage link — the thing that lets the verification report "link each requirement to its evidence" (p.11 §"H3 in detail") — only exists on the deterministic-check path, not on the default `NoToolErrors`/`CleanTermination`/judge checks.

**Why it matters:** "verification autonomy" (eval-plan §3; paper p.10) and the H3 `AutonomousVerifiedSuccess` rule both depend on a *complete* `verification_trace` with requirement coverage. A partial mapping means the package records *that* checks ran but not *which requirements they covered* for the non-deterministic checks — degrading the report from "requirement-linked evidence" (the paper's whole H3 thesis, p.12 §"Verification is a runtime capability") back toward an assertion. **Recommendation:** specify the projector (again, compose package-assembly): `CheckResult`/`CheckRunResult`/`JudgeResult` → `VerifyEntry`, tagging `method` from the check's origin (a `NoToolErrors` check → `method = registered_test`-class or a new `internal_check` value; deterministic → `deterministic_check`; judge → `manual`/`patch_review` as appropriate) and carrying `covers` from `DeterministicCheck.covers` where present, empty otherwise. This is a small mapping table, but it must be named or the trace is half-built.

## 5. MCP (PRD 07): does it integrate without breaking evidence capture?

Mostly yes — and the design is well-aligned with the paper's **tool registry** responsibility (Table 1, p.6: "Declare available tools and allowed commands"; failure-when-absent "Failed call; unsafe command; repeated timeout" → "Tool trace"). MCP tools are wrapped in `McpToolFn` → `ToolFn` and registered in the *same* `ToolRegistry` as built-ins ([PRD 07](../prd/07-mcp.md) §"Tool registration"), namespaced `mcp__<server>__<tool>`, and they "go through the same `Policy::before_tool()` path as built-ins" (§"Policy integration"). Because they dispatch through the identical `ToolDispatch` boundary, **MCP tool calls produce `ToolEvent`s exactly like built-ins** — so tool-class evidence (#2) is captured uniformly, and `McpToolFirstUse` approvals flow into the intervention log (#6) as `tool_block`-adjacent records. The server role is explicitly "a thin transport over `Session::send()` — the same turn cycle, post-turn work, verification, and evidence journal apply … the harness layer is not bypassed" (§"Integration with harness layer"). That sentence is the right invariant and it is stated. Good.

Two integration concerns the evidence lens surfaces:

- **`McpToolFn::call` returns a `String`, not a `ToolOutcome`.** PRD 07's `impl ToolFn for McpToolFn` (§"Tool registration") has `async fn call(&self, args) -> String` returning `"ERROR: MCP call failed: {e}"` on error — but the canonical `ToolFn` trait (PRD 03; ADR-0022) is `async fn call(&self, args) -> ToolOutcome`. So MCP is the **one place the "status is structural, not sniffed" contract is violated**: an MCP failure comes back as a magic-prefixed `"ERROR: …"` string, which the `Tracer` would then have to re-sniff to set `ToolOutcome.status = error` — exactly the fragile prefix-parsing ADR-0022 abolished (PRD 04 §"Status is structural"). This silently re-introduces the misclassification bug for MCP results (any MCP tool whose legitimate output starts with "ERROR" is mis-statused), and it means MCP tool failures may not cleanly drive `f_tool` attribution. **Recommendation (P1):** update PRD 07's `McpToolFn` to return `ToolOutcome` (`ToolOutcome::error(...)` on `Err`, `ToolOutcome::ok(s)` on success), matching the trait. One-line fix in PRD 07; restores evidence-capture fidelity for the entire MCP tool surface. (This also tightens Round 2 R1's "`ToolOutcome` mapping" note from the *outside* — there it was about wrapping `rmcp`; here it is about the trait's return type itself.)

- **MCP timeouts inherit 4a.** A hung remote SSE call (PRD 07 §"Heartbeat & reconnect") that the client surfaces "the same way a crashed stdio server does" needs to land as `timeout = true` in the tool trace — but per 4a there is no `timeout` field/status to land in. So the MCP reconnect machinery, correctly designed at the transport layer, has nowhere to *record* a timeout as evidence. Fixing 4a fixes this for free; flagging the dependency.

No MCP-specific *new* evidence hole beyond these — the absorption-into-`ToolRegistry` design is sound and is the right way to keep the action/tool surface uniform (paper p.5 §Positioning: an ACI "is one component of a harness").

## 6. Observability vs the paper's responsibility — and one sound divergence

The **observability layer** responsibility (Table 1, p.6: "Expose logs, traces, outputs, runtime errors"; failure-when-absent "Unverifiable success; undiagnosable failure" → "Observation log") is well-served in principle: the `Tracer` accumulates evidence "regardless of the trace flag — the verifier always has a complete episode" (PRD 04 §"Structured logging"), the four JSONL logs + episode packages are the observation substrate, and the `!Send` `Tracer`-owned-by-`Session` design (ARCHITECTURE §7) is a clean no-lock capture path. The post-turn `tokio::join!` (ADR-0012) correctly runs entropy + judge + consolidation off the reply path while still joining their signals before the next turn — so evidence emission does not cost hot-path latency. This is faithful.

**The sound divergence (already pinned, restated for completeness):** RK's **episode = one `send()` turn**, while the paper's episode = "one attempt … to complete a specified software-engineering task" (p.8 §Episode). RK reconciles via `episode_id` grouping (ADR-0018) and recovers the task-level unit by aggregating over `episode_id` in the eval plan (eval-plan §3). This is a *questionable-but-defensible* divergence, and it is honestly flagged everywhere (ARCHITECTURE §12; PRD 04 §M-HIR; data-model §5). My integration note: the `parent_turn_id` subagent linkage (data-model §4.1) plus `episode_id` is *just* enough to reconstruct a task's full trace tree, **provided** every per-turn package carries the same `episode_id` — which depends on `task_id` being stable across a task's turns. That stability is asserted (`episode_id = "ep_<task_id>"`) but the *mechanism* that holds `task_id` constant across turns is not specified in any PRD. Minor, but worth a one-line pin in PRD 06 (the turn cycle) so the grouping that makes the whole task-level metric family work is not left implicit.

**One assembly gap on the otherwise-solid intervention class (#6):** `interventions.jsonl` is the append-only source of record, but the episode package embeds `intervention_log: Vec<InterventionRecord>` *for that turn*. Nothing specifies the **filter** — which interventions (by `session_id` + the turn's time window, or by `source_message_id`) belong to *this* turn's package. Without it, a turn's package either over-reports (all session interventions) or under-reports. Cheap to pin (compose reads the logger filtered by the turn's `source_message_id` set); flagging so it is owned.

**Common root cause (worth the owner's attention):** five of seven findings (R1, R3, R4, R6, and half of R2) are the *same* missing component — **a `compose` package-assembly projector** that turns the raw, per-turn evidence the producers emit (`Episode.tool_events`, `CheckResult`s, the recall candidates, the intervention log) into the eight typed traces. RK has specified the *struct* (`EpisodePackage`, all eight fields) and the *writer* (`EvidenceJournal::record_episode`), but not the *builder* between them. The schema is faithful; the assembly step is the hole. One ADR ("episode-package assembly: where each of the eight traces is produced/projected") would close R1/R3/R4/R6 at once and is the highest-leverage doc to write.
