# Round 3 — Systems Architect

## 1. Scope & lens

The harness is a *runtime substrate* that "mediates how a foundation-model agent observes a project, acts on it, receives feedback, and establishes that a change is complete" (p.1, p.4). My three questions, against the clean text:

1. Do RK's H0–H3 definitions match the paper's **progressive-runtime-support-exposure** semantics — specifically R1 controlled visibility (what is *withheld* at each level), not just what is *added* (p.6–7, Table 3)?
2. Is "**adjudicate by verification autonomy, not task success**" (contribution iii, p.2; Outcome taxonomy, p.10; Methods, p.15) actually reflected in RK's outcome/adjudication design?
3. Does the deployment/topology model (single-writer SQLite WAL, sessions, isolation seam) stay consistent with the paper's substrate framing (p.4–5) **and** its eval-substrate methods (per-episode isolated workspace at a fixed commit, p.15)?

Read: paper §"A controlled harness ladder" + Table 3 + Methods; [`ARCHITECTURE.md`](../ARCHITECTURE.md) §3/§7/§8/§9/§12; [`adr/0028`](../adr/0028-h0-selectable-harness-level-or-eval-only.md); [`reference/configuration.md`](../reference/configuration.md); [`prd/02-constrain.md`](../prd/02-constrain.md); [`prd/04-observe.md`](../prd/04-observe.md); [`prd/05-compose.md`](../prd/05-compose.md); [`dev/eval-plan.md`](../dev/eval-plan.md). I do **not** re-litigate the crate DAG, WAL+busy_timeout, `!Send` Tracer, or versioning — those were settled and remain sound.

## 3. Q1 — The ladder is defined faithfully but is not yet the ablation the paper specifies

**What's right.** RK's level *content* matches the paper near-verbatim. Paper H1 = "tool registry, a test-command registry, and a tool-usage protocol" (p.6); RK H1 = same ([ARCHITECTURE §3](../ARCHITECTURE.md#3-maturity-model-h0h3); [glossary](../reference/glossary.md)). Paper H2 adds "agent-readable project memory … a task-state file, and a context-selection protocol" (p.6); RK matches. Paper H3 adds "a deterministic behavioral check registry, a bug-reproduction protocol, a failure-attribution protocol, a verification protocol, and a verification report template" (p.6–7); RK's H3 checks (`ReproduceBeforeEdit`, `VerificationReportRequired`), `CheckRegistry`, and `EpisodePackage` map cleanly ([PRD 05](../prd/05-compose.md)). H0 = "task description; repository files" with no tool registry — correctly named the ablation floor, with selectability deferred to [ADR-0028](../adr/0028-h0-selectable-harness-level-or-eval-only.md). The additive/monotonic-inheritance intent (Figure 2: "each level inherits all artifacts of lower levels") is stated in [ARCHITECTURE §3](../ARCHITECTURE.md). **No drift in *what each level exposes*.**

**The load-bearing gap (already flagged, correctly).** The paper's ladder is a *controlled-visibility ablation*, and its operational definition is **R1**: "each level exposes only the artifacts assigned to that level; lower levels **do not see** higher-level artifacts" (p.7), made concrete by the Table 3 visibility matrix (the "—" cells). RK enforces the **additive** half (higher levels gate in more tools/checks) but **not the subtractive half**: [ARCHITECTURE §3](../ARCHITECTURE.md) and [eval-plan §4](../dev/eval-plan.md) both state plainly that "the level gates tools/checks but does not yet hide H2 memory from H1."

Mapping the paper's Table 3 onto what RK enforces today makes the gap precise (paper "—" = hidden; RK "leaks" = present-in-workspace, readable regardless of level):

| Paper artifact (Table 3) | Hidden below | RK enforcement today |
|---|---|---|
| Tool registry / test-command registry / tool-usage protocol | H1 | **gated** (no registry at H0) — additive half works |
| `AGENT_GUIDE` / `ARCHITECTURE` / `TESTING` / `TASK_STATE` / `KNOWN_FAILURES` | H2 | **leaks** — files sit in the shared workspace; an H1 read isn't blocked |
| Context-selection protocol | H2 | **leaks** — same |
| Deterministic-check registry (`checks.toml`) | H3 | **partly gated** ("agent-visible at H3", [PRD 05](../prd/05-compose.md)) but the file is on disk; no read-filter described |
| Bug-reproduction / failure-attribution / verification protocol + report template | H3 | **gated** as tools (H3-only `attribute_failure`, `verification_report`) — but any *prose* protocol docs in the tree leak |
| Hidden evaluator notes | all levels | **must stay hidden** (R4) — RK keeps the evaluator pack out of agent context ([eval-plan](../dev/eval-plan.md)); confirm no `checks.toml` `expected_substring` leaks into H0–H2 context |

That is the difference between a *capability-gating ladder* (what RK has) and a *controlled-visibility ablation* (what the paper's empirical claim — "makes the harness's contribution empirically separable from the model's," p.2 — actually requires). Without subtractive hiding, an H1 run can incidentally read H2 project memory sitting in the workspace, and the H1-vs-H2 contrast is confounded. **This is the single most important fidelity item in my lens.** RK is honest about it (a tracked refinement, not a hidden bug), so the verdict is *sound divergence-in-progress*, not silent drift — but it is the item that most directly weakens the paper's central methodological claim if left unresolved, and it should be sequenced before any H1-vs-H2 lift is reported as evidence.

**Two refinements (additive, small):**

- **R1 has a clean Rust home.** The matrix is a fixed, level-keyed allowlist of artifact names (the rows of Table 3). The natural enforcement point is the **context-assembly seam in `feed`** (the same place [PRD 03](../prd/03-feed.md) builds context) plus a path-visibility filter on the file-reading tools: at level H*n*, reads of higher-level artifacts (`AGENT_GUIDE`, `TASK_STATE`, `checks.toml`, the H3 protocol docs) return "not present at this level" rather than content. This is a *visibility* concern, distinct from the `constrain` *permission* concern (§4) — it withholds existence, not authority — so it belongs in `feed`/context-assembly, not in `WorkspacePolicy`. Worth an ADR ("Table-3 visibility enforced at the context/read seam; H0–H3 hides higher-level artifacts") to convert ADR-0028's open item into a named seam.
- **Level ≠ phase — fix the conflation in [ARCHITECTURE §3](../ARCHITECTURE.md).** The §3 table's "Rusty Keys" column maps levels to *build phases* ("H3 = Phase 2 (deterministic), Phase 4/10 (semantic)"; "H2 = Phases 3–4"), which reads as if H3 partly precedes H2. The paper's ladder is a *runtime visibility configuration*, fully orthogonal to build order. The mapping is fine as a roadmap note but should be labelled "(build order, not ladder order; the ladder is a runtime config — R2: same task/repo/state across levels)" so a reader doesn't infer a non-monotonic ladder. One sentence.

## 4. Q2 — Adjudication drifts from "verification autonomy" toward "agent self-report at H3 only"

This is the finding I'd most want a second opinion on, because RK gets the *vocabulary* right while the *adjudication wiring* quietly narrows the paper's claim.

**The paper's design (two separations RK partially collapses):**

- **Separation A — agent-side vs evaluator-side.** Deterministic behavioral checks have an explicit **dual role**: "at H3 they are agent-visible harness artifacts that support the agent's own verification; **at all levels they are evaluator-side adjudication checks that classify the final outcome**" (p.10; restated Methods p.14–15). The *evaluator* applies the checks at every level; the agent only *sees* them at H3.
- **Separation B — task behavior vs evidence quality.** "The taxonomy separates task behavior from evidence quality: a patch can be correct but unverified" (p.10). `unverified_success` = "the patch appears correct or the task behavior passes evaluator-side checks, but the agent did not itself produce evidence sufficient under the protocol." This is *precisely* the autonomy-vs-success distinction (contribution iii: "adjudicates … by verification autonomy rather than task success alone," p.2). Table 5 makes it concrete: **H0 is labelled `autonomous_verified_success` via "evaluator-side deterministic checks pass"** — with no agent-produced verification report at all — while **H1/H2 are `unverified_success`** despite producing a working patch.

**Where RK lands.** RK's `EpisodeOutcome` is the right five labels with the right boundaries, and the `judge_ran`/`UnsafeInvalid` gates are faithful ([PRD 05 Outcome taxonomy](../prd/05-compose.md)). But two wiring facts diverge:

1. **RK classifies "every H3 turn"** ([PRD 05](../prd/05-compose.md): "Every H3 turn is classified under the five-label taxonomy"), and [eval-plan §4](../dev/eval-plan.md) gives H0 "(baseline only)" with no outcome label. The paper assigns an outcome label to **all four levels** from the *same* evaluator-side checks (Table 5). So RK's H0/H1/H2 episodes carry no adjudicated outcome, which means the paper's headline contrast — *H0 reaches `autonomous_verified_success` on evaluator checks while H1 is only `unverified_success`* — **cannot be reproduced in RK as currently specified.** R5 ("every level is adjudicated under the same final outcome taxonomy," p.7) is therefore not met.
2. **RK adjudicates from the agent's *self-produced* tool calls**, not an independent evaluator pass. The classifier reads whether the agent emitted a `verification_report` and an `attribute_failure` (the `VerificationReportRequired`/`ReproduceBeforeEdit` checks), and `CheckRegistry::run_all()` is "agent-visible at H3" ([PRD 05](../prd/05-compose.md)). There is no described **evaluator-side check pass that runs at H0–H2 independent of the agent**. This collapses Separation A: RK conflates "the agent produced verification evidence" with "the evaluator verified the behavior." The paper keeps them distinct so that a correct-but-silent patch is *labelled* `unverified_success` rather than going unlabelled — that label is the operationalization of "verification autonomy."

**The contrast, side by side** (paper Table 5 / Methods p.15 vs RK as specified):

| Level | Paper: evaluator-side label (Table 5) | RK today |
|---|---|---|
| H0 | `autonomous_verified_success` — "evaluator-side deterministic checks pass; full regression succeeds" (no agent report) | **no label** — "(baseline only)" ([eval-plan §4](../dev/eval-plan.md)); classifier is H3-only ([PRD 05](../prd/05-compose.md)) |
| H1 | `unverified_success` — patch + tool trace, but agent self-produces no verification | **no label** — H1 gate is schema-validity / clean-termination, not an `EpisodeOutcome` |
| H2 | `unverified_success` — adds context trace, still no self-verification | **no label** |
| H3 | `autonomous_verified_success` — agent's own reproduce→attribute→verify→report | **labelled** — the only level RK adjudicates |

The empty "RK today" labels for H0–H2 are the drift: the paper's headline contrast (H0 reaches verified-success on *evaluator* checks while H1 is only *unverified*) is unreproducible in RK, and R5 ("every level adjudicated under the same final outcome taxonomy," p.7) is unmet.

**Why it matters for the lens.** "Adjudicate by verification autonomy, not task success" is not just a label set — it's the claim that the *same evaluator-side ground truth* runs under every harness configuration, and the *delta* between "behavior passes" (task success) and "agent proved it" (verification autonomy) is what the ladder measures. RK has the labels but not the invariant evaluator. The fix is structural but contained, and the pieces already exist:

- Make `CheckRegistry::run_all()` an **evaluator-side adjudication pass that runs at all levels** (it already loads `checks.toml`), distinct from the agent-visible H3 surfacing. The dual role is the paper's own resolution — "the distinction preserves the ladder while permitting consistent adjudication" (p.10) — so this is faithful, not an addition.
- Let the `EpisodeOutcome` classifier run at **H0–H3**: at H0–H2 the inputs are (evaluator deterministic checks ✓/✗) + (did the agent self-produce a verification report? → almost never below H3 → `unverified_success`); at H3 add the agent's own verification report → eligible for `autonomous_verified_success`. This is exactly Table 5's pattern.
- Worth an ADR ("evaluator-side deterministic-check adjudication at all levels; `EpisodeOutcome` assigned H0–H3; agent-visible checks remain H3-only") and an [eval-plan §4](../dev/eval-plan.md) edit replacing H0's "(baseline only)" with "(adjudicated `unverified_success`/`autonomous_verified_success` from evaluator-side checks; no agent-produced evidence)".

*Caveat on my own confidence:* RK's "episode = turn" ([ADR-0018](../adr/0018-episode-equals-turn-with-episode-id-grouping.md)) already makes RK's outcome unit narrower than the paper's task-grained episode, and a turn-level conversational reply genuinely may not warrant a deterministic-check adjudication every turn. So the *all-levels* fix lands most cleanly in the **eval-plan's golden-episode replay** (a task-grained context where `checks.toml` is meaningful), not necessarily the live per-turn hot path. The drift is real for the *eval substrate*; for the *live product* it's defensible to adjudicate only when checks exist. That nuance should be stated rather than left implicit.

## 5. Q3 — Substrate framing is faithful; the *eval-substrate* isolation requirement is under-specified

**Product topology — consistent with the substrate framing.** The paper's substrate is "task-runtime infrastructure: it governs how an agent observes a project, acts on it, receives feedback, and establishes completion" (p.4), and it explicitly *disclaims* an agent OS ("we do not propose an operating system for AI agents," p.5 — the resource-management analogy of Table 2 is "strictly … a lens"). RK matches this posture: `Session::send()` as the substrate boundary, the four verbs over OODA, "no overhead in the hot path" ([PRD 00](../prd/00-overview.md); [ARCHITECTURE §2/§6](../ARCHITECTURE.md)). The single-writer-friendly **SQLite WAL + `busy_timeout`** under multi-mode sessions and subagents ([ARCHITECTURE §8/§10](../ARCHITECTURE.md)) is a sound product-runtime choice and *not* in tension with the paper — the paper says nothing about persistence topology; it's silent there, so RK is free. Concurrency (one `Session` per tokio task, `mpsc(1)` for turn ordering, `!Send` Tracer, post-turn `tokio::join!`) is internally coherent and unaffected by the paper. **No drift in the substrate model itself.**

**The under-specified seam — eval isolation.** Where RK *does* diverge is the paper's **eval-substrate Methods**, which are a harder contract than the product runtime currently meets:

- R2: "all levels run from the **same task and the same repository state**" (p.7).
- Methods: "Each episode is executed in an **isolated workspace** with the repository checked out at a **fixed initial commit**. … The agent's compute environment is **identical across harness levels except for the harness artifacts**" (p.15).
- Full-regression handling: timeouts are *recorded*, "full regression is **not silently retried**, and a missing full-regression result is **not silently treated as success**" (p.15) — RK matches this last point well ([ARCHITECTURE §10](../ARCHITECTURE.md): judge-unavailable bars `AutonomousVerifiedSuccess`; full-regression-timeout exemption in [PRD 05](../prd/05-compose.md)).

RK's runtime **shares** one workspace, two SQLite DBs, four JSONL logs, and one `task.json` across `multi`-mode sessions and subagents ([ARCHITECTURE §8](../ARCHITECTURE.md)). For a *product* that is correct (shared project memory is the point). For the *eval ladder* it violates R2/Methods: two episodes at different levels against a shared workspace can see each other's residue, share accreted `task.json` state, and read each other's `.rustykeys/` history — which both confounds the ablation (cross-level contamination) *and* compounds the §3 R1 gap (a shared workspace is exactly where un-hidden H2 artifacts leak into an H1 run). The `EpisodePackage.initial_state: { commit, workspace }` field ([PRD 05](../prd/05-compose.md)) *records* the baseline but **nothing checks out at that commit or isolates the tree** — it's a label, not an enforced invariant.

**Fix (additive, eval-side):** the eval harness ([eval-plan §5](../dev/eval-plan.md) golden suite) should run each episode in a **fresh workspace checked out at the fixed commit, with a per-episode `.rustykeys/`** — not the shared product state. This is the same "per-episode isolated workspace" the paper's Methods require and pairs naturally with the round-2 `RUSTYKEYS_ISOLATION` / `ToolExecutor` seam (a `sandboxed` executor already implies a confined, disposable filesystem) and with the round-2 "harness profile" proposal (level + isolation + workspace co-declared). It also gives the round-3 §3/§4 fixes their natural home: visibility hiding (§3), the evaluator-side check pass (§4), and workspace isolation (§5) are *the same eval-substrate concern* and should land as one workstream, not three. Worth an ADR ("eval episodes run in an isolated workspace at a fixed commit with a per-episode `.rustykeys/`; R2/Methods compliance; distinct from the shared product runtime").

## 6. Permissions responsibility — faithful, with one paper-anchored note

The paper's permissions component: "Restrict risky actions; expose approval gates," failure-when-absent "Unsafe invalid episodes," evidence "Permission record" (Table 1, p.6); resource "Allowed and forbidden actions" → "Unsafe edits; destructive commands" (Table 2, p.7). RK's `constrain` layer is a **faithful and arguably over-delivered** realization: `WorkspacePolicy` (canonicalized boundary), `PermissionMode` (six modes incl. `Plan`'s approval-gate-before-switch), `ApprovalGate` (the paper's "expose approval gates" verbatim), the `security.jsonl` "permission record," and structured `PolicyError` variants that feed attribution `(category, layer)` ([PRD 02](../prd/02-constrain.md)). The mapping is explicit in [ARCHITECTURE §12](../ARCHITECTURE.md) ("constrain ≈ permissions + task-interface").

Two systems notes:

- **The permission→`unsafe_invalid` linkage is sound and should be stated.** The paper ties the permission boundary's *absence* to "Unsafe invalid episodes" (Table 1). RK realizes this from the *other* direction: `UnsafeInvalid` is triggered by entropy findings (`TestWeakening`/`BoundaryViolation` severity ≥ 2), not by a permission *block* ([PRD 04](../prd/04-observe.md)/[05](../prd/05-compose.md)). That's a reasonable RK choice — a *blocked* unsafe action is correctly *not* an unsafe episode (the harness worked; it's an `unavoidable` `tool_block` intervention, [PRD 04](../prd/04-observe.md)). But the paper's framing is "absence of the permission boundary → unsafe_invalid"; RK's `unsafe_invalid` fires on *entropy*, and the permission boundary's success shows up as a *non-event* (a block + an intervention record). The two are consistent but the linkage is implicit — one line in [PRD 02](../prd/02-constrain.md) or [ARCHITECTURE §12](../ARCHITECTURE.md) ("a *blocked* risky action is a working boundary, recorded as a `tool_block` intervention; `unsafe_invalid` captures only actions that *got through* and weakened/violated") would close the loop the paper draws.
- **Visibility (§3) vs permission (this section) are different seams — keep them apart.** R1 artifact-hiding withholds *existence/knowledge* (a `feed`/context concern); `WorkspacePolicy` withholds *authority to act* (a `constrain` concern). It would be a mistake to implement Table-3 visibility by denying file reads in the policy layer — an H1 agent reading `AGENT_GUIDE` is not a *security* violation, it's an *ablation* leak. Naming both seams explicitly prevents that conflation.

## 7. Net assessment & sequencing

RK's paper fidelity is high on *vocabulary and component structure* and honest about its known gaps. The three lens questions surface **one settled-but-unbuilt gap (R1 visibility, §3), one genuine adjudication drift (evaluator-side checks at all levels, §4), and one under-specified eval invariant (per-episode workspace isolation, §5)** — and crucially, **all three are the same eval-substrate concern** and should be sequenced as one workstream rather than three ADRs:

1. **§5 workspace isolation** is the substrate the other two sit on (fresh tree + per-episode `.rustykeys/` at a fixed commit) — do first.
2. **§3 Table-3 visibility hiding** at the `feed`/context-read seam — needs the isolated workspace to be meaningful.
3. **§4 evaluator-side adjudication at all levels** + `EpisodeOutcome` H0–H3 — needs the isolated workspace + `checks.toml` to produce the paper's Table 5 pattern.

Until they land, RK can *demonstrate* the ladder's evidence-structure differences (which it does well — the episode package genuinely thickens H1→H3) but cannot yet make the paper's stronger *separability* claim (R1) or reproduce its headline *autonomy-vs-success* contrast (R5, Table 5). That is the right thing to know before any H*n*-vs-H*m* lift is reported as evidence. The permissions responsibility (§6) and the substrate/concurrency model (§7-adjacent: WAL, sessions, `!Send` Tracer) need no structural change — only two clarifying sentences.

*Cross-persona:* the **verification/observability persona** co-owns §4 (the evaluator-side check pass is also their adjudication contract); the **eval/harness persona** owns the §5 isolated-workspace + golden-suite mechanics; the round-2 **`RUSTYKEYS_ISOLATION` / harness-profile** proposals are the natural carrier for §5. I own the *seam placement* (visibility in `feed` not `constrain`; eval isolation distinct from product runtime; evaluator-checks as an invariant across levels) and the paper-fidelity framing.
