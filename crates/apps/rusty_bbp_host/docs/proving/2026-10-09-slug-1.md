## Runbook defects

1. Step 2/3 and the setup list assume Linux; the runbook never says the runner is Unix-only (the README does, "On Windows `bbp runner` compiles and reports every run as `error`"). A first-time reader on Windows loses time before finding out.
2. The profile in `profiles.json` is machine-specific and the toolchain it names is not always runnable in the sandbox: a symlinked `~/.cargo/config.toml` (common with dotfile managers) silently breaks every run. The runbook should say that `read_roots` must cover the *resolved* targets of anything under `CARGO_HOME`, or tell the operator to point `CARGO_HOME` at a clean directory.
3. "An MCP-only role lists only `mcp__bbp__*`" is false for this Claude Code build: `LSP` is listed under `--tools ""` (section 6).
4. There is no pre-flight check for the harness login: `claude auth status` reported `loggedIn: true` while every API call returned 401. A `claude -p "ok"` smoke test belongs in setup, because the moderator otherwise forfeits turns for ~133 s each.
5. The runbook says `bbp mod` "returns at `closed` or `cancelled`". At `escalated` it keeps running (waiting for `resume`/`cancel`) and says nothing, so an operator who does not want to cancel has to kill it. The runbook should say what `escalated` expects of the human.
6. Nothing tells a Tester, the Coder or the operator what to do when a run fails for an environmental reason. The only available message is `revise`, which costs an iteration; four iterations are enough to escalate the task with a correct candidate on the table.
