# Data Mesh Monitor

Vendored from [baileyrd/meshed](https://github.com/baileyrd/meshed)'s
`data-mesh-monitor` into `rusty_mill` (2026-09-03) so it runs against the
Rust registry. From this directory:

```
cargo run -p rusty-meshed-registry --bin meshed_registry   # registry on 127.0.0.1:8100
npm ci && npm run dev                                       # dashboard on http://localhost:5173
npm test                                                    # reverse-trace parity vs the Rust reference
```

Set `MESHED_REGISTRY_URL` to proxy to a registry on another address. The
rest of this file is the source repo's own README, unchanged.

Full-screen ops-center dashboard for monitoring an event-driven data mesh in real time.

## Features

- **Topology graph** — SVG force-layout with 4 tiers (Producers → Brokers → Processors → Consumers)
- **Animated particles** — events travel bezier-curved edges; errors glow red
- **Live event stream** — right panel, newest-first, timestamped to ms with latency + payload size
- **Metrics bar** — throughput sparkline, P50 latency bar, error rate health, active flows, DLQ counter
- **Reverse Trace tab** — pick a leadership outcome and watch it trace back through the domains and sources it depends on, with a fidelity gauge, a worst-first bottleneck list, per-domain maturity sliders (what-if), an always-on legend, and a Markdown gap-summary export (see below)

## Reverse Trace (outcome → domains → sources)

Leadership asks for *"a dashboard showing acquisition status across my
programs"* and sees one deliverable. The **REVERSE TRACE** tab (`/#trace`)
shows what it actually depends on: the outcome sits on the right, the domains
it draws on in the middle, and the concrete sources (systems, files, people)
on the left — the reverse of the Mesh Ops flow, deliberately. Every domain
carries a maturity level on a five-level ladder:

| Level | Name | Definition |
|---|---|---|
| 0 | Tribal | In people's heads or undocumented process. No artifact. |
| 1 | Documented | Static artifacts: slides, PDFs, a personal spreadsheet. |
| 2 | Structured | In a system with a schema, but siloed; extraction is manual. |
| 3 | Accessible | Programmatically queryable: API, DB, scheduled export. |
| 4 | Integrated | On the mesh: governed, contracted, flows automatically. |

Each outcome declares a minimum maturity per domain and how much it depends
on it (blocking / degrading / optional). The trace classifies every edge —
**satisfied** (green, flowing), **blocked** (red, dashed, particles die at the
domain), **degraded** (amber, throttled) or **missing** (grey, dotted) — and
caps the outcome's fidelity at its weakest required domain: *Full*,
*Partial (n%)* or *Not achievable*. The side panel is the "what to fund
first" list; the bottom bar's sliders let you raise a domain and watch the
verdict move (scenario-local, resets on reload). *Copy gap summary* puts a
Markdown version on the clipboard for briefing decks.

The model and the trace algorithm are owned by the Rust crate
`rusty-meshed-trace` in [`Rusty-Mill/rusty_mill`](https://github.com/Rusty-Mill/rusty_mill)
(`crates/rusty_meshed/crates/rusty-meshed-trace`). This app carries:

- `src/reverseTrace.js` — a line-for-line JavaScript port of the crate's
  `trace()` and Markdown export, so v1 runs fully client-side (no backend).
- `src/scenarios/acquisition_status.json` — the shipped scenario, generated by
  the crate (its maturity levels are illustrative placeholders, not an
  assessment).
- `src/scenarios/acquisition_status.reports.json` — the crate's own trace of
  that scenario. `npm test` (`scripts/trace-parity.mjs`) re-traces the
  scenario in JS and fails if anything differs, so the port can't drift.

To regenerate both JSON files after editing the scenario TOML in the crate:

```bash
# in rusty_mill
cargo run -p rusty-meshed-trace --example export > export.json
# "scenario" → src/scenarios/acquisition_status.json
# "reports"  → src/scenarios/acquisition_status.reports.json
```

Later, the live-feed swap point is the same as Mesh Ops: replace
`traceOutcome(scenario, id)` with a fetch of the crate's `TraceReport` JSON —
the shapes are identical.

## Connecting a Real Backend

The simulation loop in `DataMeshMonitor.jsx` is clearly marked. Replace it with an `EventSource`:

```js
// In DataMeshMonitor.jsx — replace the simulation useEffect body:
const es = new EventSource("/api/mesh/events");
es.onmessage = (e) => {
  const ev = JSON.parse(e.data);
  // Expected event shape:
  // {
  //   type: string,          // e.g. "order.placed"
  //   from: string,          // source node label
  //   fromType: string,      // "producer" | "broker" | "processor" | "consumer"
  //   to: string,            // target node label
  //   lat: number,           // latency in ms
  //   kb: number,            // payload size in KB
  //   isErr: boolean         // error flag
  // }
  handleEvent(ev);
};
return () => es.close();
```

Then enable the proxy in `vite.config.js`:

```js
server: {
  proxy: { "/api/mesh": "http://localhost:8000" }
}
```

## Customising Topology

Edit `NODES` and `EDGES` in `DataMeshMonitor.jsx` to reflect your real mesh.
Node `x`/`y` coordinates are within an `810 × 500` SVG viewBox.

```js
const NODES = [
  { id: "p1", type: "producer", label: "My Source", sub: "Kafka · v3", x: 90, y: 95 },
  // ...
];

const EDGES = [
  { id: "e1", from: "p1", to: "b1" },
  // ...
];
```
