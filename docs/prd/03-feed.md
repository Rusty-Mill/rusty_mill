# PRD 03 — Feed

## Responsibility

The feed layer is the **Observe + Orient** half of the OODA loop. It supplies
the kernel with everything it needs to reason well:

- **Tools**: what the agent can do (`#[tool]` registry)
- **Context**: system prompt + oriented working memory (recall + task prompt)
- **Memory**: short-term stream capture, long-term graph, Task State

Feed does not execute — it prepares. The kernel executes.

## Tools

### `#[tool]` proc macro

aisdk's `#[tool]` macro annotates a Rust function and generates the JSON schema
the model needs, eliminating the manual schema authorship that Keystone required:

```rust
#[tool]
/// Read a file from the workspace. Path must be within the workspace root.
pub async fn read_file(path: String) -> Result<String, ToolError> {
    tokio::fs::read_to_string(&path).await.map_err(ToolError::from)
}
```

The macro derives: tool name (function name), description (doc comment),
parameter schema (function signature), return handling.

### `ToolRegistry`

Tools are registered at startup and passed to the kernel. The registry handles
dispatch (with policy vetting — see PRD 02) and exposes the tool list to aisdk.

```rust
pub struct ToolRegistry {
    tools: HashMap<String, Box<dyn ToolFn>>,
    session_factory: Arc<dyn SessionFactory>,   // for the `agent` tool (ADR-0017)
}
```

MCP server tools are registered alongside built-ins with namespaced names
(`mcp__<server>__<tool>`) — see PRD 07.

### The `ToolFn` trait (the aisdk ↔ harness seam)

`Box<dyn ToolFn>` is used throughout but was never declared. It is the object-safe
plugin seam (ADR-0024: trait objects at every seam) that lets the registry hold
heterogeneous tools — built-ins, the `agent` tool, MCP proxies — behind one type.

> *v1 intent, revisit after a spike.* The exact method set and the `ToolOutcome`
> field list are pinned in [data-model](../architecture/data-model.md) /
> [error-handling](../dev/error-handling.md); this is the shape, not a frozen ABI.

```rust
#[async_trait]                       // async-trait mechanism per ADR-0024
pub trait ToolFn: Send + Sync {
    /// Tool name surfaced to aisdk (function name from `#[tool]`).
    fn name(&self) -> &str;
    /// JSON schema (generated by `#[tool]`) for aisdk's tool list.
    fn schema(&self) -> serde_json::Value;
    /// Execute. Always returns a structured `ToolOutcome` (ADR-0022) — never a
    /// magic-prefixed string. Policy vetting happens in `dispatch`, before this.
    async fn call(&self, args: serde_json::Value) -> ToolOutcome;
}
```

`ToolOutcome` (defined in `observe`, ADR-0022) carries the status **structurally**
(`Ok | Error | Blocked | Timeout | Truncated`) plus the payload, replacing the
fragile `BLOCKED …`/`ERROR …`/`TIMEOUT …` prefix-sniffing. One formatter renders it
to the model-facing string; the `Tracer` reads `outcome.status` directly. Status
encoding and the formatter/parser live in
[data-model](../architecture/data-model.md) and
[error-handling.md](../dev/error-handling.md).

### Concrete adapter — `#[tool]` fn → `Box<dyn ToolFn>`

This is the load-bearing seam that turns an aisdk `#[tool]`-annotated function
(which generates name/schema/signature) into a registry entry. The `#[tool]` macro
emits a generated descriptor type per function (e.g. `read_file::descriptor()`
yielding the name + JSON schema); the adapter wraps it and maps the function's
`Result<String, ToolError>` into a `ToolOutcome`:

```rust
/// Adapts one aisdk `#[tool]` function into a registry-ready `ToolFn`.
pub struct AiSdkTool<F> {
    name: &'static str,
    schema: serde_json::Value,
    invoke: F,                       // async closure over the generated `#[tool]` fn
}

#[async_trait]
impl<F, Fut> ToolFn for AiSdkTool<F>
where
    F: Fn(serde_json::Value) -> Fut + Send + Sync,
    Fut: Future<Output = Result<String, ToolError>> + Send,
{
    fn name(&self) -> &str { self.name }
    fn schema(&self) -> serde_json::Value { self.schema.clone() }

    async fn call(&self, args: serde_json::Value) -> ToolOutcome {
        match (self.invoke)(args).await {
            Ok(s)  => ToolOutcome::ok(s),
            Err(e) => ToolOutcome::from(e),   // ToolError → Error/Timeout/Truncated (ADR-0022)
        }
    }
}

// Registration (at Session::new): the `#[tool]` macro's generated descriptor
// supplies name + schema; the closure adapts the model's JSON args to the typed fn.
registry.insert(Box::new(AiSdkTool {
    name:   read_file::NAME,
    schema: read_file::schema(),
    invoke: |args| async move {
        let p: ReadFileArgs = serde_json::from_value(args)?;   // arg deserialisation
        read_file(p.path).await
    },
}));
```

Policy vetting is **not** in `call()` — it happens once in
`ToolRegistry::dispatch()`, which consults `&dyn Policy` (`constrain`) and, on a
block, returns a `ToolOutcome` with `status = Blocked` *without* invoking
`call()`. The kernel only ever sees `&dyn ToolDispatch` (ARCHITECTURE §5), so this
adapter is the single place the concrete aisdk function type is named.

## Built-in tool suite

The full set of tools registered at `Session::new()`. All are policy-vetted
before dispatch.

### Filesystem tools

| Tool | Description |
|---|---|
| `read_file(path)` | Read a file; returns content as string |
| `write_file(path, content)` | Create or overwrite a file; creates parent dirs |
| `edit_file(path, old_string, new_string)` | Targeted replacement; fails if 0 or 2+ matches |
| `list_directory(path)` | List directory contents |

checks that `read_file` was called on the same path in the current episode.

### Agent tool (subagent spawning)

```rust
#[tool]
/// Spawn a subagent Session to complete a focused subtask.
pub async fn agent(task: String, tools: Option<Vec<String>>) -> Result<String, ToolError>
```

Creates a child `Session` with an isolated history and the specified tool subset.
Inherits `Config` and `WorkspacePolicy` from the parent. `AgentDepthPolicy`
prevents recursion beyond `RUSTYKEYS_MAX_AGENT_DEPTH` (default 3).
The child's episode is recorded as a nested entry in `EvidenceJournal` (linked via
`parent_turn_id`; see
[data-model §4.1](../architecture/data-model.md#41-evidencejsonl--verification-consolidation-compaction-prd-05)).

**Construction via `SessionFactory` (ADR-0017).** The `agent` tool lives in `feed`
but a `Session` lives in `app`; constructing one directly would create a
`feed → app → feed` cycle. So `feed` defines a **`SessionFactory` trait**; `app`
implements it and injects it into the `ToolRegistry` (the `session_factory` field
above) at startup. The tool calls the trait, never the concrete type:

```rust
#[async_trait]
pub trait SessionFactory: Send + Sync {
    /// Build a child Session for a subtask. depth gates recursion; tools is the subset.
    async fn spawn_child(
        &self, task: &str, tools: Option<Vec<String>>, depth: usize,
    ) -> Result<Box<dyn ChildSession>, ToolError>;
}
```

**System-prompt / Task-State inheritance (resolves the unspecified inheritance):**

- **System prompt:** the child is built by the *same producer* at the *same
  harness level* (identity + tool-use protocol + H-rules + safety rails are
  inherited), so a subagent is held to the same discipline as its parent. *(v1
  intent, revisit after a spike — a focused "you are a subagent completing one
  subtask" identity preamble is an additive option; the
  [divergent→converge strategy](#divergent--converge-exploration-opt-in-fan-out-strategy)
  below reuses this same layer-1 override to seed distinct cognitive frames.)*
- **Task State:** the child does **not** inherit the parent's `TaskState`. Its
  `task` argument *becomes* the child's goal (the factory seeds a fresh child
  `TaskState { goal: task, scope: <parent scope or narrowed>, … }`), keeping the
  parent's drift-prevention and `BoundaryViolation` scope semantics intact within
  the subtask. The child's recall runs against the **shared** long-term store
  (subagents share `.rustykeys/`), so lessons learned anywhere are available.
- **Authority:** the child inherits the parent's `WorkspacePolicy` but only the
  requested `tools` subset — never broader authority than the parent.

#### Divergent → converge exploration (opt-in fan-out strategy)

> *v1 intent, revisit after a spike.* The cognitive-frame list, the branch count
> `N`, the deepen-`K`, and the cost cap below track ADR-0032 and are product calls,
> not a frozen contract. This describes the **pattern** (an MIT-licensed prior
> art); no third-party code is vendored.

The `agent` tool's default use is **decomposition** — spawn one focused worker for a
subtask. ADR-0032 adds a second, **opt-in** use — **divergent ideation** on
open-ended design — that the same `SessionFactory` already supports with **no new
infra**. The strategy:

1. **Fan out `N` isolated children.** Spawn `N` child `Session`s via
   `SessionFactory::spawn_child`, each seeded with the **same task** but a different
   **cognitive-frame** system-prompt preamble (an override of the producer's layer-1
   "Identity" — the "focused subagent identity preamble" already floated above, here
   given teeth: e.g. *regulator / speedrunner / $0-budget / infinite-budget /
   3am-on-call*). The branches share **no context** — separate `Session`s give
   isolation for free, so the generator/critic split is enforced *mechanically*
   (distinct Sessions, opposite preambles), not by a single-context promise. Fan-out
   is `tokio::JoinSet`/`join!` over `spawn_child` under `AgentDepthPolicy`.
2. **Mechanical critic / converge pass.** A convergence step — the parent, or a
   dedicated critic child under the *opposite* frame — runs a deterministic
   **score → cluster → deepen top-`K`** over the `N` results: score every leaf,
   cluster near-duplicates, prune traps, and deepen only the top-`K` candidates. The
   critic is one more aisdk call; the scoring/clustering is mechanical.
3. **Plan-mode "explore" option.** This is offered as a **plan-mode** option (PRD 06,
   `enter_plan_mode`): the fan-out runs *inside* plan mode (writes/bash already
   blocked), produces `K` candidate plans, and the user/critic approves one before
   `exit_plan_mode`. Divergent-explore → converge → approve maps 1:1 onto plan
   mode's lifecycle.

**Cost-gated.** `N` parallel children cost roughly **5–10× the tokens** of a
single-shot turn, so this is **opt-in behind an explicit strategy**, never the
default `agent` path, and is bounded by a **branch-count / cost cap** (`v1 intent` —
the software/integration architect owns the concurrency + depth + cost guard so the
fan-out cannot blow the budget). Reuses `SessionFactory`, `AgentDepthPolicy`, and the
layered system-prompt producer wholesale; the frame preamble is just a layer-1
override.

## Memory

Memory is the three-tier cognitive architecture:

```
Short-term stream  →  [consolidation]  →  Long-term graph
        ↑                                        ↓
   (Observe: capture)                    (Orient: recall)
        ↑                                        ↓
   Task State (working memory: goal + success criteria)
```

`Stream` and `Store` are plugin seams (ADR-0024), so the `Memory` facade holds
them as **`Arc<dyn …>`** — shared, object-safe handles that the post-turn
`tokio::join!` (consolidation) and the orient path (recall) can hold
concurrently without cloning the backend:

```rust
pub struct Memory {
    stream: Arc<dyn Stream>,         // short-term; SqliteStream in v1
    store:  Arc<dyn Store>,          // long-term;  SqliteStore (or DuckDB, Phase 5)
    task_store: Arc<TaskStore>,
    // embed model handle, config, …
}
```

### Short-term stream

An append-only log of observations: user messages, agent replies, tool events,
verification verdicts, task changes. Every event in the system passes through
`Stream::append()`.

```rust
pub trait Stream: Send + Sync {
    async fn append(&self, obs: &Observation) -> Result<()>;
    async fn recent(&self, n: usize) -> Result<Vec<Observation>>;
    async fn since(&self, ts: f64) -> Result<Vec<Observation>>;
}
```

`Observation` fields: `ts`, `role`, `kind`, `content`.

Default implementation: `SqliteStream` via `rusqlite` (append-optimised,
OLTP-pattern).

### Long-term graph

Consolidated memories: facts, summaries, skills, entities — with typed edges
between them. Recall queries this store to orient the kernel.

```rust
pub trait Store: Send + Sync {
    async fn upsert(&self, memory: &Memory) -> Result<()>;
    async fn candidates(&self, query: &str, embed: Option<&[f32]>, k: usize)
        -> Result<Vec<(Memory, f32)>>;
    async fn neighbors(&self, title: &str) -> Result<Vec<Memory>>;
    async fn prune(&self, older_than: f64, importance_below: f32) -> Result<usize>;
    async fn remove(&self, title: &str) -> Result<()>;
}
```

`candidates()` returns `(memory, relevance)` — each backend uses its best
strategy (FTS5 lexical for SQLite, `list_cosine_similarity` for DuckDB).

Skills (`type = "skill"`) are exempt from `prune()` **once `validated=1`** (ADR-0031;
see [Validation-gated skills](#validation-gated-skills)). A freshly minted *candidate*
skill (`validated=0`) is not yet exempt and decays/prunes like an ordinary memory
until it earns promotion. Promoted skills accumulate until grooming (refine / merge
/ split) consolidates them.

### Recall

Recall assembles the Orient layer: score candidates by relevance + recency +
importance, take top-k, expand 1-hop via `neighbors()`, and render an output
block capped at a token slice.

```rust
pub async fn recall(
    &self,
    history: &[Message],
    window: usize,
    k: usize,
) -> Result<String>
```

The query is built from the last `window` turns (`RUSTYKEYS_RECALL_WINDOW`,
default 6 — not just the latest message): a follow-up like "do that again" has
no retrieval signal alone; recent turns carry the topic.

When `RUSTYKEYS_EMBED_MODEL` is set, recall is semantic (embedding cosine).
Without it, recall falls back to FTS5 lexical (`bm25`) search — the system runs
on a chat key alone. `Store::candidates()` returns `(memory, relevance)` where
the raw `relevance` is `bm25` for lexical and cosine for semantic — **different
domains** (see [data-model §3](../architecture/data-model.md#3-long-term-store--storedb-sqlite--storeduckdb)).

#### Scoring formula

> *v1 intent, revisit after a spike.* Weights and τ are product-tunable starting
> points (cross-ref the open product decisions in the consolidated plan), not a
> frozen contract. They build on the AI-engineer review sketch (§5).

Per candidate, after **batch min-max normalization** of the raw relevance so the
FTS5/cosine score shares a `[0,1]` domain with the other two terms:

```text
score   = 0.55 * rel_norm + 0.25 * recency + 0.20 * importance
rel_norm = (relevance - min_batch) / (max_batch - min_batch)   # within the returned candidate batch
recency  = exp(-Δdays / τ)         # Δdays = (now - last_used_ts)/86400; τ = 14 (≈2-week decay)
importance = stored 0..1           # from memories.importance; *validated* skills floored at 0.6 (ADR-0011, ADR-0031)
```

- **Why normalize per batch:** combining a raw `bm25` magnitude (unbounded) or a
  cosine value (`[-1,1]`) directly with recency/importance is undefined behavior;
  min-max within the candidate batch puts all three terms on `[0,1]` before
  blending. (If a batch is degenerate — one candidate, or `max==min` — `rel_norm`
  defaults to `1.0`.)
- **Recency decay** reads `last_used_ts`; decay-at-read keeps the stored value
  stable (the systems-architect owns decay-at-read vs decay-at-write).
- **Skill importance floor (0.6)** keeps hard-won lessons from sinking below
  ordinary facts purely on age; floored skills are also exempt from `prune()`
  (ADR-0011), so the floor governs *recall priority*, not retention. **The floor
  applies only to *validated* (`validated=1`) skills** (ADR-0031): a freshly minted
  *candidate* skill (`validated=0`) is recall-eligible but unfloored — it scores on
  its emitted importance and decays/prunes like an ordinary memory until it earns
  promotion (see [Validation-gated skills](#validation-gated-skills)).
- **Failure-born skill boost (closing the loop — see
  [Self-improvement loop](#self-improvement-loop)):** when the current turn's
  attribution context matches a `type=skill` memory's stored failing condition,
  add `+0.15` to that skill's score (clamped to `1.0`) so the lesson surfaces
  *before* the agent repeats the mistake. Match = lexical/embedding similarity of
  the current `(failure_type, layer)` + recent-turn query against the skill's
  body above the candidate threshold. **The boost — like the floor — is reserved
  for *validated* skills** (ADR-0031); a candidate still surfaces on its own
  relevance but is not recall-privileged until promoted.
- **Tie-break:** `type=skill` > `summary` > `fact` > `entity`; then most-recent
  `last_used_ts`.

#### Selection + neighbor expansion

1. Take **top-k** by `score` (`RUSTYKEYS_RECALL_K`, default 6).
2. **1-hop neighbor expansion on the top-3 only** via `Store::neighbors()` (caps
   added tokens). Neighbors are de-duplicated against the top-k and appended under
   their anchor; they are not re-scored.

#### Output block (the string `recall()` returns)

> *v1 intent, revisit after a spike.* Capped at a configured token slice of the
> context window; when the cap is hit, drop lowest-scored entries first, then drop
> neighbor lines before primary entries.

```text
## Relevant memory
- [skill] <title>: <body>            (why: matched "<query frag>")
- [fact]  <title>: <body>
  ↳ related: <neighbor title>: <neighbor body>
- [summary] <title>: <body>
```

Empty corpus or no candidates above threshold ⇒ recall returns `""` (the
`orient()` join filters it out). The `[type]` tag is the snake_case `mem_type`;
the `(why: …)` annotation is best-effort provenance for the matched query
fragment.

### Consolidation

Distillation of short-term → long-term runs at three tempos:

| Tempo | Trigger | Behaviour |
|---|---|---|
| idle | after each turn if `len(recent) >= idle_threshold` | extract facts/summaries/skills from recent observations |
| sleep | session end | deeper pass; decay + prune non-skills |
| explicit | `/reflect` or `/sleep` command | user-triggered |

Each consolidation is an async aisdk call (model = `RUSTYKEYS_CONSOLIDATE_MODEL`,
defaulting to `RUSTYKEYS_MODEL`) with a structured prompt requesting JSON output.
`serde_json` deserialises the result; the store is updated via `Store::upsert()`.
The consolidation changelog is appended to the evidence journal as an
`improvement` record (ADR-0015; see
[data-model §4.1](../architecture/data-model.md#41-evidencejsonl--verification-consolidation-compaction-prd-05)).

#### Emit contract (`Memory` JSON the model returns)

> *v1 intent, revisit after a spike.* Field names/enum members track the
> AI-engineer review sketch (§5) and the `memories` table in
> [data-model §3](../architecture/data-model.md#3-long-term-store--storedb-sqlite--storeduckdb).

```json
{"memories": [
  {"op": "create|update",
   "type": "fact|summary|skill|entity",
   "title": "stable identity; edges and update target reference this",
   "body": "the durable content",
   "importance": 0.0,
   "edges": [{"to": "<title>", "rel": "relates|causes|supersedes|part_of"}],
   "source_ts_range": [t0, t1]}
]}
```

- `type` maps 1:1 to `memories.mem_type`; `importance` to `memories.importance`
  (`0.0..1.0`); `source_ts_range` to `source_ts_lo`/`source_ts_hi`; `edges[].rel`
  to the `memory_edges.rel` controlled set. The whole object is the storage shape
  of [data-model §3](../architecture/data-model.md#3-long-term-store--storedb-sqlite--storeduckdb).
- Records that fail `serde_json` deserialisation are **skipped and logged**, never
  fatal; a wholesale parse failure yields an empty changelog (`created=0,…`), and
  that degradation is itself recorded (graceful-degradation, ARCHITECTURE §11).

#### Importance rubric (aligned with the recall formula and data-model §3)

The emitted `importance ∈ [0,1]` is the *same scale* the recall formula consumes:

| Signal in the observation window | Emit | Importance |
|---|---|---|
| **UNVERIFIED outcome** (a failure/lesson) | one `skill` **candidate** (`validated=0`) | **≥ 0.8**; body = *the lesson + the failing condition* (so recall can match it later) |
| VERIFIED outcome reinforcing a known approach | `update` the skill used (bump `use_count`/importance; **promote** it if a candidate — see below) | ≥ 0.7 |
| Stable project fact (paths, conventions, decisions) | `fact` | 0.4–0.6 |
| Episode/period recap | `summary` | 0.3–0.5 |
| Named person/system/component | `entity` | 0.3–0.5 |

A failure-born skill is emitted as a **candidate** (`validated=0`): recall-eligible
but **not** yet floored and **not** yet prune-exempt. Only a *validated* (`validated=1`)
skill is floored at **0.6** at recall time (ADR-0011, ADR-0031) regardless of its
emitted value, so a *promoted* skill never sinks below an ordinary fact on age
alone — while an unproven candidate must still earn that durability (see
[Validation-gated skills](#validation-gated-skills)).

#### Create-vs-merge (dedup rule)

Before emitting `create`, the prompt instructs the model to prefer `update` when
a candidate `title` **lexically or semantically matches** an existing memory above
the candidate threshold (the same similarity gate recall uses). On `update`, the
store merges body/importance into the existing `title` rather than inserting a
duplicate. `supersedes` edges (and grooming `merge`/`split`, which call
`Store::remove()`) handle the cases dedup-on-title cannot.

#### Idle-vs-sleep prompt deltas

The three tempos share the emit contract; the **prompts differ**:

- **idle** (after a turn when `len(recent) >= RUSTYKEYS_IDLE_THRESHOLD`): *"Extract
  only NEW durable facts/skills from the last N observations. Do not restate
  memories that already exist."* Cheap, additive, no decay.
- **sleep** (session end): the idle prompt **plus** *"merge near-duplicate
  memories (`update`/`supersedes`), decay stale importances, and propose
  grooming."* This is the only tempo that runs decay + `prune()` (non-skills) and
  skill grooming.
- **explicit** (`/reflect` = idle-style, `/sleep` = sleep-style): user-triggered;
  same prompts.

#### Verification signals + attribution feed (closing the loop)

Verification signals (`kind = "verification"`) in the stream are high-value
consolidation input: UNVERIFIED outcomes generate the high-importance skill above;
VERIFIED outcomes reinforce the skill used. **Crucially, the consolidation prompt
also receives the structured `Attribution { failure_type, layer }` from compose**
(PRD 05) — not just the free-text reply. The prompt renders it as:

```text
Last turn failed verification.
  failure_type: f_verify     # fixed FailureType enum (ADR-0021)
  layer:        compose/semantic
  evidence:     <attribution.evidence>
Emit a `skill` capturing the lesson AND the failing condition above, so the next
similar turn recalls it before repeating the mistake.
```

This is the middle link of the self-improvement loop — see
[Self-improvement loop](#self-improvement-loop) for the end-to-end chain.

### Skill grooming

Once the skill count exceeds `RUSTYKEYS_SKILL_GROOM_THRESHOLD`, a grooming pass
asks the model to propose `refine`, `merge`, and `split` operations over the skill
set. Merges and splits supersede originals via `Store::remove()`. Grooming runs
on `/groom` (forced) and during `sleep`.

Grooming is the self-improvement loop's **optimizer step**, so it is
**non-regression-gated** (ADR-0031): a `merge`/`refine` that produces a new body is
emitted as a **candidate** (`validated=0`) unless it preserves the
`(failure_type, layer)` conditions its *validated* source skills already proved
against — a groom that would drop a previously-validated condition is rejected or
downgraded to candidate, so grooming can refine the skill set without silently
discarding a proven lesson. See [Validation-gated skills](#validation-gated-skills).

### Validation-gated skills

> *v1 intent, revisit after a spike.* The `validated` flag, the promotion trigger,
> and the non-regression conditions track ADR-0031 and the `memories` table in
> [data-model §3](../architecture/data-model.md#3-long-term-store--storedb-sqlite--storeduckdb);
> they are the design to build against, not a frozen contract.

A failure-born skill is **credulous** by default: a single UNVERIFIED turn would
otherwise mint a high-floor, prune-exempt, recall-privileged lesson that is as
durable as a proven one — even if it is wrong or over-fit. The `validated`
(`validated=0|1`) flag on the memory row (ADR-0031) closes that gap with an explicit
**candidate → promoted** lifecycle, so the self-improvement loop **cannot silently
un-learn**:

- **Candidate (`validated=0`).** The state a failure-born skill is minted in (the
  importance-rubric "UNVERIFIED" row). It is **recall-eligible** — the lesson still
  surfaces on its own relevance next turn — but it does **not** get the 0.6
  importance floor, the `+0.15` failure-born boost, or `prune()` exemption. It
  decays and prunes like an ordinary memory until it proves itself.
- **Promoted (`validated=1`).** A candidate is promoted — gaining the **floor +
  prune-exemption + recall boost** — only after it **validates**:
  - **Online:** a later turn whose attribution context *matches* this skill (the
    same `(failure_type, layer)` + condition match that drives the recall boost)
    completes **VERIFIED**. The loop's own real outcome on a matching condition is
    the held-out check — no extra hot-path LLM call. This sharpens step 4 of the
    [Self-improvement loop](#self-improvement-loop): a VERIFIED turn no longer just
    bumps `importance`, it *flips `validated=1`* on the matched candidate.
  - **Offline:** the candidate survives **golden-episode replay** in the regression
    suite (cross-ref [`eval-plan`](../dev/eval-plan.md) — a golden episode asserts a
    candidate skill promotes after a matching verified turn and that promotion does
    not regress).
- **Un-validation on human edit.** A human `direct_edit` (PRD 04) to a
  skill-derived `body` resets it to `validated=0` — a corrected lesson must
  **re-earn** promotion rather than inheriting the old skill's privileges. (The
  desktop memory browser, PRD 08, edits through the same path.)

Only *validated* skills receive the floor/boost/exemption; everywhere those
privileges appear — the recall floor and failure-born boost in
[Recall](#recall), the `prune()` exemption in [Long-term graph](#long-term-graph),
the importance rubric, and the grooming non-regression gate — they are conditioned
on `validated=1`.

### Self-improvement loop

The feed and compose layers together close the paper's learning loop. The prior
spec captured failures and ran recall, but the structured `Attribution` from
compose was only *journaled* — it never reached consolidation, and recall did not
privilege failure-born skills. That broken middle link is now wired. The
**end-to-end chain**:

```text
1. FAILURE     compose verifies the turn → UNVERIFIED; builds
               Attribution { failure_type (FailureType enum), layer, evidence }   (PRD 05)
                     │  structured, not free text (ADR-0021)
                     ▼
2. SKILL       consolidation prompt receives that Attribution as structured input
               (see Consolidation → "attribution feed") and emits a `skill`
               *candidate* (validated=0), importance ≥0.8, body = lesson +
               failing condition + the (failure_type, layer) context.   (this PRD)
                     │  Store::upsert()
                     ▼
3. RECALL      next similar turn: recall scores candidates; a *validated*
               failure-born skill gets a +0.15 boost (+0.6 floor) when its stored
               (failure_type, layer) + condition matches → surfaces in the
               "## Relevant memory" block of extra_context. A candidate still
               surfaces on raw relevance, just unprivileged.            (Recall → boost)
                     │  orient() → extra_context
                     ▼
4. BEHAVIOR /  the model reads the lesson *before* acting, avoids repeating the
   PROMOTE     mistake; the next verification is more likely VERIFIED. A VERIFIED
               turn on a *matching* condition flips the candidate to validated=1
               (PROMOTE — floor + boost + prune-exemption) instead of minting a new
               skill; a repeat failure leaves it a candidate to re-prove. (Validation-gated skills)
                     └────────────────────── loop ──────────────────────┘
```

Each hop is owned by a section above: **(1)** PRD 05 (`Attribution`); **(2)**
[Consolidation](#consolidation) (the attribution feed + importance rubric — emits a
**candidate**); **(3)** [Recall](#recall) (the failure-born skill boost, reserved
for *validated* skills); **(4)** the [system prompt's](#system-prompt-construction)
H2/H3 rules tell the model to trust recalled lessons, and a matching VERIFIED turn
**promotes** the candidate (`validated=1`) per
[Validation-gated skills](#validation-gated-skills) (ADR-0031) — so a proven lesson,
not every guess, earns durability. The loop runs every turn via the post-turn
`tokio::join!` (verify + consolidate observed together before the next turn's
recall; ARCHITECTURE §6, ADR-0012).

### Task State

`TaskState` is the working-memory tier: a single current goal + success criteria.

```rust
pub struct TaskState {
    pub goal: String,
    pub success_criteria: Vec<String>,
    pub scope: Vec<String>,   // declared file/dir/crate scope (drift + boundary heuristic)
    pub status: TaskStatus,   // Idle | Active | Done
    pub updated_ts: f64,
}
```

`scope: Vec<String>` is **required by the entropy `BoundaryViolation` heuristic**
(PRD 04), which flags a `write_file`/`edit_file` to a path outside the declared
scope. The previous struct omitted it while PRD 04 already referenced it; this
adds it and matches the `task.json` schema in
[data-model §8](../architecture/data-model.md#8-toml--config-shaped-files).
Scope entries are workspace-relative paths or path prefixes (e.g.
`["crates/feed/", "src/auth.rs"]`); an empty `scope` disables the boundary check.

Persisted to `.rustykeys/task.json` (schema in
[data-model §8](../architecture/data-model.md#8-toml--config-shaped-files)). The
agent maintains it via `set_task` and `complete_task` tools — no extra per-turn
LLM call.

**Where Task State is rendered (contradiction resolved).** The prior draft said
Task State was injected *into the static system prompt* here, while
[Context assembly](#context-assembly) said the oriented string lands *between the
system prompt and the first user message*. Those describe two different
positions. **Decision: Task State is rendered into `extra_context` via `orient()`
— it is NOT part of the static system prompt.** Rationale: the system prompt is
constant for the session (cacheable, harness-level-stable; see
[System-prompt construction](#system-prompt-construction)), whereas Task State
changes per turn (`set_task`/`complete_task`) and must reflect the *current*
goal. Putting a mutable value in the static prompt would defeat prompt caching
and risk a stale goal. The system prompt instead carries a *static instruction*
("an active task, if any, appears in the oriented context below — treat its goal
and success criteria as the current objective"); the *value* is rendered by
`TaskStore::render()` into `orient()` (see below). Recall is still anchored on
the goal regardless of where the rendered block lands.

`TaskStore::render()` produces a compact, stable block (empty string when
`status == Idle`):

```text
## Current task
Goal: <goal>
Success criteria:
- <criterion 1>
- <criterion 2>
Scope: <scope[0]>, <scope[1]>          (omitted when scope is empty)
Status: active
```

> *v1 intent, revisit after a spike* — the exact header wording and field order
> are a starting point, not a frozen contract.

## System-prompt construction

The kernel takes `system_prompt: String` and `extra_context: Option<&str>` as
*inputs* (PRD 01) but no PRD said who *produces* the system prompt or what goes in
it. The feed layer is that producer: alongside `orient()` (which builds the
per-turn `extra_context`), it builds the **static, per-session** system prompt
once at `Session::new()`. The split is deliberate:

- **System prompt** — *constant for the session*: identity, the tool-use protocol,
  the harness-level rules, and the safety rails. Stable ⇒ cacheable, and it never
  carries mutable state (no Task State value, no recall).
- **`extra_context`** — *per turn*: Task State render + recall (see
  [Context assembly](#context-assembly)).

> *v1 intent, revisit after a spike.* The exact wording of each layer is a
> starting point; a dedicated prompt registry (`docs/dev/prompts.md`) is a
> follow-up. Safety-rail content overlaps the `constrain` policy spec (PRD 02) and
> is co-owned with it.

### Producer

```rust
impl Feed {
    /// Built once per session; constant thereafter (drives prompt caching).
    pub fn system_prompt(&self, level: HarnessLevel, extra: Option<&str>) -> String {
        // identity → tool-use protocol → harness-level rules → safety rails → extra
    }
}
```

The producer is parameterised by `RUSTYKEYS_HARNESS_LEVEL` so the prompt *varies by
maturity level* (H1 omits the H3 reproduce→attribute→fix discipline; H0 has no tool
registry at all, so the tool-use layer is empty — ADR-0028). It composes with the
caller-supplied `extra_context` only by *referencing* it ("the oriented context
below"); it never inlines the oriented value, preserving cacheability.

### Layered template

Concatenated top→bottom; each layer is independently overridable:

1. **Identity** — who the agent is and its operating frame (an autonomous engineer
   in a workspace; OODA-driven; reports evidence and limits).
2. **Tool-use protocol** — how to call tools, the read-before-edit invariant for
   `edit_file` in AcceptEdits mode, that blocked/errored calls come back as a
   structured `ToolOutcome` to observe and recover from (not a hard stop), and that
   an active task (if any) appears in the oriented context — treat its goal and
   success criteria as the current objective. *(Empty at H0.)*
3. **Harness-level rules (H1/H2/H3)** — additive by level:
   - **H1**: use the tool registry; prefer minimal, reversible actions.
   - **H2**: project memory + Task State are available; set/refine the task with
     `set_task`, and trust recalled lessons (skills) surfaced in context.
   - **H3**: the **reproduce → attribute → fix → verify → report** discipline —
     reproduce before editing, record a structured `attribute_failure` (using the
     fixed `FailureType` enum) before any fix, and end with a `verification_report`
     linking requirements to evidence (PRD 05). Each level *inherits* the lower
     levels' rules (the controlled-visibility ladder, ARCHITECTURE §3).
4. **Safety rails** — the workspace is the policy boundary; never act outside the
   declared Task State `scope` without saying so; secrets in tool args/results are
   redacted downstream (do not echo them); web access is off unless enabled. These
   mirror the `constrain` policy (PRD 02) so the model is *told* the rules the
   policy *enforces*.

### Composition with `extra_context`

The final aisdk request is assembled by the kernel (PRD 01):

```text
system(system_prompt)               # static: identity → protocol → H-rules → rails
↓
[extra_context]                     # per turn: ## Current task  +  ## Relevant memory
↓
messages(history)                   # the conversation
```

`extra_context` lands **between** the static system prompt and the first user
message. This is the resolution of the two-places contradiction: the *static*
behavioral contract is in the system prompt; the *mutable* Task State value and
recall are in `extra_context` via `orient()` — never duplicated across the two.

## Context assembly

Before each kernel run, the feed layer assembles `extra_context` — the **Orient**
output. It is the *only* per-turn variable the kernel receives besides `history`;
the system prompt is constant for the session (see
[System-prompt construction](#system-prompt-construction)).

```rust
pub async fn orient(&self, history: &[Message]) -> String {
    let task_prompt = self.task_store.render();              // Task State (working memory)
    let recall = self.recall(history, self.config.recall_window, self.config.recall_k).await?;
    [task_prompt, recall].iter().filter(|s| !s.is_empty()).join("\n\n")
}
```

This string is passed to the kernel as `extra_context: Option<&str>`
(PRD 01) and injected **between the system prompt and the first user message**.
Both per-turn variable layers — Task State (`task_store.render()`) **and** recall
— live here; **neither is in the static system prompt** (the contradiction noted
under [Task State](#task-state)). The kernel receives an oriented view without
knowing where the context came from.

> **Token-budget note (v1 intent, revisit after a spike).** `extra_context`
> competes with `history` and the tool schemas for the context window. The recall
> block is capped at a configured token slice (see
> [Recall](#recall)); Task State is small and uncapped. Per-turn line-item
> budgeting across system prompt + `extra_context` + tool schemas + history, and
> the recall-vs-history de-dup rule, are tracked as a refinement (cross-ref the
> compaction tiers in PRD 06) and are not pinned here.

## Seams

- **Embedding model**: set `RUSTYKEYS_EMBED_MODEL` to any aisdk embed string for
  semantic recall. Absent → lexical fallback.
- **DuckDB backend**: `RUSTYKEYS_LONG_TERM_BACKEND=duckdb` for native vector
  search at scale (Phase 5).
- **MCP tools**: external MCP server tools registered in `ToolRegistry` with
  `mcp__<server>__<tool>` namespacing — see PRD 07.
- **Hierarchical rollups**: multi-cadence temporal consolidation (hourly/daily/
  weekly summaries-of-summaries). Tracked in BACKLOG.
- **Auto-maintained focus**: infer/refresh Task State automatically for turns
  where the agent doesn't call `set_task`. Additive to agent-driven approach.
- **Tool result classification**: explicit `ToolResultClassifier` (ok / blocked /
  error / truncated / timeout) for richer attribution — currently inferred from
  result string prefix.
