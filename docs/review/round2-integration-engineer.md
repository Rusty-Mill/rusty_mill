## 3. Recommendations

### R1 — Build PRD 07's `mcp` crate on `rmcp`; rewrite the transports as thin adapters *(refine; resolves the open PRD-07 "names no crate" gap)* — **P1, NOW (Phase-12 design)**

**What.** PRD 07 hand-specifies the wire for both roles: `StdioMcpClient` (manual `tokio::process` spawn + `initialize`/`initialized`/`tools/list` framing over stdin/stdout), `SseMcpClient` (manual `reqwest` + SSE + the heartbeat/reconnect-with-backoff sketched as NOW), and the `--mcp` server (manual `axum` SSE + the wire-protocol block `initialize`/`tools/list`/`tools/call`). All of this is the MCP state machine `rmcp` 1.7 already implements (stdio + streamable HTTP, client *and* server, an `#[tool]`-style macro). Concrete PRD-07 integration sketch:

- **`McpClient` trait stays** (our `list_tools`/`call_tool`/`server_name` contract) — it now wraps `rmcp`'s client handle rather than raw framing. `StdioMcpClient`/`SseMcpClient` become **constructors that hand `rmcp` a transport** (`rmcp` child-process transport for stdio; `rmcp` streamable-HTTP/SSE transport for `sse`), not protocol code.
- **Our layers sit untouched *above* `rmcp`:** `mcp__<server>__<tool>` namespacing, the `McpToolFn`→`ToolFn` adapter, `McpPolicy::before_tool` vetting (ADR-0007 still vets before dispatch), `ApprovalGate::McpToolFirstUse`, and the `"ERROR: MCP call failed: …"` `ToolOutcome` mapping. `rmcp` owns framing/lifecycle; RK owns policy/namespacing/approval — the boundary is clean.
- **Auth + TLS (Round-1 pins) are passed *into* `rmcp`'s HTTP transport**, not re-implemented: the `Authorization: Bearer <token>` header from `auth_token_env` and the non-loopback-`http://`-with-token rejection become transport config. Confirm `rmcp`'s SSE transport exposes a custom-header + TLS hook; if not, that gap is the one thing we wrap.
- **Heartbeat/reconnect:** prefer `rmcp`'s reconnect if it provides one; otherwise our bounded-backoff+jitter wrapper (mirroring `RUSTYKEYS_RETRY_*`) sits around `rmcp`'s transport. Either way `/mcp reconnect` drives it.
- **Server role (`--mcp`):** the `chat`-tool-over-`Session::send()` exposure (PRD 07 §MCP server) registers as an `rmcp` server tool; `rmcp` owns the `axum`/stdio transport and the `RUSTYKEYS_MCP_SERVER_TRANSPORT` switch. The harness layer is still not bypassed — `rmcp` is transport only.

**Why.** Re-implementing the MCP wire is undifferentiated work the harness should not own; `rmcp` is the *official* SDK, tokio-native (ADR-0003), spec-tracking, and proven in-language by opendocswork at sub-ms dispatch (so MCP won't dominate the turn cycle). It de-risks the single largest unknown before Phase 12 and shrinks PRD 07's transport structs to wrappers.

**Exact target.** Revise **`docs/prd/07-mcp.md`**: §"Transport implementations" (both client structs → `rmcp`-backed constructors), §"MCP server / Transports" (server wraps `rmcp`), §Seams (drop the hand-rolled framing as a seam; reconnect note references `rmcp`'s capability). The **ADR is the software-architect's** ("`mcp` crate builds on `rmcp`"); I own the **wire/auth/reconnect reconciliation inside PRD 07**.

**Rust + AI-first.** Pure in-ecosystem; no foreign stack. **License (load-bearing):** `rmcp` = **MIT** (verified by software-arch) → dependency-safe; **opendocswork-mcp = GPL-3.0 → reference its modular tool layout, never copy/vendor.** The supply-chain sign-off (`cargo deny`, full dep tree) is the **systems-architect's gate** — do not pin the version until that clears. *(proposal / v1 intent.)*

### R2 — Refine `RUSTYKEYS_WEB_ALLOWLIST` to "capability grant," add remote-vs-local MCP trust, and a tool-output inspection seam *(refine; the Anthropic article applied to my two surfaces)* — **P1, NOW (doc-only)**

**What.** Three precise edits to boundaries Round 1 just pinned, all from the article's documented incidents:

1. **Egress allowlist is a capability grant, not a destination filter (threat-model §4).** The Cowork incident: an attacker-embedded API key + a malicious workspace file caused Claude to upload other files to the attacker's account *through an allowed domain* (`api.anthropic.com`) — the proxy checked the destination, saw an allowed host, and passed it. Add a caveat to §4's `RUSTYKEYS_WEB_ALLOWLIST` text: **every function reachable through an allowlisted host is now an attack surface; an allowlist entry grants a *capability* (e.g. "POST to this API"), not merely "talk to this host."** State the residual-risk explicitly in §9: RK's egress guard is host/IP-level (SSRF floor + allow/deny) and **does not inspect credentials or request bodies** — exfiltration through an *approved* host with an attacker's key is **out of scope for v1** (the article's own fix was a body/credential-aware MITM proxy inside the VM — a `sandboxed`-profile concern, cross-ref systems-arch Rec 1). This is honesty about the boundary, not new mechanism.

2. **Remote-vs-local MCP trust split (PRD 07 + threat-model §1).** The article: *"remote versus local is more important than it seems"* — a local MCP server is auditable (read the code, pin the version), a remote one **can change behavior after you approved it**, so the install-time trust decision expires. threat-model §1 today lumps all "External MCP servers" as one "Untrusted input" row. Refine: **local (stdio) MCP = host software, audited like any installed dependency** (the user chose to run it; pinned, inspectable); **remote (SSE) MCP = untrusted and *mutable after approval*** — treat as the open internet, **run against fake/non-sensitive data first**, and note that `ApprovalGate::McpToolFirstUse` approval **does not bind the server's future behavior**. Add a one-line PRD 07 note: a remote MCP server's tool *descriptions and schemas* can change between sessions; re-enumeration on reconnect is not re-vetting. (Also: per the article, **localhost listeners are not implicitly trusted just because they're local** — reinforces the Round-1 finding that the `--mcp` SSE server and `127.0.0.1` MCP clients still sit on a trust boundary.)

3. **Tool output is an attack surface — a return-value inspection seam (threat-model §1/§4).** The article's GitHub-README case: a *trusted, audited* connector loaded a poisoned README straight into context; *"any input scanning applied to web pages needs to be applied to network-enabled tool results with the same rigor,"* and they *"err toward live inspection"* because after a poisoned return steers an exfil, the log just shows a successful authorized call — **no after-the-fact signal**. RK today treats MCP/web results as "data, not instructions" (threat-model §1) but has **no inspection point on the return path** — `McpToolFn::call` and `web_fetch` results flow straight into history. Pin a **seam** (not v1 mechanism): an optional **tool-return inspection hook** on `McpToolFn`/`web_fetch` results *before* they enter `history`, that a small/fast classifier (the article: *"doesn't need to be the one doing the reasoning"*) can occupy. v1 ships the seam + the existing redaction-on-emit; the classifier is a documented future fill. This is the *return*-path analog of `before_tool` (which guards the *call* path).

**Why.** These are the two surfaces I own (web egress, MCP trust) and the article is the authoritative source that Round 1's pins, while correct, were *destination/call-path* framed — the documented failures all slipped through *approved* paths and *return* values. The fixes are doc-only (caveats + a seam), cheap now, and expensive to retrofit once the journal/trust framing is fixed.

**Exact target.** **`threat-model.md`**: §4 (allowlist-as-capability caveat + §9 residual-risk line on credential/body-blind egress), §1 (split the MCP row into local-audited vs remote-mutable; add the return-value-as-attack-surface row). **`docs/prd/07-mcp.md`**: the remote-mutable-after-approval note + the return-inspection seam under §Seams. **`configuration.md`**: one line on `RUSTYKEYS_WEB_ALLOWLIST` pointing at the capability-grant caveat.

**Rust + AI-first.** All doc/framing + one trait seam (idiomatic, ADR-0024 trait-at-seam); the inspection classifier is an aisdk call (AI-first: a small model guards the big model's inputs). No code lifted (article = principles, no license). **Cross-dep:** the credential-aware-egress *enforcement* belongs to the systems-arch `sandboxed` profile (Rec 1); I document the v1 gap, they own the fill. *(proposal / v1 intent; doc-only NOW.)*

### R3 — Wire the OTel seam as a pull-based OTLP export over one lifecycle stream, with cost/latency attributes *(refine the existing seam; Eino aspects + AI-Q Phoenix + the Anthropic EDR note)* — **P2**

**What.** PRD 04 §Seams already names OpenTelemetry as a future fill ("`ToolEvent` maps cleanly to OTel span attributes"; BACKLOG "spans per turn, tool-call attributes, token counters"). Three refinements from this round, all integration-shaped:

- **One typed lifecycle stream → one OTLP exporter.** Eino's callback aspects (OnStart/OnEnd/OnError) are the same fixed lifecycle points the software-arch's `KernelEvent` enum will pin. The integration contract: the OTLP exporter is **one consumer of that single enum stream** (turn = span, tool call = child span), **not** bespoke instrumentation per call-site. I don't define the enum (software-arch's lane) — I assert the OTel exporter binds to it 1:1, same as `Tracer` and `RUSTYKEYS_TRACE` logging do.
- **Carry token/cost/latency as span attributes** (AI-Q's Phoenix profiling): the per-turn span should attach `tokens_used`/`session_total_tokens` (already in `TokenBudget`) + latency, so cost profiling is a query over traces, not a separate pipe.
- **Pull-based export model** (the article's EDR lesson): Anthropic found VM isolation that contained Claude *also blinded host EDR* — their mitigation was **pull-based OTLP exports** (admins retrieve event logs after the fact) rather than live monitoring. For RK this is the *right default shape* the moment the harness runs inside any isolation (the systems-arch `sandboxed` profile, Rec 1): the observe layer should **expose OTLP for pull** rather than assume an outside-the-boundary collector can see in. Note this in the seam so the export model is chosen correctly when isolation lands, and "budget for the EDR/visibility conversation early" (the article's explicit advice) for any `--gateway`/sandboxed deployment.

**Why.** The seam exists but is under-specified on *shape*: these three notes ($1$ avoids N bespoke instrumentation sites, $2$ makes cost observable, $3$ picks pull-based so isolation doesn't blind operators) are cheap to record now and prevent a wrong export topology later. All three are integration concerns (where the wire attaches), distinct from the enum itself.

**Exact target.** **`docs/prd/04-observe.md`** §Seams (OpenTelemetry bullet): expand to "binds to the single lifecycle-event stream (software-arch `KernelEvent`); span-per-turn + span-per-tool with token/cost/latency attributes; **pull-based OTLP** export model so an isolation boundary (systems-arch `sandboxed` profile) does not blind operators." **`BACKLOG.md`** OpenTelemetry item: add "pull-based exports; attributes carry cost." 

**Rust + AI-first.** `tracing` + `opentelemetry`/`tracing-opentelemetry` crates are idiomatic; no foreign stack (AI-Q is Python/Phoenix — we take the *attribute set* and pull-model, not the tool). **Cross-dep:** the `KernelEvent` enum is software-arch's; the `sandboxed` profile that motivates pull-based is systems-arch's. *(proposal / v1 intent for the seam shape; mechanism DEFER to the OTel phase.)*
