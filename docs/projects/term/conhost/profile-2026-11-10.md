# rusty_conhost profile, 2026-11-10 (card #785)

Where our console host spends its time after #1433 (the VT bulk path), and one proposed fix. No code changed.

## Method

- **Machine:** Beast, AMD Ryzen 9 7900X3D (12 cores), 63 GB, Windows 11 build 26300.9818. The machine was otherwise idle (3% load before the runs).
- **Commit:** `main` at `db325fada`. Release build, rustc 1.98.1.
- **Driver:** `conhost_bench` (the Phase B bench), console writer (`cat console`: std's stdout, so WriteConsoleW), 30x120. Each run starts a fresh console, so the grid is fresh.
- **Workloads:** the 8 from `gen_workloads.py`, at the default 4 MB size.
- **Timing:** best of 7. Each repetition was a separate `conhost_bench --reps 1` invocation, which runs ConPTY once and our host once per workload. Times are spawn to EOF plus the client's exit, as the bench measures them.
- **Fixed cost:** a 40 KB workload takes 5.7 ms on our host (7.0 MB/s), which is mostly spawn and exit. Every 4 MB row includes it.
- **Profiler:** a throwaway suspend-and-sample profiler outside the repo (std Rust over dbghelp). Every 1 ms it suspends each thread of the bench process, walks the stack with `StackWalk64`, and resumes the thread. Inline frames come from `SymQueryInlineTrace`. A thread whose RIP and RSP haven't moved since its last sample is blocked, so it is skipped.
  - The machine has WPR but neither WPA nor xperf, so ETW stacks couldn't be read.
  - Profiles used a copy built with `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only` in a separate target directory. The timed binary is the default release build.
- **Profile workloads:** the same 8 at 16 MB (`--size large`), 6 runs each (alt_screen_flicker: 3). At 4 MB an engine thread lives only 20–90 ms, too short to sample well.
  - Sampling slows our host by about a third (sgr_alternate: 121 → 80 MB/s). The shares below are of samples, not of wall time.
- **Engine busy share:** measured separately, with the sampler only reading thread CPU times (no suspends). It is the engine thread's CPU time divided by our host's wall time, over 6 runs of each 16 MB workload.

A CSI is scanned three times before the parser reads it: by `unwatched_csi` for its end, by `contains(b'\n')`, and by `watched_at`. Each byte is then copied three times on the engine thread: into `scratch`, into `OutputQueue.new`, and into the shared `VecDeque`.

## Proposed fix: parse the mirror after the reply

**What.** `Screen::forward` would still push bytes to the terminal at once, but would append them to a pending buffer instead of calling `feed`. The pending buffer is parsed in three places:
- by the engine after step 5 of its loop (`submit_read` with the write's reply) and before step 6 (`wait`), so the client is already preparing its next write while the mirror parses this one;
- by any read of the mirror before it reads, through one syncing accessor that replaces the direct `grid` field uses: read-back calls, cursor and size queries, the legacy path's margin checks, and the DSR/CPR answers in `route_vt`;
- at hang-up and shutdown.

**Why.** WriteConsoleW is synchronous. The client waits while the engine handles its packet, mirror parse included, and the engine waits while the client prepares the next one. The engine is busy 75–94% of the run and the parse is 32–89% of that, so the two halves never overlap today. Parsing after the reply overlaps the parse with the client's share.

**Expected gain.**
- Model: per packet, the time goes from E + C to (E − P) + max(C, P), where E is engine time, C the client's share and P the parse. On every workload here P > C, so the saving is C, the idle share: 23% ascii, 11% unicode_heavy, 6% unicode_2027, 13% sgr_churn, 11% sgr_alternate, 17% cursor_thrash, 16% scroll_heavy, 25% alt_screen_flicker. Geomean about **15% less wall time** at 16 MB, where the busy shares were measured. The gain is a little smaller at 4 MB, where the fixed 5.7 ms start-up is a larger share.
- Real programs do more work between writes than `cat`, so C is larger for them. For a program whose C exceeds P, the parse disappears from its write latency entirely.
- The gain grows as the engine gets cheaper, because C then becomes a larger share.
- It does not reduce CPU. The other buckets (scan, copies, lock, per-packet alloc) remain separate work.

**Risk: low to medium, about 100 lines in `screen.rs`, `console.rs` and `runtime.rs`.**
- The one real risk is a stale read-back: some path reading the grid before the pending bytes are parsed. Keeping the grid behind a single accessor that syncs first makes that hard to write by accident.
- Ordering is unchanged: bytes still reach the terminal in the order they were handled, and the mirror parses them in the same order.
- Memory stays bounded: the engine parses the pending buffer every turn, so it holds at most one turn's output, which §7.2 bounds.
- Tests: the existing core and `own_pty` suites and the parity suite. Add one core test that every read-back API sees all bytes from a write handled just before it, and one `sched` test that the sync runs after `submit_read` and before `wait`.
- Re-run this bench before and after.

**Also seen (not proposed here).**
- Fuse `client_vt`'s three CSI scans into one, and drop the `OutputQueue` intermediate copy and the zeroed per-packet payload `Vec`: about 10–20% of engine CPU on the escape-heavy workloads.
- Skip the scrollback push and pop in `Grid::scroll_up` when `scrollback_max` is 0: scroll_heavy and ascii.
- Both are CPU savings that compose with the fix above.
