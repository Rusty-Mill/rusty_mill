| 2026-10-27 | C31: `terminal.process` answers in text, `PID<TAB>NAME<TAB>COMMAND` per line from the foreground process up to the block's program, name and command escaped (`\\`, `\t`, `\n`, `\r`, other controls `\u{HEX}`, as ctl prints text; review on the C31 PR); `ProcessChanged` (kind 20) carries the new foreground group's leader pid and name, behind its own `Features::PROCESS` (bit 12). | 2026-10-27 | C32: named keys are a block method, `terminal.send-keys` with a repeated `key` (a character, or `enter`, `tab`, `space`, `backspace`, `escape`, arrows, `home`, `end`, `page-up`, `page-down`, `insert`, `delete`, `f1`–`f12`, after any of `ctrl+`, `alt+`, `shift+`), encoded by the server in xterm's encoding and needing the lease like `input`; a modifier a key has no encoding with is refused, not dropped. `terminal.format` gains optional flags `trim` (blank lines at either end), `unwrap` (join soft-wrapped rows, keeping their blanks) and `vt` (one reset-then-set SGR per style change, truecolor, each line back to the default style; no OSC 8 links) behind `Features::CAPTURE` (bit 13), through a new `Flag` parameter type | The server knows the program's cursor-key mode, so it encodes, not the client; flags keep `format` one method instead of a format enum, and a VT line that starts and ends in the default style can be printed or cut on its own. HTML capture waits for a client that needs it | Claude's defaults under the owner's Phase 2b go-ahead; for review on the C32 PR |
| 2026-10-27 | C33: a label is the existing `name`, now on all four kinds (blocks and clients start empty, and an empty name names nothing in a target). Four catalog methods `rename-session`, `rename-window`, `rename-block`, `rename-client` build one `Rename` message (type 0x10) whose target is whichever id field it carries; four events `session-renamed` … `client-renamed` (kinds 21–24), sent only on a real change. `list` ends with one client entry per connection (name, attached block), including the caller's own; `disconnect-client` (type 0x11) drops the target as the output budget does. All behind one `Features::LABELS` (bit 14); a block entry's name is sent to every client, since older decoders skip it. Every name, at creation or rename, is at most `MAX_NAME` = 256 UTF-8 bytes; a longer one is refused before anything changes (review on #1189) | "Name" is already the wire and model word, so labels add no second concept; per-kind events match the existing per-kind kinds, so rules and `wait --event` filter by `session`/`window`/`block`/`client` as before. Clients join `list` so ctl targets resolve them like the rest | Claude's defaults under the owner's Phase 2b go-ahead; for review on the C33 PR |

| 2026-10-27 | C34 may write agent settings outside the repo (gap check K4): `rusty-mux-ctl agent setup` writes Claude Code's `skills/rusty-mux/SKILL.md` and adds one `SessionStart` hook to its `settings.json` | Agents in a block should learn where they are and how to drive the mux without the person explaining it; the writes are opt-in per command and undone by `agent remove` | Owner (2026-10-27: "Step 6 then 7") |
| 2026-10-27 | C34 defaults: the directory is `--dir`, else `$CLAUDE_CONFIG_DIR`, else `~/.claude` (a project's `.claude` via `--dir`); the hook runs this ctl by absolute path, single-quoted for the POSIX shell Claude Code uses, and is ours only in exactly that shape (a `type: command` hook whose command is one single-quoted path ending in `rusty-mux-ctl` or `rusty-mux-ctl.exe`, then ` agent hook`), so a moved ctl is updated in place and no one else's hook is taken (review on #1190); it is one group with no matcher. Nothing is written until both files are checked; a skill without our mark, or a settings file that is not JSON or whose `hooks`/`SessionStart` has another shape, is refused, never replaced. The settings file is rewritten with sorted keys and two-space indent (`rusty_json`), so setup keeps its original bytes in `settings.json.rusty-mux.bak` and `remove` restores them when nothing else changed, otherwise removes only our hook and the containers it empties, keeping a `hooks` or `SessionStart` the backup had; a settings file setup created and left as `{}` is deleted. Every file setup or remove writes (temporary file, backup, skill) is created exclusively and private before any bytes go in: mode 0600 on Unix, then the old file's mode; on Windows an owner-only protected DACL (`platform_windows::fs::restrict_to_owner`) set while the handle shares no access, failing closed if it cannot be set, so a replaced settings file loses any broader grants it had rather than gaining the directory's; then a rename that follows a symlink (review on #1190). `status` exits 0 only when both are current. The hook prints only inside a block. Only Claude Code; no `--agent` flag until a second agent | Undo should leave the person's files as they were; a refusal is cheaper than a lost setting; one agent needs no selector | Claude's defaults under the owner's approval; for review on the C34 PR |
| 2026-10-27 | C12 model: a window's layout is a binary split tree (`rusty_mux_core::Layout`) whose leaves are exactly its blocks, each split `cols` (side by side) or `rows` (stacked) with the first child's share in percent, at most 32 splits deep; one optional zoomed block per window. Text form `cols50(A,rows50(B,C))` on the wire (field 34) and in ctl. `split-block` (type 0x12) halves its target, `zoom-block` (0x13) and `unzoom-window` (0x14) set the zoom, and `close-block` is close-pane: the sibling takes the split's place. `layout-changed` (kind 25) carries the whole layout and zoom, after the `block-created` or `block-closed` that caused it; closing a whole window sends none. All behind `Features::LAYOUT` (bit 15); window entries in `list` carry the layout for every client, since older decoders skip the fields | A binary tree with a share is the smallest model that tiles a screen and later takes resizing; the whole layout in each event saves a renderer a `list` round trip; keeping `close-block` as the pane close avoids a second way to end a block | Claude's defaults under the owner's Phase 2b go-ahead; for review on the C12 PR |
| 2026-10-27 | C12 placement and size: a block from `create-block` (and so `run`) splits the window's largest block, side by side when that block's columns are at least twice its rows, stacked otherwise, and leaves a zoom alone; `split-block` unzooms. A split block gets its half of the target's size, a one-cell divider between, and the target keeps its own size until a lease holder resizes it; a target with under 3 cells on that axis is refused. The server does not resize blocks to a layout: a window has no size yet, and each client draws at its own | An agent's background `run` should not disturb what the person is zoomed on, while an explicit split is a request to see the block. Resizing needs the lease, so the server does not take it; choosing one size for clients of different sizes is the renderer's question, for the attach-client PR | Claude's defaults under the owner's Phase 2b go-ahead; for review on the C12 PR |
